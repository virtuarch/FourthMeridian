# v2.7 — Adjusted-cash basis cutover runbook (2026-10-27)

**Scope.** PR #56 made today's/future `SpaceSnapshot` rows store cash / assets /
net worth on the ADJUSTED basis (pending bank activity the bank has not yet
deducted is netted out). History is immutable — no backfill, no schema stamp.
The only record of where the basis changes is the **cutover marker**, which
drives the one-line chart note under the Net Worth / Assets / Cash trends
(`AdjustedBasisNote`). This runbook covers how the marker is set per
environment, how to verify the first post-release snapshot, how the cutover-day
discontinuity is disclosed, and rollback.

Code: `lib/balances/adjusted-basis.ts` · test `lib/balances/adjusted-basis.test.ts`.

---

## 1. Semantics (why the marker is a changeover DAY)

| Clock | What it is | Role |
|---|---|---|
| `SpaceSnapshot.date` | UTC calendar day (`@db.Date`) | Row key; chart points are these days |
| Live writer run time | Any refresh / webhook / cron / account change | Upserts **today's UTC row** only; never an earlier day |
| `SpaceSnapshot.createdAt` | First insert of the row (no `updatedAt` exists) | `createdAt ≥ T` proves the row is adjusted; `createdAt < T` proves nothing |
| Deployment go-live `T` | When the adjusted code starts serving | Defines the changeover day `C` = UTC day of `T` |
| User-local display | Viewer's time zone | **Not used** — the note formats UTC days with `timeZone: "UTC"`, same as the chart axis |

For a go-live at instant `T` on UTC day `C`:

- rows dated **before `C`** — written only by old code ⇒ **reported**;
- the row dated **`C`** — adjusted **iff its last write came after `T`**. A row first
  written before `T` and not touched again before 24:00 UTC stays reported ⇒ **may be either**;
- rows dated **after `C`** — written only by new code ⇒ **adjusted**;
- exception: `T` exactly `00:00:00Z` ⇒ no mixed day, `C` is adjusted.

Example — deploy at 23:50 UTC on D: D's row is adjusted only if some refresh,
webhook or cron rewrote it in the last ten minutes of D. D+1 is the first day
that is certainly adjusted.

The old single date constant (`ADJUSTED_CASH_BASIS_SINCE = "2026-10-28"`, "first
adjusted day") could not express this: set to D it mislabels D whenever D's row
was not rewritten after `T`; set to D+1 it calls D "bank-reported" whenever it
was. It was also one value for every environment, so Production (which adopts
the basis on a later promotion date) would have disclosed Preview's date.

### Mechanism

`NEXT_PUBLIC_ADJUSTED_CASH_BASIS_CUTOVER` — a public, build-time env var, inlined
by Next into both server and client bundles (same pattern as
`NEXT_PUBLIC_TURNSTILE_SITE_KEY`; server render and hydration always agree; no
prop plumbing, no schema change). Accepted values:

- `YYYY-MM-DD` — the UTC changeover day (time unknown ⇒ that day is "may be either"). **Recommended.**
- `YYYY-MM-DDTHH:MM[:SS[.sss]]Z` or `…±HH:MM` — the exact go-live instant (zone required).

Missing, empty, malformed, zone-less, impossible (`2026-02-30`) or earlier than
2026-10-27 ⇒ the code default `ADJUSTED_CASH_BASIS_CUTOVER_DEFAULT = "2026-10-27"`.
It never crashes, and never hides the note for a valid default.

A window discloses when it holds a day that may be reported and a later day that
may be adjusted (`from < to`, `from ≤ lastReportedDay`, `to ≥ changeoverDay`).
The note:

> From Oct 28, 2026 (UTC), cash is net of pending bank activity not yet deducted
> from the bank's balance; points before Oct 27 use bank-reported balances, and
> Oct 27, the changeover day, may use either.

(For a midnight-exact instant: "…; earlier points use bank-reported balances.")

### Per-environment values

| Environment | Go-live | Correct value | Set where |
|---|---|---|---|
| develop / **Preview** | f84feac merged 2026-10-27T01:51:54Z, Preview live ~02:00Z | `2026-10-27` (changeover day; 10-26 and earlier reported; 10-27 either; 10-28+ adjusted) | Code default — **no env needed** |
| Development (local) | n/a | code default | — |
| **Production** | the future promotion | the UTC day the promotion deployment goes live | Vercel env, Production scope, **before** the promotion build (§2) |

The previous constant (`2026-10-28`) was wrong for Preview in the strict sense:
Preview's 2026-10-27 row was almost certainly rewritten after ~02:00Z (any
refresh does it), so the jump sits between 10-26 and 10-27 while the note said
10-28 and called 10-27 bank-reported.

**How a reader can tell a row's basis:** `date < C` ⇒ reported; `date > C` ⇒
adjusted; `date = C` ⇒ adjusted if `createdAt ≥ T`, otherwise undeterminable from
the row (its live account inputs are gone). The chart note says exactly that.

## 2. Production activation procedure

**Who:** the owner (Vercel environment variables are owner-only; agents
document, never change Vercel env). **When:** in the Production promotion that
first carries PR #56 (develop → main).

1. **Pick the promotion slot.** Avoid 23:30–00:30 UTC so the build/go-live
   cannot straddle midnight and land on a different UTC day than planned.
2. **Before merging the promotion PR**, in Vercel → Project → Settings →
   Environment Variables, add for the **Production** scope only:
   `NEXT_PUBLIC_ADJUSTED_CASH_BASIS_CUTOVER = <planned UTC date, YYYY-MM-DD>`.
   Do not set it on Preview (Preview uses the code default, which is correct).
   `NEXT_PUBLIC_*` is inlined at build: it MUST exist before the build starts.
3. Merge the promotion PR; wait for the Production deployment to be **Ready**.
4. Record the deployment's go-live time (Vercel deployment "Ready" timestamp,
   or `vercel inspect <deployment-url>`), converted to **UTC**.
5. **If the UTC date of go-live ≠ the value set in step 2** (slot slipped past
   midnight): update the env value to the actual UTC date and **Redeploy** the
   same deployment (Vercel → Deployments → … → Redeploy, without build cache).
   Optional precision: set the exact instant (`2026-11-12T15:04:00Z`) instead —
   only matters if go-live was exactly 00:00:00Z.
6. Verify (§3). Record date, go-live instant, deployment id and value in STATUS.md.

**If step 2 is forgotten:** Production shows the code default (Preview's
2026-10-27). For a Production window it then misplaces the disclosure (says the
change happened Oct 27/28, and may stay silent on a window that spans the real
Production changeover). Fix: set the variable to the real UTC go-live date and
redeploy. No data is affected; only the note's wording/visibility.

## 3. Verifying the first post-release snapshot (read-only)

Only transaction-scoped read-only access. **Never** `SET` at session level
through the pooler (a session `SET default_transaction_read_only` once leaked to
`fm_system` and broke Preview AI). Use `psql -1 -c "SET TRANSACTION READ ONLY; …"`.

Let `C` = changeover day, `T` = go-live instant (UTC), `<space>` = a Space with a
checking/savings account that has pending transactions.

**3a. Rows around the cutover** (run on C+1 or later):

```sh
psql "$PROD_DATABASE_URL" -1 -c "SET TRANSACTION READ ONLY;
SELECT date, \"createdAt\", cash + savings AS cash_total, \"totalAssets\", \"netWorth\", \"isEstimated\"
FROM \"SpaceSnapshot\"
WHERE \"spaceId\" = '<space>' AND date BETWEEN DATE '<C>' - 1 AND DATE '<C>' + 1
ORDER BY date;"
```

Expect: C−1 `createdAt` < T (frozen, reported); C+1 `createdAt` ≥ T (adjusted by
construction); C — adjusted if `createdAt ≥ T`, otherwise either.

**3b. The C+1 row is on the adjusted basis** — compare it with the reported sum
of the Space's depository accounts and their pending activity:

```sh
psql "$PROD_DATABASE_URL" -1 -c "SET TRANSACTION READ ONLY;
SELECT fa.id, fa.type, fa.balance AS reported_c, fa.\"availableBalance\" AS available_a,
       COALESCE(SUM(t.amount) FILTER (WHERE t.pending AND t.\"deletedAt\" IS NULL), 0) AS pending_p
FROM \"SpaceAccountLink\" l
JOIN \"FinancialAccount\" fa ON fa.id = l.\"financialAccountId\"
LEFT JOIN \"Transaction\" t ON t.\"financialAccountId\" = fa.id
WHERE l.\"spaceId\" = '<space>' AND l.status = 'ACTIVE' AND fa.type IN ('checking','savings')
GROUP BY fa.id, fa.type, fa.balance, fa.\"availableBalance\";"
```

For each account with `|C + P − A| ≤ 0.01` (PENDING_EXCLUDED) the adjusted
balance is `C + P`; otherwise `C`. The latest row's `cash_total` must equal
Σ adjusted (as of its last write), not Σ `reported_c`. In the app, the Cash hero
"today" figure equals today's row `cash_total`.

**3c. UI.** On the Net Worth trend, choose a window spanning C (e.g. 1M on C+1):
the note appears, naming C+1 as "From … (UTC)" and C as the changeover day. A
window starting after C shows no note.

Do not open `/dashboard/brief` on Production for this check (it triggers generation).

## 4. Expected chart discontinuity and its disclosure

On any Space whose depository accounts had pending debits/credits at go-live,
cash / total assets / net worth step by Σ(pending correction) between the last
reported day and the first adjusted day — on C−1→C if C's row was rewritten
after T, else on C→C+1. It is a change of basis, not a money movement. It is
disclosed by the note whenever the plotted window spans it (Net Worth, Assets
and Cash trends; not Debt / Invested, which the basis does not touch). Change
ledgers/"what moved it" may attribute the step to cash; that is expected for the
changeover window only. Nothing is backfilled; old rows stay reported forever, so
the note keeps appearing for windows that span C.

## 5. Rollback

- **Note wrong only (date):** fix `NEXT_PUBLIC_ADJUSTED_CASH_BASIS_CUTOVER` in the
  Production scope and redeploy. Removing it falls back to the code default
  (Preview's day) — wrong for Production; prefer correcting it.
- **Revert the adjusted basis itself** (Vercel instant rollback to the previous
  Production deployment, e.g. v2.6.0 `dpl_Dq2joJaa` / the pre-promotion one):
  the writer returns to the reported basis from the rollback instant `R`. Rows
  dated after C up to R's day stay adjusted (immutable); R's day is again
  "either". The note in the rolled-back build does not exist (pre-#56) — the
  adjusted window is undisclosed until re-promotion. Record C and R in STATUS.md;
  on re-promotion set the marker to the **original** C (the first day the basis
  reached Production), since the history between C and R is adjusted. A second
  discontinuity at R is then undisclosed by design — no schema stamp exists to
  describe two boundaries; raise a schema follow-up if that window matters.
- No DB writes are part of activation, so there is nothing to undo in the database.
