## 0 · Executive answer

**Yes — but not as one abstraction over everything.** Two findings shape the whole recommendation.

**F1 · Fourth Meridian has two kinds of lens, and the Investments engine generalises to only one of them.**
STOCK lenses (Net Worth, Investments, Liquidity, Debt, Cash, Savings, Crypto) ask *"what did you have on date D"*. FLOW lenses (Income, Spending, Cash Flow) ask *"what moved between D₁ and D₂"* — they are built on `lib/transactions/cash-flow-*`, not on `SpaceSnapshot` **[EXISTS]**. A composition authority whose unit is a *position at a date* cannot answer a question whose unit is *a transaction over an interval*. Forcing one abstraction across both produces a model that fits neither. The recommendation is **one drill-down PRIMITIVE, two composition AUTHORITIES** — and the flow authority is deliberately out of scope for this arc.

**F2 · The drill-down tree already has authorities at its two lowest levels and none at its highest.**

| Level | Question | Authority today |
|---|---|---|
| 0 · Space aggregate | what made up Net Worth? | **[ABSENT]** — no aggregate authorisation |
| 1 · Bucket | investments / cash / debt / crypto | columns exist, no authorisation |
| 2 · Account | what was this account worth? | `getAccountsAsOf` **[EXISTS]**, single date only |
| 3 · Holding | what was this position? | `historicalHoldingsForWindow` + `getHistoricalPointDetail` **[EXISTS]** |

We built the hardest level first. What is missing is not an engine — it is **authorisation at the top and a series at the middle**.

**The single largest architectural decision in this document:** there is no per-account historical *series* anywhere. `SpaceSnapshot` is Space-level (ten float columns) **[EXISTS]**. Every "account history chart" the vision asks for needs one. **Recommendation: compute it on demand from the existing as-of resolvers; do NOT persist it.** §5.

## 1 · What already exists (the head start is larger than it looks)

**The chart primitive is already universal.** `TrendChart` is shared by Net Worth, Investments, Debt and Liquidity **[EXISTS]**, and V26-S4 gave it an optional `onSelectPoint` that reports a **date and nothing else**. Every lens gains click-to-explore by passing one prop. No chart work is required for any lens.

**The panel primitive is already shared.** `components/atlas/panels/{Panel,RightPanel,PanelHeader,PanelContent}` **[EXISTS]**, already used by Wealth, Investments and Transactions.

**The time window is already inherited.** `asOf` / `compareTo` / `preset` live in the URL and are owned by the Perspective Shell **[EXISTS]**. A drill-down inherits by construction if it reads the same params.

**The as-of account resolver exists.** `getAccountsAsOf({ spaceId, asOf })` returns every visible account with its balance resolved to that date, stamped `{ method, tier }` **[EXISTS]**. Liquidity and Debt already consume it.

**The historical composition authority exists and is proven.** `getHistoricalPointDetail` returns components, exclusions, scope categories, four reconciliation states and a denominator; the standing probe reports **366/366 dates EXACT** **[EXISTS]**.

**What this means:** the vision is roughly 60% built. The remaining work is concentrated in three places — aggregate authorisation, per-account series, and one navigation primitive.

## 2 · The recommended architecture

### 2.1 The model: authority-based, with a thin DTO at the seam

The question asked whether this should be DTO-, service- or authority-based. **Authority-based, with a single serialisable DTO at the API seam.** Not because it is more elegant — because of what each alternative fails at:

- **DTO-first** would let each lens shape its own payload, and the shapes would drift. The V26 arc's whole lesson is that a second shape becomes a second engine.
- **Service-first** (one `HistoricalService.explain(anything)`) forces one function to know every lens's semantics. It becomes the god-object the perspective engine already refused once.
- **Authority-based** keeps each *question* with the module that owns it, and composes them at one seam.

```
                    ┌──────────────────────────────────────┐
                    │  HistoricalNode  (the ONE DTO)       │
                    │  — one selected date                 │
                    │  — inherited window / currency       │
                    │  — displayed total                   │
                    │  — components[] (each a child node)  │
                    │  — reconciliation state + remainder  │
                    │  — provenance + scope categories     │
                    │  — breadcrumb ancestry               │
                    └──────────────────────────────────────┘
                                    ▲
              ┌─────────────────────┼─────────────────────┐
              │                     │                     │
      spaceAggregate()       accountSeries()        holdingDetail()
      [PROPOSED]             [PROPOSED, thin]       [EXISTS]
              │                     │                     │
              └──────── all consume ─┴─────────────────────┘
                                    │
   ┌────────────────────────────────┴──────────────────────────────┐
   │ CANONICAL AUTHORITIES — unchanged, never duplicated           │
   │  getInvestmentValueForWindow   the ONE valuation engine       │
   │  loadHoldingOwnership          the ONE ownership engine       │
   │  buildHistoricalHoldings       the ONE holdings-set builder   │
   │  valueCryptoDay                the ONE crypto day valuation   │
   │  getAccountsAsOf               the ONE as-of account resolver │
   │  classifyAccounts              the ONE bucket partition       │
   │  convertMoney / ConversionCtx  the ONE FX seam                │
   │  resolveCryptoValuationState   the ONE crypto authorisation   │
   └───────────────────────────────────────────────────────────────┘
```

### 2.2 `HistoricalNode` — the smallest canonical model

One recursive shape. Every level of the tree returns it; the UI renders it without knowing which level it is looking at.

```
HistoricalNode
  id            "space" | "bucket:investments" | "account:{id}" | "holding:{acct}|{inst}"
  label         display name (never a synthesised phrase)
  dateISO       the selected date
  windowFrom/To the INHERITED range, carried down untouched
  currency      the reporting currency, inherited
  total         the displayed value at dateISO
  totalBasis    "observed" | "reconstructed"      ← is `total` a recording or a computation?
  series        [{ date, value, basis }]           ← the child chart, over the inherited window
  components    HistoricalNode[]                   ← the next level down
  state         EXACT | PARTIALLY_ATTRIBUTED | CONTRADICTORY | UNAVAILABLE
  remainder     number | null                      ← observed − explained, or null
  heldCount / valuedCount                          ← the historical denominator
  scope         { notYetOwned, alreadyClosed, ownershipUncertain, excludedArtifact, heldUnavailable }
  provenance    { quantity, price, ownership, fx } each an existing tier
  reason        the authority's own sentence
  drillable     boolean                            ← does a child level exist?
```

Three properties make this work and are worth stating as rules:

1. **`components` are themselves nodes.** The drill-down is `node.components[i]`, resolved lazily. There is no separate "child request" shape.
2. **`state` and `remainder` mean the same thing at every level** — the V26-S4 vocabulary, unchanged. A reader who learns it once knows it everywhere.
3. **`series` is the child's chart.** Clicking a component and seeing its chart is the same object, one level down — not a different endpoint with a different contract.

### 2.3 Why the Investments engine is the right precedent — and where it must NOT be copied

Copy: the four states, the observed-vs-derived tolerance split, the scope categories, the "photograph of the date" rule, the refusal-over-partial-lie posture.

Do **not** copy: `getHistoricalPointDetail`'s *shape*, which hardcodes `stocks + crypto`. Generalising it by adding parameters would grow the god-object. The generalisation is the **DTO**, not the function.

## 3 · Stock lenses vs flow lenses — the boundary this arc must respect

| | STOCK lens | FLOW lens |
|---|---|---|
| Lenses | Net Worth, Investments, Liquidity, Debt, Cash, Savings, Crypto | Income, Spending, Cash Flow |
| Unit | a position/account **at a date** | a transaction **over an interval** |
| Source | `SpaceSnapshot` + `PositionObservation` | `Transaction` **[EXISTS]** |
| "Point" | a balance | a period sum |
| Composition | held set on date D | transactions in [D₁, D₂] |
| Denominator | holdings that existed | *(none — a count of transactions is not a coverage ratio)* |
| Reconciliation | Σ components (+ remainder) = point | Σ transactions = period total |
| Ownership | load-bearing | irrelevant |

The reconciliation *shape* is analogous; the *evidence model* is not. **Recommendation: this arc covers stock lenses only.** Flow-lens drill-down is a genuinely valuable but separate initiative, and it is already partly served — `TransactionSliceDrawer` **[EXISTS]** does transaction-level drill-down for Cash Flow today. Attempting both in one arc would force `HistoricalNode` to carry two disjoint halves, and a DTO where half the fields are always null for half the callers is two DTOs wearing one name.

## 4 · The four slices

### Slice A — Aggregate authorisation (the unlock)

**Nothing else can be built honestly first.** Components carry authorisation; aggregates do not.

`SpaceSnapshot.cryptoValuationStatus` authorises `crypto` alone **[EXISTS]**. `netWorth`, `totalAssets`, `total`, `netLiquid` are computed from it and carry nothing. The V26-S4 probe measured **378 rows whose crypto may not be asserted while their aggregates assert freely** **[EXISTS]**. Net Worth explainability on such a row would produce a breakdown that reconciles to a number the engine itself refuses.

Scope:
- Extend the read boundary (`lib/data/snapshots.ts` — already the single authority resolving `cryptoAssertable`) to derive **aggregate** assertability from component assertability.
- Define the rule once: *an aggregate may be asserted only when every component it sums is assertable.* Otherwise it is `PARTIALLY_ATTRIBUTED` (a known part plus a stated unknown) or `UNAVAILABLE`.
- No schema change. No regeneration. Derivation at the read boundary, exactly as `cryptoAssertable` is today.

**Deliberately NOT in scope:** the nullable-component migration. V26-S4 concluded outcome A+B were sufficient and C unsafe; that holds until aggregates carry authorisation — which is what this slice provides. Revisit *after*.

**Risk:** Net Worth points that today render will begin refusing or partially attributing. That is the correct outcome and it will look like a regression. It must ship with the honesty story, not quietly.

### Slice B — `HistoricalNode` + the Net Worth root

Introduce the DTO and one composer for the top two levels.

- `spaceHistoricalNode({ spaceId, dateISO, window })` → root node whose components are the buckets, from `classifyAccounts`' existing partition **[EXISTS]** — never a new bucket vocabulary.
- Buckets that already have a composition authority delegate to it (Investments → `getHistoricalPointDetail`, refactored to *return a node* rather than its own shape).
- Buckets that do not yet (cash, savings, debt, real assets) resolve to account-level components via `getAccountsAsOf`.
- Reconciliation at the root: `Σ buckets + remainder = netWorth`, under Slice A's authorisation.

**Dependency: A.** Without aggregate authorisation the root's `state` cannot be computed honestly.

### Slice C — Account series

The one genuinely new capability. §5 covers the build-vs-persist decision.

- `accountHistoricalSeries({ accountId, window })` → `{ date, value, basis, tier }[]`.
- Composed, never re-derived: investment/crypto accounts from `getInvestmentValueForWindow` (already a *window* call **[EXISTS]** — it values N dates from one read); cash/debt accounts from the `accounts-asof.core` walk-backs, lifted to a window.
- Observation precedence, frozen rows and unsupported intervals inherit the existing rules unchanged.

**Dependency: B** (for the node shape). Independent of A.

### Slice D — Holding history and "what changed?"

Position-level: quantity series, price series, the transactions and corporate actions behind them, ownership episodes.

Almost entirely a **re-presentation of existing evidence**: `PositionObservation` (quantity), `PriceObservation` (price), `InvestmentEvent` (transactions), `CorporateActionTerms` (actions), `loadHoldingOwnership` (episodes) — all **[EXISTS]**.

The one genuine gap is **multiple ownership episodes**. V26-S4 shipped `interiorClosureISO` as a *detector* **[EXISTS]**; a holding panel that shows episodes needs the *model*. This is the natural place to do it: `OwnershipSegment[]` already exists as a shape — `resolveOwnershipWindow` must be taught to emit more than one KNOWN segment, driven by an alternating positive/zero observation sequence.

**Dependency: B.** Best done last, because it is the only slice that changes an ownership rule, and it should land where its blast radius is smallest.

## 5 · The central decision: compute the account series, do not persist it

**Recommendation: compute on demand. [PROPOSED]**

For:
- A persisted per-account series is a **second fact store derived from the first** — precisely what the anti-`FinancialState` ruling refused, and what `historical-holdings` deliberately avoided in V26-S2.
- It would need migrating on **every** engine correction. This arc shipped four in four slices; each would have invalidated a persisted series.
- The reads are already batched: `getInvestmentValueForWindow` values an entire window from one position read, one price read and one FX context **[EXISTS]**.
- A drill-down is a **deliberate user action on one account**, not a page-load fan-out. The N is one account × one window, not every account × all history.

Against (and worth measuring before dismissing):
- A 2-year daily window is ~730 points per account. For cash/debt that is a walk-back per date unless the walk is done once and sampled — it should be.
- The Space-level chart still reads persisted `SpaceSnapshot`; account charts would be computed. **Two mechanisms, and they must reconcile.** This is the strongest argument for persistence and the reason §10's invariant P3 exists.

**Trigger to revisit:** if a measured account-series request exceeds ~500 ms warm, persist a `AccountDailyValue` projection — but as a *cache with a version stamp keyed to the engine version*, invalidated by regeneration, never as a fact.

## 6 · Expected changes

### 6.1 Database — **none required for A, B, D; none recommended for C**

| Slice | Change | Verdict |
|---|---|---|
| A | none — derive at the read boundary | **no migration** |
| B | none — compose existing rows | **no migration** |
| C | optional `AccountDailyValue` cache | **defer**; measure first |
| D | none — `OwnershipSegment[]` already supports multiple segments in shape | **no migration** |

The nullable-component migration remains **deferred**, now with a stated precondition: aggregates must carry authorisation (Slice A) before nulling a component can be reasoned about.

### 6.2 API

One route family, not one per lens:

```
GET /api/spaces/[id]/history/node
      ?node=space | bucket:investments | account:{id} | holding:{acct}|{inst}
      &date=YYYY-MM-DD
      &from=YYYY-MM-DD&to=YYYY-MM-DD      ← the inherited window
```

Returns a `HistoricalNode`. The existing `/investments/point-detail` route **[EXISTS]** becomes a thin alias for `node=bucket:investments` during migration and is then retired — not left as a second door.

The route must keep V26-S3's posture: it resolves nothing, strips the diagnostic, and returns the authority verbatim.

### 6.3 UI

```
HistoricalDrawer                    ← ONE component, all lenses
  ├── Breadcrumb                    ← from node.ancestry; each crumb re-navigates
  ├── TrendChart  (existing)        ← node.series, onSelectPoint → change date
  ├── TotalBlock                    ← total + basis + denominator
  ├── RemainderBlock                ← only when PARTIALLY_ATTRIBUTED
  ├── ComponentList                 ← node.components; a row is drillable iff child.drillable
  ├── ScopeSection  (existing)      ← the collapsible category summary
  └── RefusalBlock                  ← CONTRADICTORY / UNAVAILABLE
```

Built on the existing `Panel`/`PanelStack` primitives **[EXISTS]** — `PanelStack` already handles depth and stacking, which is exactly what breadcrumb navigation needs.

**Answer to product question 5: reuse one drawer everywhere.** A lens that owns its own historical UI will re-derive meaning to fill it; that is how the "N of M" denominator drifted in the first place. Lens-specific presentation belongs in the *component row renderer*, not in a second drawer.

## 7 · Answers to the product questions

**1 · Should every chart point become inspectable?**
**Yes for stock lenses; not yet for flow lenses.** With one caveat that matters: *inspectable* must not mean *always explainable*. V26 established that a refusal is a feature. Every point should be clickable and every click should return an honest answer — sometimes "this cannot be explained, and here is why".

**2 · Should the window be inherited automatically?**
**Yes, and it should live in the URL.** It already does **[EXISTS]**. Inheriting through component state would break deep links and the back button, and the drill-down is exactly the interaction where a user wants to share "look at NVDA over this year".

One refinement: the *selected date* and the *window* are different things. Drilling into a component should preserve **both**, and changing the date inside the drawer should move the date without resetting the window.

**3 · Should every child reconcile exactly to its parent?**
**Yes, with the V26-S4 tolerance model — and this is the hardest invariant to hold.** `sum(children) + allowed remainder = parent` is achievable at Investments (366/366 EXACT). It will be *harder* at Net Worth because the buckets are resolved by different mechanisms (walked-back cash, replayed positions, recorded crypto) with different rounding. Two rules make it tractable:
- engine-vs-itself demands one cent; engine-vs-observation demands `max($1, 1bp)` **[EXISTS]**;
- **a remainder is only permitted where the parent total is an OBSERVATION.** A computed parent that does not equal its own children is stale, not partially attributed.

**4 · Should every panel expose provenance?**
**Yes, and the vocabulary already exists** — `CompletenessTier` (observed/derived/estimated/incomplete/unknown), `OwnershipConfidenceAxis`, `QuantityConfidenceAxis`, `PriceCoverageAxis` **[EXISTS]**. The risk is not absence, it is **inventing a fifth vocabulary for the drawer**. `HistoricalNode.provenance` must carry the existing tiers, not a new five-value scale.

**5 · One drawer or per-lens UI?** One. §6.3.

## 8 · Historical scope — does the photograph model generalise?

**Yes for positions, with a necessary translation for accounts.**

| Category | Positions | Accounts |
|---|---|---|
| HELD_VALUED | held + valued | account existed + balance resolvable |
| HELD_UNAVAILABLE | held, no price | existed, balance unresolvable |
| NOT_YET_OWNED | ownership opens later | **account not yet connected / not yet linked** |
| ALREADY_CLOSED | observed zero | **account closed or unlinked before the date** |
| OWNERSHIP_UNCERTAIN | no evidence reaches the date | before the account's floor |
| EXCLUDED_ARTIFACT | provider transfer records | *(none)* |

The account analogue already half-exists: `getAccountsAsOf` carries a per-account `floorISO` and refuses before it **[EXISTS]**, and `regenerate-history` has a membership-changed guard for accounts revoked after a date **[EXISTS]**. Slice B should reuse both rather than invent an account-scope model.

**A caution.** "Account not yet connected" is *not* the same as "account did not exist". Fourth Meridian learns of an account when it is linked; the account often predates that. The photograph is honest about **what we can see**, and the copy must not claim more. This is the account-level analogue of the KNOWN/POSSIBLE distinction, and it should reuse that vocabulary rather than a new one.

## 9 · Performance

| Concern | Assessment | Mitigation |
|---|---|---|
| Account series over 2 years | ~730 points × walk-back | Walk **once** over the window and sample; never per-date. `getInvestmentValueForWindow` already does this **[EXISTS]** |
| Root node fans out to N buckets × M accounts | one page-load could touch every account | Resolve **lazily per level**. The root returns bucket totals only; account components load on expand |
| `loadHoldingOwnership` per drill | 4 grouped queries per call **[EXISTS]** | Request-scoped memo; the window is identical within one drawer session |
| Probe suite over 366 dates | `getHistoricalPointDetail` per date | Already acceptable for diagnostics; **do not** put it in a request path |
| Frozen-row crypto lookup | one extra observation read per node | Fold into the existing account read |

**The real risk is not latency, it is fan-out shape.** A root node that eagerly resolves every account at every level would turn one click into hundreds of queries. Lazy-per-level is not an optimisation here; it is the architecture.

## 10 · Integrity invariants

Carry forward, extended to every level:

- **P1 · Never today's holdings.** Historical composition derives from dated evidence only. *(Distinction worth stating explicitly: an **anchored backward replay** — cash walked back from today's balance through a complete transaction ledger — is NOT a violation. It is arithmetic from an anchor, exact where the ledger is complete. The invariant forbids today's holdings deciding **ownership or composition**, not being an arithmetic anchor. Conflating these would force the removal of a correct mechanism.)*
- **P2 · Photograph.** Only what existed on the date, at every level.
- **P3 · Parent/child reconciliation.** `Σ children + permitted remainder = parent`, per level, under the two-tolerance model. **New probe required:** node-tree reconciliation, walking the tree and checking every edge.
- **P4 · Remainder only under an observation.** A computed parent that disagrees with its children is stale.
- **P5 · Contradiction is never a remainder.** Children exceeding a parent, duplicates, or currency mismatch refuse.
- **P6 · One vocabulary.** No fifth tier scale, no second ownership model, no second bucket partition.
- **P7 · No financial work in React.** Already guarded by static tests **[EXISTS]**; extend to the drawer.
- **P8 · Frozen rows are immutable and inspectable.** Both, always.
- **P9 · Every level is refusable.** A level that cannot refuse will eventually assert something false.

## 11 · Recommended order, with dependencies

```
A · Aggregate authorisation        ── no deps ── unlocks everything
        │
        ▼
B · HistoricalNode + Net Worth root ── needs A
        │
        ├──────────────┐
        ▼              ▼
C · Account series   D · Holding history + ownership episodes
    needs B              needs B
```

**A → B → (C ∥ D).** C and D are independent of each other and could run in parallel; if they must be sequenced, **C before D**, because an account chart is the more common interaction and D is the only slice that changes an ownership rule.

**Do not start with the drawer.** It is the most visible and the least load-bearing; building it first would fix the DTO around whatever the first lens happened to need.

## 12 · Definition of done

The arc is finished when all seven hold:

1. **Every stock-lens chart point is clickable and returns a `HistoricalNode`** — EXACT, PARTIALLY_ATTRIBUTED, CONTRADICTORY or UNAVAILABLE, never silence.
2. **Net Worth reconciles to its buckets, buckets to their accounts, accounts to their holdings** — every edge, under the two-tolerance model, verified by a standing tree probe.
3. **Every aggregate carries authorisation**, and no aggregate can be asserted from an unassertable component.
4. **Drilling preserves the window and the selected date**, in the URL, deep-linkable.
5. **One drawer, one DTO, one ownership engine, one valuation engine, one reconciliation vocabulary** — provable by static guard.
6. **The denominator is historical at every level**, including accounts.
7. **Multiple ownership episodes are modelled, not merely detected** — or the limitation is still detected and stated, and that is a conscious decision rather than an oversight.

**Explicitly NOT part of done:** flow-lens drill-down (§3), the nullable-component migration (§6.1), a persisted account series (§5).

## 14 · The one-paragraph recommendation

Build **aggregate authorisation first** — it is small, it needs no migration, and without it a Net Worth breakdown would reconcile to a number the engine already refuses. Then introduce **one recursive `HistoricalNode`** and compose the top two levels from authorities that already exist, delegating Investments to the engine that is already proven. Add the **account series on demand**, not persisted, and treat any persistence as a versioned cache only after measurement. Finish with **holding history**, which is mostly re-presentation, and use it as the place to promote multi-segment ownership from detector to model. Keep flow lenses out. The result is not a new engine — it is the engine we already have, asked the same question at four levels, through one drawer.
