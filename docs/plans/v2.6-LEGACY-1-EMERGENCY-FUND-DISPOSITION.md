## 3. The slice: retire, don't extract — the primitive already has a home

The question was whether these contracts are reusable goal primitives. They are
not, because **a generic goal framework already exists and is live**:

```
model SpaceGoal
  goalType     FINANCIAL | HABIT | SPENDING_LIMIT | DEBT_REDUCTION
  category     EMERGENCY_FUND | DEBT_PAYOFF | HOME_PURCHASE | … | GENERAL
  targetAmount / currentAmount / targetDate
  + GoalCheckIn, GoalContribution
```

10 goal rows exist, one of them `category = EMERGENCY_FUND`, and `AddGoalModal`
already offers it. `emergency_fund_progress` was a **weaker duplicate** of that
concept, bound to one dead category.

**So there is nothing to extract into a goal framework — the framework is
already there and already covers the concept.** What was removed here is the
duplicate, not the capability.

**What was done:** the EF hero lede is removed. v2.6-ASSESS-5 had converged it
onto the resolved expense baseline; that analysis was right about the
architecture (different question, shared unit) and wrong about whether the
surface should exist. Leaving it converged would have made a dead surface look
maintained, which is harder to retire than one that plainly is not. The hero
still renders for any legacy EF Space — the plain savings balance from
`lib/space-hero.ts` — so nothing that exists loses its headline.

**What was deliberately kept:** `resolveExpenseBaseline`, the Space-level
`/expense-baseline` route, and the Liquidity coverage line. Those have a live
consumer on a creatable Space and are unaffected by the retirement.

## 4. The one idea worth carrying forward

`SpaceGoal.targetAmount` is an absolute dollar figure. The retired widget could
express a target in **months of expenses** (`targetMonths` × `monthlyExpenses`),
which is a genuinely better way to state an emergency-fund goal and now has an
authority behind it:

```
targetAmount = targetMonths × resolveExpenseBaseline({ declared, measured }).amount
```

**Not built here**, deliberately: there is no consumer today, and shipping an
authority without one is the failure this codebase already learned (TX-3). It is
recorded so the next Goals slice does not re-derive it.

⚠️ **Retiring the section orphans the DECLARED rung.** `emergency_fund_progress`
config is the *only* producer of a user-declared monthly expense figure. Once it
goes, `resolveExpenseBaseline` is MEASURED-only in practice — the precedence
stays correct but rung 1 has no input. The widget's own config hint already names
the successor: *"Will auto-populate from the monthly_expenses widget when that
widget is built."* A live home for a declared expense baseline (Space settings or
that widget) should land **before** the section is deleted, or the product loses
the ability to state its own expense figure.

## Out of scope — recorded

1. **The full retirement is not done.** This slice removed the surface I had just
   polished. The preset, widget-registry entry, SectionRegistry renderer, hero
   definition and perspective list remain — safe (0 rows) but dead. They should
   go in one deletion slice, *after* §4's declared-baseline successor exists.
2. **The seed no longer demonstrates the product.** Zero FAMILY/CUSTOM Spaces;
   every seeded Space is a retired or coming-soon category. Any measurement over
   this corpus describes a product shape users cannot create.
3. **Other retired categories carry the same dead weight.** `debt-payoff`,
   `investment`, `equipment`, `household`, `other` are all `hidden` with their
   own presets, hero defs and perspective lists. EF is one of five; a single
   sweep would be cheaper than five slices.
4. **`GoalCategory` and `SpaceCategory` overlap by name but not by lifecycle.**
   `EMERGENCY_FUND` is retired as a Space category and live as a goal category.
   Same word, opposite dispositions — worth a naming note before someone retires
   the wrong one.
