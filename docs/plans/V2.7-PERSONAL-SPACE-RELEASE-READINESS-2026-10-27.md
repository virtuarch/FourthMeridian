## 3. What each workstream delivered

**Calendar controls (#73).**
- Row 1 (M · Q · Y + measure) never moves. Measured: identical x, y and width before and after selecting M, at every width.
- Selecting a unit adds row 2: ‹ previous, clickable label ("October 2026", "Q4 2026", "2026"), next ›, Reset.
- The label opens a picker bounded to the data range.
- Reset clears the pinned period and restores rolling 1M. It does not touch the measure or Net Worth's dates.
- Reset is URL-backed, so it survives navigation, back / forward and reload.

**Classification (#74; #71 gated).**
- *Root cause of the $2,078.50 Sandbox case.* The classifier rule that any card-account outflow is a purchase (it protects against provider mislabels of real purchases) applied to a Sandbox "payment" row that carries a charge sign.
- *Sandbox-only?* Yes, as a recurring row: real card payments arrive as balance-reducing credits.
- *Real-account risk.* The same shape occurs for **returned or reversed card payments**, which today count as purchases. This is what #71 addresses.
- *Regression matrix.* It pins the owner contract for:
  - purchases vs card payments;
  - owned transfers;
  - one-sided ACH;
  - pending / posted;
  - loan payments;
  - refunds;
  - unknown counterparties;
  - provider contradictions;
  - cross-institution transfers;
  - resync idempotence;
  - category drift;
  - user override.
- *Known gaps.* Recorded as current vs expected, not encoded as correct:
  - GAP-3: an income tag on an owned-transfer leg;
  - GAP-4: returned payments not netted from debt paid;
  - no principal / interest split in the provider feed.
- *Label fixes.* An unattested provider "debt payment" reads "Transfer in/out"; a fee or interest reversal reads "Refund".

**Mobile / desktop parity (#81).**
- **Debt All · Credit · Loans at every width.**
  - Desktop gets the class donuts (Loans "By loan type"), class totals, class account lists and the analytics note.
  - The sidebar follows the class.
- **Assets slice control** in every state, including no history and snapshot error.
- **Cash accounts:** one row model (mask, combined-accounts note, pending note and unreconciled amount on both widths).
- **Holdings:** one list plus a searchable "View all" at both widths.
- **Freshness:**
  - "Last checked" on the compact Cash Flow and Spending cards;
  - the stale-accounts warning on mobile.
- **Mobile Cash Flow / Spending:**
  - name the comparison window and carry the explanation line;
  - fixed three-line note, so pinning a period no longer shifts the page. This was a browser-found bug, fixed.
- **"Talk with Fourth Meridian about this"** on the desktop heroes. Spending has no topic at either width.
- **Smaller fixes:**
  - Debt utilization shows its level as a word;
  - Markets sub-views are hidden while Markets is "coming soon".
- **Not changed:** the Members roster on mobile for members / viewers. It is owner decision D-1, pinned by a test. Flagged in §6.

## 5. Production checklist

**Migrations.** None. `prisma/migrations` and `schema.prisma` are identical on main `43768b5` and develop. Promotion runs no migration.

**Environment (Vercel Production scope), set before the promotion build:**
- `NEXT_PUBLIC_ADJUSTED_CASH_BASIS_CUTOVER=<planned UTC date, YYYY-MM-DD>`.
  - It is inlined at build time.
  - If unset, the code default `2026-10-27` applies, which would mislabel the cutover for Production history.
  - Follow `V2.7-ADJUSTED-CASH-CUTOVER-RUNBOOK-2026-10-27.md`.
- No other new runtime variables. `FM_PRODUCTION_DB_REF` is read only by the historical-repair script (not part of the release).

**Branching.** main is an ancestor of develop (0 commits on main missing from develop), so no main→develop sync PR is needed. Promotion is one develop→main PR, prepared as a **draft** for the owner.

**Promotion sequence:**
1. Owner reviews Preview (§8) and decides on #71 (merge before promotion or ship without it).
2. Owner sets the cutover variable (Production scope).
3. Owner approves the develop→main PR. Required checks run again.
4. Merge **outside 23:30–00:30 UTC**. Vercel deploys Production.
5. Post-deploy checks:
   - `/api/health` = 200 (ok / ok);
   - the cutover-runbook read-only checks (C−1 / C+1, transaction-scoped read-only only);
   - owner smoke test (below).
6. **Separately authorized, after v2.7 is live:** the P1 historical repair per `P1-REPAIR-PRODUCTION-RUNBOOK-2026-10-27.md`.
   - Dry run first; expect 16 rows.
   - Then `--apply --env=production --i-have-owner-approval=<ticket> --expect=16`.
   - Keep the restore file.

**Rollback:**
- **Deployment:** promote the previous Production deployment `dpl_GKUMFmtb` (main `43768b5`, v2.6) in Vercel. There is no schema change to undo.
- **Cutover:** unset or change the variable and redeploy without cache (labels only; snapshots are immutable).
- **Repair** (if run): `scripts/repair-transfer-debt-payment.ts --rollback=<restore.json>`.

**Owner smoke test (Production, after deploy).** Read-only, about 10 minutes.
- **Do not** open `/dashboard/brief` unless you intend to generate today's Brief.
- Opening a Space writes that day's snapshot; this is normal.

1. Net Worth, Assets and Debt headers match the account balances. "Talk with Fourth Meridian" is present on desktop.
2. Debt → Credit / Loans:
   - the donut total equals the class total;
   - loans "By loan type" is present if you have more than one loan type.
3. Cash: Accessible cash equals the ledger total. Pending notes read sensibly.
4. Cash Flow (1M):
   - Cash in, out and net look right;
   - Transfers & movements lists unresolved transfers as "destination not confirmed";
   - click M, then a month in the picker, then Reset: the controls must not move.
5. Spending (1M): the donut centre equals Total spending, and categories sum to it.
6. Net Worth still shows its own period after you change Cash Flow's.
7. On a phone: repeat 2, 4 and 5. Check "Last checked" and any stale warning.
