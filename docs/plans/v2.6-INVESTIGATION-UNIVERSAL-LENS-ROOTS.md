# v2.6 — Universal Stock-Lens Historical Exploration Roots

**Investigation only.** No code, no schema, no data mutation, no commit.
Branch `v2.6`. Baseline commits: `be39b1d` `e947c46` `eb10b30` `5ceff2e` `af1b3bd` `86f3b74` `a9e1c7f`.

---

## 0. The three findings that decide everything

1. **Net Worth dominance is five lines in one function, not an architectural property.**
   `HistoricalNode` already carries `lens: string` — the contract is root-agnostic. The coupling is
   entirely in `resolveExplorationNode`: a guard that rejects any lens ≠ `"net-worth"`, and an
   unconditional call to `getNetWorthPointDetail`. Nothing below the root assumes Net Worth.

2. **The candidate lens list contains one duplicate and one stranger.**
   *Liabilities* is not a distinct concept — there is no `totalLiabilities` aggregate anywhere;
   `debt` is a **component**, and "Liabilities" and "Debt" resolve to the same node with the same
   children. *Liquidity* is not a snapshot aggregate at all — it is a **tiered convertibility
   ladder with no liability subtraction**, structurally unlike every other candidate.

3. **Assets and Liquid Net Worth are already authorised aggregates.** They need a root adapter,
   not a formula. Liquid NW additionally has a **duplicate formula in the UI** that should be
   retired in favour of the authorised stored column.

## 2. Repository formulas (traced, not assumed)

From `computeSnapshotFields` (`lib/snapshots/backfill-core.ts`) — the one place the arithmetic lives:

```
total       = stocks + crypto
totalAssets = total + cash + savings + realAssets
netWorth    = totalAssets − debt
netLiquid   = cash + savings − debt
cashOnHand  = max(cash, 0)              ← formula has drifted; deliberately unasserted
```

Authorised aggregates (`be39b1d`): `total`, `totalAssets`, `netWorth`, `netLiquid`, `cashOnHand`.
Components: `stocks`, `crypto`, `cash`, `savings`, `debt`, `realAssets`.

**There is no `totalLiabilities` aggregate.** The Wealth chart's `totalLiabilities` metric is
`s.totalDebt` renamed in the view layer (`lib/wealth/wealth-time-machine.ts:172`).

**Liquidity** (`lib/perspective-engine/lenses/liquidity.core.ts`) is a different model entirely:

```
cashNow    = Σ balance (checking, savings)
marketable = Σ balance (investment, crypto)      "could be raised by selling"
illiquid   = Σ balance (other / manual / real)
credit     = Σ max(creditLimit − amountOwed(balance), 0)
             — borrowing capacity, NEVER counted as liquidity, never in the headline
```

No liability subtraction. Credit is explicitly excluded from every sum. Liquidity answers *"how fast
could I raise cash?"*; Liquid NW answers *"what is my liquid position net of debt?"* They are
different questions that happen to share accounts.

## 3. Liquid Net Worth — exact status

| Question | Answer |
|---|---|
| Exact formula | `cash + savings − debt` |
| Stored field | `SpaceSnapshot.netLiquid` |
| Authorised? | **Yes** — `AGGREGATE_COMPOSITION.netLiquid = ["cash","savings","debt"]` |
| Components | checking, savings, **all** debt accounts (no short-term filter) |
| Investments/crypto included? | **No** |
| Reconciles to accounts? | Yes — cash/savings/debt buckets each reconcile EXACT to their accounts |
| Historically repaired? | Yes — `86f3b74` moved `netLiquid` on all 375 rows alongside debt |
| **Defect** | The chart **re-derives** it (`wealth-time-machine.ts:179`) instead of reading the authorised `netLiquid` column |

The same file also re-derives the real-assets residual as
`Math.max(0, totalAssets − cash − investments − crypto)`, duplicating `derivedRealAssets` in
`aggregate-authorisation.core.ts`. Both duplications agree today and both are drift risks.

A Liquid NW root must show **exactly three children** — cash, savings, debt(−) — and must not
reuse the Net Worth tree with investments and crypto hidden. Hiding children a formula excludes is
how a user learns to distrust the total.

## 4. Assets and Liabilities — recommendation

**Assets: a first-class root, no new chart.** `totalAssets` is an authorised aggregate with a known
composition. It already has a chart surface — the Wealth chart's metric switcher. What it lacks is a
*root identity* so `Assets › Investments › Schwab › TQQQ` is a legitimate path.

**Liabilities: not a lens.** It has no aggregate, no distinct composition and no distinct children.
Keep the word as the **chart metric label** (users think in those terms) but resolve it to
`lens:debt`. Minting `lens:liabilities` would create two names for one node — the duplicate-concept
failure this investigation was asked to catch.

**Liquid NW: a first-class root**, for the same reason as Assets, with the added benefit of forcing
the duplicate UI formula to be retired.

Recommended hierarchy — **metric selector for the surface, root identity for the exploration**:

```
Wealth workspace (one chart, four metrics)      Exploration roots (deep-linkable)
  ├─ Net Worth      ──────────────────────────►   lens:net-worth
  ├─ Assets         ──────────────────────────►   lens:assets
  ├─ Liabilities    ──────────────────────────►   lens:debt        (same node, honest label)
  └─ Liquid NW      ──────────────────────────►   lens:liquid-net-worth

Debt workspace        ─────────────────────────►   lens:debt
Investments workspace ─────────────────────────►   lens:investments
Liquidity workspace   ─────────────────────────►   lens:liquidity   (needs a new authority)
```

This adds **no new dashboards**. The metric the user already selected becomes the root they explore,
which is the smallest change that removes Net Worth's monopoly.

## 5. Root-node identity model

| Identity | Legitimate? | Maps to |
|---|---|---|
| `lens:net-worth` | ✅ | `getNetWorthPointDetail` (exists) |
| `lens:assets` | ✅ | `totalAssets` aggregate + the 5 asset buckets |
| `lens:liquid-net-worth` | ✅ | `netLiquid` aggregate + cash/savings/debt |
| `lens:debt` | ✅ | `debt` component → `bucket:debt` re-framed as root |
| `lens:investments` | ✅ | `bucket:investments` re-framed as root |
| `lens:crypto` / `cash` / `savings` | ✅ | corresponding bucket re-framed |
| `lens:liquidity` | ✅ **but** | needs a NEW tier-composition authority |
| `lens:liabilities` | ❌ | duplicate of `lens:debt` |

**The same account under multiple roots is correct, not duplication.** Chase checking reachable from
Assets, Liquid NW and Cash is three different *questions* about one account. The path carries the
formula context; the account node itself is identical (`account:<id>`), which is what keeps
parent/child reconciliation meaningful under each formula.

**URL:** add `hroot` (or extend `hnode` to carry the root). The root must be explicit — without it a
deep link to `account:x` cannot know whether the user was asking under Assets or under Liquid NW,
and back-navigation would land in the wrong parent. **Back follows the path that was travelled**, not
a canonical parent, which is why the resolver must return the path for the *requested* root.

## 6. Per-lens reconciliation contracts

| Lens | Parent formula | Children | Observed remainder | Notes |
|---|---|---|---|---|
| Net Worth | assets − liabilities | 6 buckets, debt subtracts | permitted (stored) | today's behaviour |
| Assets | Σ asset buckets + realAssets | 5 buckets, none subtract | permitted | realAssets terminal |
| Liquid NW | cash + savings − debt | 3 buckets, debt subtracts | permitted | must not show investments/crypto |
| Debt | Σ liability accounts | accounts | permitted | positive owed; `amountOwed` clamp |
| Investments | Σ investment accounts | accounts → holdings | permitted | present-date uses observed balance |
| Crypto | Σ wallet accounts | wallets | permitted | price-floor gaps stay gaps |
| Cash / Savings | Σ accounts of that type | accounts | permitted | — |
| Liquidity | tier sums, **no** subtraction | **tiers**, then accounts | permitted | credit excluded from every sum |

Liquidity is the only one whose children are not accounts-of-a-bucket. Its first level is
`cashNow / marketable / illiquid`, and accounts sit beneath those.

## 7. Performance

Measured on Chris' Space (745 snapshots, 11 accounts), warm:

| Resolution | Now | With direct root |
|---|---|---|
| Net Worth root | 18–41 ms | unchanged |
| Bucket (e.g. Debt) | 20–195 ms | −(20–41 ms): no NW root read |
| Account | 181–340 ms | **materially less** — see below |
| Holding | ~200 ms | same as account |

The real saving is structural. `findBucketFor` locates an account's parent by expanding **every
drillable bucket in parallel** (`Promise.all(candidates.map(expandBucketNode))` — 5 expansions). With
an explicit root, exactly **one** bucket is expanded. A deep link to a debt account currently pays to
expand Investments, Crypto, Cash and Savings as well.

**Recommendation: option B — explicit root dispatch.** A generic graph loader (option C) would
recreate the financial god-object the perspective engine already refused. Continuing to walk from Net
Worth (option A) is what encodes the dominance.

## 8. Implementation slices (recommended order differs from the brief)

Ordered by *risk*, cheapest and most certain first. The brief's sequence puts Assets/Liabilities
before Liquidity; the evidence says Liquidity is the only one needing a new authority, so it goes
last, and the re-frames go first because they add no financial logic at all.

### Slice 1 — Root dispatch + Debt root (end-to-end proof)
- **Goal:** `resolveExplorationNode` dispatches by root lens; `lens:debt` resolves directly; the Debt
  chart opens the shared sheet.
- **Files:** `lib/history/exploration.ts`, `lib/history/exploration-url.ts` (+`hroot`),
  `app/api/.../history/node/route.ts`, `components/space/widgets/debt/DebtBalanceHistory.tsx`
  + `DebtWorkspace.tsx`, `workspaceRenderers.tsx`.
- **Reuses:** `buildNetWorthNode` (bucket construction), `expandBucketNode`, `expandAccountNode`.
- **Tests:** debt root resolves without constructing Net Worth; breadcrumb starts at Debt; one
  bucket expanded not five; `lens:liabilities` rejected; existing NW paths unchanged.
- **Browser:** Debt chart point → sheet → Chase Card → account series.
- **Risk:** low. `bucket:debt` already reconciles EXACT.
- **Done when:** `Debt › Chase Card` is a valid deep link and NW behaviour is byte-identical.

### Slice 2 — Investments/Crypto/Cash/Savings roots; retire the V26 panel
- **Goal:** four more re-framed roots; Investments chart moves to the shared sheet.
- **Files:** `exploration.ts`, `InvestmentsWorkspace.tsx`, delete `HistoricalPointPanel.tsx`.
- **Risk:** medium — the old panel has V26 behaviour (scope section, excluded artifacts) the shared
  sheet does not yet render. **Do not delete until parity is confirmed**, or the slice removes
  capability. Consider folding the scope section in here rather than in Slice 4.
- **Done when:** exactly one exploration panel exists in the codebase.

### Slice 3 — Assets and Liquid NW roots
- **Goal:** `lens:assets`, `lens:liquid-net-worth`; the Wealth metric switcher selects the root.
- **Also:** retire `wealth-time-machine.ts`'s duplicate `liquidNetWorth` and `real` derivations in
  favour of the authorised `netLiquid` and `derivedRealAssets`.
- **Risk:** medium — the duplicate-formula retirement touches a shipped chart. Prove byte-identical
  values on all 1,686 rows before and after.
- **Done when:** Liquid NW shows exactly three children and its own formula sentence.

### Slice 4 — Liquidity root
- **Goal:** a tier-composition authority (`cashNow / marketable / illiquid`), then accounts.
- **Risk:** highest — the only slice inventing a new composition. Must not present `credit` as
  liquidity, and must not reconcile against Net Worth's partition.
- **Done when:** Liquidity reconciles under its own tier formula, with credit excluded and stated.

## 9. Risks

- **Retiring the V26 Investments panel loses capability** unless the scope section ships first.
- **Duplicate-formula retirement (Slice 3)** touches a shipped chart; needs a before/after proof.
- **`hroot` in the URL** is a new param; existing links without it must still resolve (default
  `net-worth`) or every shared link breaks.
- **Liquidity's tier model** could be mistakenly reconciled against snapshot buckets, producing a
  contradiction that is an artifact of the wrong formula rather than the data.
- **Same account, multiple parents:** back-navigation must follow the travelled path. Deriving a
  canonical parent would send the user somewhere they never were.

## 10. Definition of done (whole arc)

Every stock lens listed in §5 as legitimate resolves as a root; `Debt › Chase Card` and
`Assets › Investments › Schwab › TQQQ` are both valid deep links; exactly one exploration panel
exists; each lens reconciles under its own formula; no lens is reachable *only* through Net Worth;
no new financial arithmetic was introduced for any re-framed root.
