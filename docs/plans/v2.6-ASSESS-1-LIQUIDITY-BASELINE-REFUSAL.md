## Part 2 — The critical path, and why it changed

The previous roadmap implied converging more consumers onto `computeAssessment`.
Measurement says that would have propagated a falsehood, because the authority
itself was manufacturing a verdict from absent evidence.

`computeAverageMonthlySpending` returns `null` only when **no reliable month
exists**. A Space with reliable months and no spending in them returns `0` — a
true measurement — and the coverage guard tested only `=== null`, so `0` went
into the divide.

**Measured on the live corpus — 5 of 9 Spaces carry the triggering condition**
(liquid accounts present, `$0.00` measured baseline):

```
Jane's Space          liquidAccts=4   avgMonthlySpend=0.00   ⚠ fires
John's Space          liquidAccts=3   avgMonthlySpend=0.00   ⚠ fires
Smith-Doe Household   liquidAccts=2   avgMonthlySpend=0.00   ⚠ fires
Japan Trip 2027       liquidAccts=1   avgMonthlySpend=0.00   ⚠ fires
JD Freelance LLC      liquidAccts=1   avgMonthlySpend=0.00   ⚠ fires
Chris' Space          liquidAccts=4   avgMonthlySpend=5494.09
```

And this is what the model was told, rendered through the real serializer:

```
LIQUIDITY  [confidence: HIGH]
  Est. monthly expenses: $0.00/mo
  Coverage: Infinity months → EXCELLENT
  Liquid coverage: Infinity months
  1. [HIGH] READY_TO_INVEST — Liquidity is safe and debt is manageable —
     conditions support investing
```

A **HIGH-impact investment recommendation manufactured from an absence of
evidence**, leading the interpreted state.

Two aggravating details:

- **The zero-cash case is worse.** `0/0` is `NaN`; every rung of the
  classification ladder is a `<` test, and `NaN` fails all of them — so it fell
  through to `EXCELLENT`, the most favourable verdict available. No rung had to
  be wrong for the worst evidence to produce the best-sounding answer.
- **It serialized incoherently.** `JSON.stringify(Infinity)` is `null`, so a
  consumer received `{ coverageMonths: null, classification: "EXCELLENT" }` — an
  object contradicting itself, the null looking exactly like an honest refusal.

This is the arc's own doctrine inverted. v2.6-DEBT-1 refused to **admit** a debt
payment on silence; here the engine produced a **finding** on silence.

## Part 3 — The slice

`lib/ai/intelligence/annotations/engine.ts`, Step 4:

- the coverage divide now requires a baseline that is **non-null AND > 0**;
- a non-finite result is refused as a belt to that brace, because the ladder's
  `<` chain silently rewards `NaN`;
- **confidence follows the classification** — there is no such thing as a
  HIGH-confidence `UNKNOWN`. Reporting `UNKNOWN [confidence: HIGH]` would have
  fixed the grade and kept the lie.

`estimatedMonthlyExpense` is still reported as `$0.00`: that is a real
measurement, and suppressing it would replace a wrong conclusion with a missing
input.

The fabricated recommendation disappears **through the existing gates** —
`READY_TO_INVEST` already required liquidity `SAFE || EXCELLENT`. Nothing
downstream needed changing, which is the sign the fix went in the right place.

After:

```
LIQUIDITY  [confidence: LOW]
  Est. monthly expenses: $0.00/mo
  Coverage: UNKNOWN
```

# v2.6-ASSESS-2 — resolving D2, the config-vs-derived baseline

## 5.1 Measured first: the divergence was only half where the map said

D2 was recorded as a DENOMINATOR divergence. Before converging it, both halves of
the fraction were measured, because fixing one half of a division fixes nothing
if the other half also differs
(`scripts/audit-coverage-fraction-divergence.ts`, 6 Spaces with a liquid
population):

```
...where the NUMERATORS differ         : 0
...with BOTH denominators              : 0
...declared only                       : 0
...measured only                       : 6
```

**The numerators agree on every Space.** `reachableNow` (the product's reachable
cash, from `availableBalance`) and the ledger sum the engine uses are identical
across this corpus, so the numerator divergence the map flagged is *latent*, not
live — the v2.6-L3 header records a historical case where the ledger sum was
$13,674 against $5,674 reachable, but nothing in the corpus exercises it today.

That made the denominator the whole divergence, and it is a live one:

```
Chris' Space   product says: (nothing)     engine says: 1.6 months → WARNING
```

The AI was being told the user held a WARNING-grade liquidity position while the
product surface showed no verdict at all.

## 5.2 The product decision, made once

`lib/liquidity/expense-baseline.ts` — `resolveExpenseBaseline`, pure:

1. **DECLARED** — the user's own figure (`emergency_fund_progress` config)
2. **MEASURED** — the reliable-month average
3. refusal — neither, or a non-positive figure

⚠️ **A declaration outranks a measurement.** This is a product decision, not a
derivable fact. It follows the ordering `lib/accounts/display-identity.ts`
already sets — `displayName` (the user's own) outranks `officialName` — on the
reasoning that a user who has told us their expenses are $4,000 should not be
shown $5,494 because their recent quarter ran high. It has **no observable effect
on the current corpus** (nothing declares a baseline); it decides what happens the
first time somebody does. Flagged here rather than buried, because it is the one
judgment in this slice that measurement could not settle.

The result carries a `basis`, so no surface can be wrong about which figure it
divided by — the same "record which rung answered" shape as
`resolveAccountIdentity`.

`v2.6-ASSESS-1`'s rule is folded in: a non-positive figure is a refusal at every
rung, so the `Infinity`/`NaN` path cannot return through a different door.

## 5.3 What changed

| Change | File |
| --- | --- |
| The precedence authority | `lib/liquidity/expense-baseline.ts` |
| The declared figure is carried beside the measured one it competes with, so the authority can see both | `lib/ai/types.ts`, `lib/ai/assemblers/transactions.ts` |
| The engine resolves through the authority; `LiquiditySection` gains `estimatedMonthlyExpenseBasis`, and reports the figure it *actually divided by* | `lib/ai/intelligence/annotations/engine.ts`, `annotations/types.ts` |
| The prompt states which baseline was used; the partial-data caveat now applies only to a measured one | `lib/ai/prompts/assessment-serializer.ts` |
| The workspace's inline positive-or-refuse rule replaced by the authority; the hero names the baseline | `LiquidityWorkspace.tsx`, `LiquidityHero.tsx` |

## 5.4 A contradiction the fix exposed

Converging the liquidity baseline made a second one visible in the same payload:

```
Est. monthly expenses: $6,000.00/mo                          ← CASH FLOW block
Est. monthly expenses: $4,000.00/mo (the figure the user set) ← LIQUIDITY block
```

Two lines, one label, two numbers. They are genuinely *different claims* — cash
flow reports what was **spent**, liquidity reports the baseline coverage
**divides by** — so they were not merged. They were relabelled, so the model can
tell them apart:

```
Est. monthly spending: $6,000.00/mo (measured)
Est. monthly expenses: $4,000.00/mo (the figure the user set)
Coverage: 3.0 months → SAFE
```

Worth stating plainly: the measured baseline would have graded this Space
WARNING at 2.0 months. **The basis changes the verdict**, which is exactly why it
had to be stated rather than assumed.

## 5.6 What "resolved" means here, precisely

The **divergence** is resolved: one precedence rule, in one module, consumed by
both the engine and the workspace, with the chosen basis disclosed on both. When
a user declares a baseline, both surfaces now divide by the same number.

What remains is a **coverage gap, not a divergence**: with only a measured
baseline the workspace still shows nothing while the engine computes a verdict.
Closing it needs the measured figure to reach the client (the liquidity lens is
the seam) *and* a product decision — should a workspace show a coverage multiple
the user never declared? That is the next slice, not this one.

# v2.6-ASSESS-3 — closing the coverage gap

ASSESS-2 resolved the *divergence* (one precedence, one authority, basis
disclosed) and left a *coverage gap*: with only a measured baseline, the
Liquidity workspace still showed nothing while the engine graded the same
position. This closes it. Presentation only — no numerator, classification,
threshold or Assessment change, and the precedence is untouched.

## 6.1 Before / after

**Before** — the workspace could only ever see the DECLARED figure, and nothing
declared one:

```
Chris' Space   product says: (nothing)     engine says: 1.6 months → WARNING
```

**After** — the resolved baseline, per Space, through the one authority:

```
Chris' Space             → $5494.09 (MEASURED)
Jane's / John's / …      → REFUSED — workspace shows no coverage
```

The refusals are correct: those Spaces measure `$0.00`, which ASSESS-1
established is not a baseline. **8 of 9 Spaces still show nothing**, and that is
the requirement working, not the change failing to land.

## 6.2 The seam, and why not the obvious one

The two candidate figures sit on opposite sides of the client/server boundary:
the declared one arrives with the section config, the measured one needs the
transactions assembler. So the resolution has to happen on the server.

The initial mount payload was the tempting seam and is the **wrong** one:
`lib/space/mount-payload-boundary.test.ts` explicitly rejects "workspace
analytics / perspectives (computed projections)" and says they stay "a workspace
responsibility (lazy, canonical loader)". A transaction-derived average is
exactly that. So:

`GET /api/spaces/[id]/liquidity/expense-baseline` → `{ baseline: { amount, basis } | null }`

fetched **only while the Liquidity perspective is open**, never on every Space
mount. It supplies evidence and serializes a verdict; `resolveExpenseBaseline`
still decides.

## 6.3 What the workspace does now

Divides and labels. Nothing else:

```
COVERAGE  1.6 months · at $5,494/mo — your average across complete months
```

- **declared** → the figure, labelled "the figure you set"
- **measured** → the figure, labelled "your average across complete months"
- **neither** → no coverage line, exactly as before

`1.6 months` is the same number the assessment engine reports. The product and
the AI now say the same thing about the same position.

## 6.4 A latent crash the linter caught

The lazy-fetch hooks were first placed beside the value they replaced — which
sits **below** this component's `loading` early return. That would have changed
hook order between the spinner render and the loaded render. `react-hooks/
rules-of-hooks` failed the build; the hooks moved above the early return, with a
comment recording why they must stay there. Worth noting because typecheck and
the unit suite were both green at that moment: only lint caught it.

# v2.6-ASSESS-4 — the Overview EF hero: STOPPED, not converged

Measured before changing anything, and the measurement says **do not converge the
baseline here**. Reporting as instructed rather than proceeding.

```

             ↓  snapshots.filter(!fxMiss).map(heroDef.value)
```

## 7.2 The verdict: **(2) the numerator is also divergent**

Not "only the denominator". The two numerators are different quantities on two
axes:

| | Overview EF hero | Liquidity workspace |
| --- | --- | --- |
| population | **savings only** | **checking + savings** |
| basis | a **stored snapshot** component | **live reachable** balance (`availableBalance`, v2.6-L3) |
| as-of | the newest snapshot's date | today |
| ledger vs reachable | **ledger** | **reachable** |

Measured (`scripts/audit-ef-hero-coverage-divergence.ts`):

```
Chris' Space          snapshot.savings  $8,315.07   reachable  $9,024.16   Δ $709.09
John's Space          snapshot.savings  $5,528.00   reachable $16,000.00   Δ $10,472.00
Smith-Doe Household   snapshot.savings $18,030.00   reachable  $5,550.00   Δ $12,480.00
                      ...live savings   $0.00       ← the snapshot is 19 days stale
Debt Payoff Tracker   snapshot.savings  $6,466.00   reachable      $0.00   Δ $6,466.00

Spaces where the two numerators differ: 5
```

Smith-Doe is the clearest case: the hero would divide **$18,030** of snapshot
savings while the live reachable savings for that Space is **$0.00**.

**Converging only the denominator would have made this worse in a specific way**:
the two surfaces would then share a divisor and *look* coordinated, while still
producing different multiples under the same words. That is the ASSESS-2 defect
with better camouflage.

## 7.3 Why this is a conflicting authority, not merely a different question

"How long does my emergency fund last?" (savings) is a legitimately different
product question from "how long does my accessible cash last?" (reachable
checking + savings). If the divergence were only the population, this would be
two honest questions needing clearer labels.

It is not only the population. The hero also divides a **stored ledger snapshot**
where the canonical numerator is a **live reachable** figure — and v2.6-L3 exists
precisely because those differ ("the ledger sum was $13,674.16 while $8,000 of it
was not reachable at all"). The hero can therefore state a coverage multiple over
money that cannot be reached, dated to a snapshot, with no as-of qualifier on the
sentence.

Choosing between those bases is a product decision about what an emergency fund
*is*, and it must be made before either surface is wired to a shared baseline.

## 7.4 It is latent, not dead — and not urgent

```
Spaces where the EF hero renders (category EMERGENCY_FUND): 0
```

`EMERGENCY_FUND` is a real, selectable category (`lib/space-presets.ts`: "Emergency
Fund — Build and protect your emergency savings buffer", schema enum, its own
section preset). So this is reachable for any future user, and its perspective
list is `["overview", "liquidity", "wealth", "goals", "cashFlow"]` — an EF Space
shows **both** surfaces, so a user would see two different "months covered"
figures on one Space.

It also means **no browser verification of this surface is possible today** on any
Space, including Chris' (which is `PERSONAL`). Nothing was changed, so nothing
needed verifying — but a future convergence cannot be browser-proven without
first creating an EF Space.

## 7.5 What was and was not done

**Done:** the measurement, and `scripts/audit-ef-hero-coverage-divergence.ts`
(INFORMATIONAL, registered) so the decision is re-runnable rather than a
paragraph.

**Not done — deliberately:** no change to `SpaceDashboard`'s hero, no baseline
wiring, no numerator change, no label change. Per the standing instruction: if
the numerator is also a conflicting authority, stop and report.
