# v2.6 — INVESTIGATION: MULTI-NETWORK CRYPTO LEDGER ARCHITECTURE

**Status:** INVESTIGATION ONLY. No implementation, no schema, no migrations, no data writes,
no snapshot regeneration, no wallet mutation. Nothing in this document has been built.

**Date:** 2026-08-05
**Branch:** v2.6 (read-only inspection)
**Parallel session:** transfer repair · transfer-window recalibration · economic-date cutover
**Scope:** Bitcoin (existing) + Solana (proposed) + the canonical model that admits Ethereum,
XRP Ledger, Cardano and others without one engine per chain.

---

## 0 · THE HEADLINE

The current Bitcoin implementation is **not a crypto architecture**. It is a
*single-asset, single-chain balance sync* that borrowed the bank `Transaction`
table to store its movements, and it is held together by four facts that are true
only by accident:

1. Only one chain has a syncer.
2. Only one asset has a price series.
3. The live wallet has **never sent a transaction** — 28 receives, zero sends, zero fees —
   so the outbound/fee/consolidation code path has never executed against real data.
4. Crypto-denominated rows are excluded from Cash Flow totals **only because the
   `FxRate` table is empty**, not because anything declares that an on-chain movement
   is not a bank income row.

Fact 4 is the most serious. The income taxonomy's own module header records the leak
in writing (`lib/transactions/income-source.ts:24`):

```
    (no provider family)    28 rows         $0.24   ← "Bitcoin received"
```

Those 28 rows are the Bitcoin wallet's entire history. They are admitted to the
banking population, attributed `UNRESOLVED_INCOME → OTHER_INCOME`, and counted at
their **native BTC magnitude read as dollars**. The only thing standing between that
and a headline is a missing exchange rate.

So the answer to the framing question — *should Bitcoin and Solana be enriched together
through one shared crypto transaction model?* — is **yes, but not first**. The first
move is not enrichment. It is **separation**: on-chain movements must stop being bank
transactions before either chain gains detail, because every field added to a leaky
model leaks harder.

## 1.4 Where UTXO assumptions are embedded

- **`normalizeBtcAddressTxs`** (`btc-explorer.ts:329`) computes `myInputs`/`myOutputs`/`toOthers`
  from `vin.prevout` and `vout`. The whole notion of "my inputs" is UTXO-native and has no
  Solana analogue (Solana gives you `preBalances`/`postBalances` deltas instead).
- **Change nets out silently.** The comment at :339 is explicit: "change to another of the
  wallet's own addresses nets out, exactly like single-address change." That is correct
  arithmetic and **total information loss** — see §3.
- **One movement per transaction** — the model assumes a tx has one economic meaning for the
  wallet. Solana routinely has many (a swap = SOL out + token in + fee + rent, in one signature).

## 1.5 Where one-native-asset assumptions are embedded

This is the deeper problem, and it is structural, not stylistic:

| Location | Assumption |
|---|---|
| `FinancialAccount.nativeBalance Float?` (schema:1005) | **One** native quantity per account. A Solana wallet has SOL + N token balances. |
| `regenerate-history.ts:245` | `cryptoAccounts = accounts.filter(a => a.type === "crypto" && a.nativeBalance != null)` |
| `regenerate-history.ts:285`, `account-series.ts:299`, `historical-probes.ts` (`probeWalletLedgers`), `btc-sync.ts:547` | Literal predicate `currency: "BTC"` scopes the movement ledger. |
| `regenerate-history.ts:699`, `account-series.ts:320` | Literal `symbol: "BTC"` passed to `valueCryptoDay`. |
| `valueCryptoDay` (`historical-crypto-valuation.core.ts:63`) | Takes **`unitPrice: number \| null`** — ONE price for the whole account set. Multi-asset valuation is not expressible. |
| `btc-sync.ts:166` `writeBtcHolding` | Upserts on `(financialAccountId, symbol="BTC")`. |
| `LEDGER_EPSILON = 1e-8` (`ledger-completeness.core.ts:50`) | One satoshi. Wrong for SOL (1 lamport = 1e-9) and meaningless for a 0-decimal or 18-decimal SPL token. |

**Latent catastrophic bug:** because `symbol` is a literal `"BTC"` at both call sites of
`valueCryptoDay`, if any non-BTC wallet ever acquired a non-zero `nativeBalance`, it would be
valued at the **Bitcoin price**. Today this is unreachable only because no non-BTC syncer
exists. It is guarded by absence, not by design.

## 1.6 Where transaction detail is discarded

- **The raw payload is never stored.** `Transaction` has no `rawPayload`/provenance JSON column
  (verified against the full field list, schema:1963–2152). Every `RawBtcTx` is parsed, netted,
  and thrown away. Nothing can be re-derived without re-fetching.
- **Time is truncated to a day.** `Transaction.date DateTime @db.Date`. `block_time` is a
  second-precision Unix timestamp; `normalizeBtcAddressTxs:351` builds a `Date` from it and the
  column drops the time. **Intra-day transaction ordering is unrecoverable.**
- **Outputs are collapsed.** A tx paying three recipients becomes one row with `toOthers` summed.
- **Counterparty addresses are discarded.** `NormalizedBtcMovement.counterpartyAddresses` is used
  once, in-memory, to resolve owned wallets (`btc-sync.ts:289`), then dropped. Nothing persists
  who the coins came from or went to.
- **Fee↔principal linkage is a string convention.** `externalId` is `txid` or `` `${txid}:fee` ``.
  There is no foreign key, no group id, no event id.
- **Block height / confirmations are never captured.**
- **UTXO identity is never captured.**
- **Pending state is unreachable.** `fetchAddressTxsRaw` calls `/txs/chain`, which is
  **confirmed-only**. So `settlement: "PENDING"` in `normalizeBtcAddressTxs:350` is dead code
  and `Transaction.pending` is always `false` for BTC.

Everything the entire v2.6 Financial Truth arc built — the transfer authority, the income

the transaction model; it is a squatter in it.

## 1.8 Verdict on Part 1's framing question

> *Do not assume the current Bitcoin model is the correct abstraction merely because it exists.*

It is not. Specifically:

- Its **completeness authority is excellent** and should be generalised (`reconcileWalletLedger`).
- Its **carry licence is excellent** and should be generalised (`licenseConstantQuantityCarry`).
- Its **identity resolver is excellent** and is already generic (`resolveCryptoInstrumentId`).
- Its **persistence target is wrong**. `Transaction` is a bank ledger row. On-chain movements
  are not bank ledger rows, and storing them there is what produces the income leak (§2.7).
- Its **valuation core is wrong-shaped**: one price for an account set cannot survive a
  second asset.
- Its **provider layer is a leaked DTO**: `RawBtcTx` is mempool.space's response shape, and
  `btc-sync.ts` imports it directly.

## 2.2 Which Plaid-like fields can be deterministically derived on-chain?

- Event identity, amount, direction, fee, block/settlement time, per-asset balance impact,
  sender/receiver **addresses**, owned-vs-external counterparty **given the owned-address set**,
  finality depth, self-transfer detection, and (for Solana) per-mint quantity deltas.
- Reorg/RBF supersession is derivable **if and only if** first-seen state is retained.

## 2.3 Which cannot exist for decentralized transactions?

- **Authorization date.** There is no authorization step.
- **Merchant / payee identity.** An address is a bearer instrument, not a party.
- **Provider category.** There is no issuer to classify.
- **Transfer purpose / memo semantics.** `OP_RETURN` and the Solana memo program carry
  arbitrary attacker-controlled bytes; they are evidence of *a string*, not of a purpose.
- **Fiat value at event time.** Always a join, never an observation.

## 2.4 Which must remain unknown rather than fabricated?

Every one of these is currently fabricated and must stop being so:

- `merchant` — "Bitcoin received" is a sentence, not a counterparty.
- `category: Income` — a receive is not income.
- `flowType: INCOME` + `classificationReason: SIGN_DEFAULT_INFLOW` — sign is not evidence.
  This is exactly the defect v2.6-TRUTH-1 removed for banks ("positive Other = UNKNOWN not REFUND")
  and it survives, un-audited, on the crypto path.
- `flowDirection: INTERNAL` on an outbound send (`btc-explorer.ts:376`) — asserted for
  *doctrine* reasons (an outbound BTC send is an asset conversion, so it must not touch
  Cash Flow), but it says "internal" about a movement whose counterparty is provably external.
  The right answer is a crypto-native disposition, not a borrowed bank enum.

## 2.5 Which need chain-specific provenance?

UTXO inputs/outputs and change identification (BTC); instructions, inner instructions, program
ids, `loadedAddresses`, rent, ATAs (SOL); nonce/sequence and ledger index (XRPL); UTXO+metadata
and stake addresses (ADA); logs and internal traces (EVM). All of these belong in an opaque,
typed-per-network provenance envelope — never in a shared normalized column.

## 2.6 Which belong to a shared canonical crypto event model?

Network, address/account identity, asset identity, signed per-asset quantity delta, fee, event
time (with basis), finality state, direction, counterparty classification (self / owned /
external / unknown / program), reconciliation status, and provenance pointer. See Part 6.

## 2.7 The income leak — the single most important finding in this section

**Chain of evidence:**

1. `lib/data/transactions.ts:101` — `BANKING_POPULATION = { flowType: { not: FlowType.INVESTMENT } }`.
2. BTC receives are written with `flowType: INCOME` (`btc-explorer.ts:361`, `btc-sync.ts:276`).
   `INCOME ≠ INVESTMENT`, so **every BTC receive is in the banking population**.
3. `lib/transactions/serialize.ts:169` calls `attributeIncome` for every such row.
4. `attributeIncome` (`income-source.ts:134`) walks its ladder: not an owned internal transfer,
   not an issuer credit, not a REFUND, amount > 0, no `providerDetail`, no `instrumentId` →
   **rung 7 → `UNRESOLVED_INCOME` → `OTHER_INCOME`**.
5. `income-source.ts:24` records the measurement in the module header itself:
   `(no provider family)  28 rows  $0.24  ← "Bitcoin received"`.
   $0.24 **is** 0.2406 BTC read as dollars.
6. `rollupIncomeFromTransactions` (`income-rollup.ts:198`) excludes the rows **only** when a
   `ConversionContext` is supplied *and* returns `null`. `opts.ctx` is optional; with no ctx the
   native magnitude passes straight through (`income-rollup.ts:212`).
7. `convertMoney` returns `amount: null` for a known foreign currency with no rate
   (`money/convert.ts:88`). BTC has no rate — **`FxRate` has zero rows in this database** (verified).

So the exclusion is real today but rests on two removable conditions: a `ConversionContext`
being threaded, and no `BTC/USD` `FxRate` row ever existing. Adding a BTC FX rate — a
superficially reasonable thing to do — would inject the full fiat value of every crypto receive
into the Cash Flow income headline.

**No rung of `attributeIncome` asks whether the movement is on-chain.** There is no
`NOT_INCOME` subtype for it. That is the gap.

## 3.2 The seven questions, answered

**Can Fourth Meridian distinguish a payment from a wallet consolidation?**
**No.** A consolidation (all outputs back to own addresses) produces `toOthers === 0`, so no
PRINCIPAL row is emitted — only a FEE row. It is indistinguishable from "a fee happened".

**Can it identify fees separately from transfer amounts?**
**Yes**, and this is done well: a separate row with `role: FEE`, `flowType: FEE`,
`category: Fee`. The weakness is linkage — the association is the string suffix `:fee`, not a
relation, so nothing can query "the fee of this transaction" without string surgery.

**Can it represent one transaction with multiple outputs?**
**No.** All external outputs are summed into `toOthers` and all recipients into one
`counterpartyAddresses` array that is then discarded.

**Can it identify self-transfer without inventing a counterparty?**
**Partially, and it invents anyway.** When every counterparty is an owned wallet it writes
`merchant: "Wallet transfer"` and `counterpartyAccountId` = the *first* owned account
(`btc-sync.ts:296`) — arbitrary when several are owned. Same-wallet consolidation is not
detected at all. And the non-self path invents `merchant: "Bitcoin sent"/"Bitcoin received"`
for every row.

**Can it preserve first-seen pending time separately from block confirmation time?**
**No.** There is one date column, day-truncated, and mempool is never fetched.

**Can it survive reorgs and RBF honestly?**
**No.** With confirmed-only fetching, an RBF-replaced transaction is never imported (benign).
But a **reorg that unconfirms an already-imported tx leaves an orphaned active row forever** —
the import is insert-only with `skipDuplicates`, nothing ever deletes or supersedes. The ledger
reconciliation *would* catch the resulting residual and refuse history, which is the honest
failure mode, but the wrong row stays and no operator signal names the cause.

**Can it reconcile wallet balance exactly from persisted movements?**
**Yes — verified live.** The real wallet: 28 movements summing to exactly `0.24060252`, equal to
`nativeBalance`. This is the strongest thing in the crypto stack and the model for every other
network.

## 3.3 Two provider hazards worth naming

- **Basis mismatch between the two Bitcoin providers.** Single-address balances come from
  mempool.space `chain_stats` (`funded − spent`, **confirmed only**, `btc-explorer.ts:71`).
  xpub balances come from blockchain.info `/multiaddr` `final_balance`
  (`btc-explorer.ts:235`), whose confirmed/unconfirmed basis is **not documented**. If
  `final_balance` includes mempool, an xpub wallet's observed balance and its confirmed-only
  movement ledger will disagree by any in-flight amount, and `reconcileWalletLedger` will refuse
  history for a reason no one can diagnose. **This needs a probe, not an assumption.**
- **Page budget vs. reconciliation.** `BTC_TX_PAGE_BUDGET` caps history at 1000 confirmed txs.
  The design deliberately relies on `reconcileWalletLedger` to catch exhaustion rather than
  detecting it directly — correct, but it converts a large wallet into a permanently
  history-refused wallet with no operator-facing "budget exhausted" signal.

## 3.4 Minimum canonical Bitcoin event shape

Per confirmed transaction touching the wallet, retain:

- `networkId`, `walletId`
- `txid`, `blockHash`, `blockHeight`, `blockTimeUtc` (**full timestamp**), `firstSeenUtc` (nullable)
- `feeSats` (integer), `virtualSize`, `isCoinbase`, `isRbfReplacement`, `replacesTxid` (nullable)
- **Per-owned-input**: `{outpoint (txid:vout), address, valueSats}`
- **Per-output**: `{vout, address|scriptType, valueSats, isOwned, isChangeCandidate}`
- Derived, stored, and independently checkable: `ownedInputSats`, `ownedOutputSats`,
  `externalOutputSats`, `netDeltaSats = ownedOutputSats − ownedInputSats − (isMine ? fee : 0)`
- `finality: {confirmations, state}` recomputed at read time from `blockHeight` + tip
- `provenance: {provider, endpoint, fetchedAt, rawHash}` and the raw payload retained until
  a reconciliation is proven

Quantities **must be integers** (satoshis / lamports / base units). `Float` for an 8-decimal
asset is already marginal; for an 18-decimal token it is disqualifying. The existing
`DEC-0 numeric precision audit` roadmap already flags crypto-wei as urgent.

# PART 4 — SOLANA DEEP AUDIT

## 4.1 What Solana actually gives you

From primary documentation (`solana.com/docs/rpc/http/*`):

**`getSignaturesForAddress`** — `limit` 1–1000 (default 1000), `before`/`until` cursors,
commitment `confirmed`|`finalized` (**not** `processed`). Returns `signature`, `slot`, `err`,
`memo`, `blockTime`, `confirmationStatus`. Indexes transactions "that reference the supplied
address in `accountKeys`".

**`getTransaction`** — `meta` carries `fee`, `preBalances`/`postBalances` (lamports, indexed to
`accountKeys`), `preTokenBalances`/`postTokenBalances` (each with `accountIndex`, `mint`,
`owner`, `programId`, `uiTokenAmount{amount, decimals, uiAmount, uiAmountString}`),
`innerInstructions`, `logMessages`, `loadedAddresses{writable, readonly}`, `rewards`,
`computeUnitsConsumed`, `err`, `blockTime`. `maxSupportedTransactionVersion: 0` is **required**
to see v0 transactions — omitting it returns only legacy transactions and errors on v0.

This is *richer* than Bitcoin: `pre/postBalances` and `pre/postTokenBalances` give a
**complete, program-agnostic, per-asset balance delta for every account in the transaction**,
with the token-account `owner` attached. You do not need to decode a single program to compute
what changed. That is the single most important architectural fact about Solana ingestion.

## 4.2 The three hard problems

**(1) Address indexing misses ALT-loaded accounts.**
`getSignaturesForAddress` indexes only accounts present in the transaction's *static*
`accountKeys`. Accounts loaded via an **Address Lookup Table** appear in `meta.loadedAddresses`,
not `accountKeys`, and such transactions are **not returned** for that address
(solana-labs/solana#35484). Since ALTs are ubiquitous in DeFi/aggregator routing, a
signature-scan of a wallet's addresses is **not provably complete**. This is not a provider
choice; it is a protocol-level indexing property.

**(2) Wallet address ≠ token activity address.**
An SPL transfer references the **associated token account (ATA)**, not the owner wallet. Scanning
only the owner address misses SPL history. You must enumerate token accounts
(`getTokenAccountsByOwner`) and scan each — and **closed token accounts no longer exist to be
enumerated**, so historical scope requires discovering ATAs from history, which requires the
history you are trying to discover. This is circular and must be broken by an indexer.

**(3) A validator retains ~2 epochs (~4 days).**
Anything older requires archival access. Long-tail history is a *vendor* dependency, not an RPC
one.

## 4.3 Full capability inventory (design intent, not built)

| Concern | Reading | Phase |
|---|---|---|

| SPL tokens | `pre/postTokenBalances` filtered by `owner` | **A** |

## 4.4 Recommended Phase A scope (and its hard exclusions)

**Phase A — "the wallet's own money, provably".**

- Native SOL balance + movements from `pre/postBalances`.
- SPL token balances + movements from `pre/postTokenBalances`, aggregated per `(owner, mint)`.
- Fees as their own movement, including on failed transactions.
- Failed transactions ingested as **fee-only events** (they are real cost).
- Rent deposits/refunds and account open/close recognised and **named**, never counted as
  income or spending.
- Wrapped SOL wrap/unwrap recognised as a **denomination change**, not a trade.
- Per-asset historical balances via the same event ledger.
- Pricing for an **explicit allowlist** of mints only (SOL + majors). Everything else is
  **held, counted, and unvalued** — never zero.
- Per-asset completeness/reconciliation (Part 9).

**Phase A explicitly EXCLUDES** — and these must not creep in:
swaps as classified trades, staking rewards, delegated stake balances, NFTs, cNFTs, DeFi/LP
positions, priority-fee decomposition, program-level semantics of any kind, cost basis.

A multi-asset event in Phase A is stored faithfully as *N movements under one event* with
`classification: UNCLASSIFIED_PROGRAM_INTERACTION`. It is not a swap. It is not income. It is
not spending. It changes composition and nothing else. That is honest and it is enough.

**Finality:** `confirmed` ≈ 500–600 ms optimistic; `finalized` ≈ 31 subsequent blocks ≈ 12.8–13 s.

contract; archival is a URL. Enhanced/parsed endpoints may be added later as an optional
*acceleration* provider behind the same port — **and their output must be re-derived against
`pre/postBalances` before it is trusted**, never accepted as the canonical shape.

> *"Do not pick a provider solely because it makes parsing easier."* — Helius's parsed
> transaction API is exactly that temptation. Accepting its DTO would put a vendor's
> interpretation of "what a swap is" inside Fourth Meridian's truth layer. The correct use is
> as a *hint* that must reconcile against balance deltas we computed ourselves.

## 5.3 The provider abstraction that prevents lock-in

Three rules, and the current Bitcoin code violates all three:

1. **A provider's DTO never crosses the adapter boundary.** `btc-sync.ts` imports `RawBtcTx` —
   mempool.space's response shape — directly. That is the lock-in already present.
2. **The adapter emits observations, not conclusions.** A provider says "I saw this"; only the
   engine says "this means that." Today `normalizeBtcAddressTxs` emits `flowType: "INCOME"` —
   the *provider layer* is making a financial classification.
3. **Every adapter must answer "did I see everything?"** as a first-class return value, with a
   coded reason when it cannot. Today completeness is inferred downstream by arithmetic alone.

Sketch of the port (conceptual — not a proposal to build now):

```
ChainAdapter<Network>
  identity()            → { networkId, assetIdSchema, quantityBasis, finalityModel }
  discoverAddresses(descriptor, cursor)  → { addresses[], cursor', complete, reason? }
  observeBalances(addresses, asOf)       → { balances: [{assetRef, baseUnits}], observedAt, complete, reason? }
  observeEvents(addresses, cursor)       → { observations: ChainObservation[], cursor', complete, reason? }
  finality(observation)                  → { state, depth }
```

`ChainObservation` carries: network, event id, event time + basis, per-account per-asset signed
**integer** base-unit deltas, fee, failure flag, finality, and an opaque `providerRaw` +
provenance stamp. It carries **no** `flowType`, **no** `category`, **no** `merchant`.

# PART 6 — CANONICAL MULTI-NETWORK MODEL

## 6.1 The thirteen concepts, classified

| # | Concept | Universal? | Persist? | Immutable? | Notes |
|---|---|---|---|---|---|
| 1 | **Network** | Universal | Reference data | Yes | `bitcoin-mainnet`, `solana-mainnet`. Carries finality model, base-unit basis, calendar. |
| 2 | **Wallet / custody account** | Universal | Yes | No | This is `FinancialAccount` today and should stay so — custody is custody. |
| 3 | **Address / on-chain account** | Universal | Yes | Yes | `ProviderAccountIdentity` already models this. Solana needs a **role** (owner wallet / token account / stake account) and a `derivedFrom` link. |
| 4 | **Asset / instrument** | Universal | Yes | Yes | `Instrument` + `InstrumentAlias(provider="crypto")` already generic. Needs `(networkId, contractOrMint)` as the alias externalId, and **`decimals`**. |
| 5 | **Chain transaction** | Universal | Yes | **Yes** (until reorg) | txid / signature. Immutable content-addressed fact. |
| 6 | **Provider observation** | Universal | Yes (bounded) | Yes | "Provider P, at time T, from endpoint E, reported X." Append-only. |
| 7 | **Economic event** | Universal | **Derived, persisted** | No | What the wallet experienced. One chain tx → 1..N events. Recomputable from observations. |
| 8 | **Asset movement** | Universal | Yes | No | Signed integer base-unit delta for one (account, asset, event). The atom. |
| 9 | **Fee movement** | Universal | Yes | No | A movement with `role = FEE`, **linked to its event by relation, not by string suffix**. |
| 10 | **Balance observation** | Universal | Yes | Yes | Per (account, asset, asOf). The independent authority reconciliation checks against. |
| 11 | **Ownership** | Universal | Derived | No | Address-set membership at a point in time. |
| 12 | **Finality / lifecycle** | **Chain-specific model, universal interface** | Store depth inputs, derive state | — | BTC: confirmations. SOL: `confirmationStatus`. XRPL: validated ledger. Store `blockHeight`/`slot`; derive state at read time against the tip. |
| 13 | **Reconciliation status** | Universal | **Derived, never stored** | — | The existing doctrine (`ledger-completeness.core.ts:33`) is right: "a stored flag would bless staleness." Extend it per-asset. |

## 6.2 What stays chain-specific

Only the **provenance envelope** and the **adapter**. Everything else normalizes. Concretely:
UTXO outpoints and script types (BTC); instructions, inner instructions, `loadedAddresses`,
rent, ATA lineage (SOL); ledger index and sequence (XRPL); traces and logs (EVM); stake
addresses and metadata (ADA). These are typed *inside* the envelope, never as shared columns.

## 6.3 What must NOT be normalized

- **Program/contract semantics.** "This was a Jupiter swap" is a decoded interpretation with a
  version, an author, and a failure mode. It is an *annotation on* an event, never the event.
- **Token metadata** (name, symbol, logo). Attacker-controlled. Reference data with a trust
  level, never identity. Identity is the mint/contract address.
- **Fiat value.** Always a read-time join against `PriceObservation`.

## 6.4 Should crypto share L8's `ProviderObservation` / `EconomicEvent` with Plaid?

**Share the abstraction. Do not share the table.**

The argument *for* sharing tables: one truth engine, one reconciliation vocabulary, no
divergence. The argument *against*: the two domains disagree on nearly every column.

| Property | Bank (Plaid) | Chain |
|---|---|---|
| Identity | Provider-assigned, **can change** (pending→posted) | Content-addressed, **cannot change** |
| Amount | Decimal fiat | **Integer base units**, 0–18 decimals |
| Denomination | ISO-4217 | Mint / contract address |
| Counterparty | Named legal entity | Bearer address |
| Lifecycle | pending → posted → (removed) | mempool → confirmed → finalized → (reorged) |
| Multi-asset events | Never | Routine |
| Completeness | Provider assertion (trust) | **Arithmetic proof** |
| Correction model | Provider restates | Chain supersedes (reorg/RBF) |

A single physical table would carry a nullable column for every one of these differences, and
every consumer would need a discriminator. That is not one engine; it is two engines wearing
one hat — the exact `FinancialState` anti-pattern this codebase already ratified against.

**Recommendation.** One **conceptual** spine — Observation → Event → Movement → Reconciliation —
expressed as a shared *interface* and shared *vocabulary* (completeness tiers, refusal reasons,
the "unknown beats a confident wrong number" doctrine), with **two domain implementations** and
**one higher-level read boundary** that both satisfy. Crypto movements must never enter
`BANKING_POPULATION`; a Space's totals compose from both domains at the aggregate layer, where
they already do (`SpaceSnapshot.crypto` is already a separate component from `cash`/`stocks`).

**This means Bitcoin's movements should migrate OUT of `Transaction`.** That is the largest
single recommendation in this document, and §12 sequences it.

# PART 7 — EVENT AND MOVEMENT TAXONOMY

## 7.1 The three-layer separation

The current model collapses all three into one `flowType`. They must be separate fields:

**Layer 1 — what happened on-chain (mechanical, always assertable).**
`RECEIVE` · `SEND` · `SELF_MOVE` (both sides owned) · `FEE_ONLY` · `FAILED` ·
`ACCOUNT_OPEN` / `ACCOUNT_CLOSE` (rent) · `MULTI_ASSET_CHANGE` · `NO_ECONOMIC_CHANGE`

**Layer 2 — what it means financially (a judgment, with evidence and confidence).**
`EXTERNAL_INFLOW` · `EXTERNAL_OUTFLOW` · `INTERNAL_TRANSFER` (own↔own) · `NETWORK_COST` ·
`DENOMINATION_CHANGE` (wrap/unwrap) · `COMPOSITION_CHANGE` (swap-shaped) · `SUPPLY_EVENT`
(mint/burn) · `PROTOCOL_YIELD` (staking/mining reward) · `UNSOLICITED_RECEIPT` (airdrop) ·
`CUSTODY_OVERHEAD` (rent deposit/refund) · `UNDETERMINED`

**Layer 3 — decoded protocol semantics (optional, versioned, never load-bearing).**
`swap:jupiter@v6` · `stake:native` · `bridge:wormhole` · `lp:deposit`. Every such annotation
carries a decoder id and version and can be discarded without changing any total.

## 7.2 The mapping, and what is deterministic

| Requested category | Layer 1 | Layer 2 | Deterministic? |
|---|---|---|---|
| Incoming transfer | RECEIVE | EXTERNAL_INFLOW | **Yes** (given the owned-address set) |
| Outgoing transfer | SEND | EXTERNAL_OUTFLOW | **Yes** |
| Internal/self transfer | SELF_MOVE | INTERNAL_TRANSFER | **Yes** |
| External transfer | RECEIVE/SEND | EXTERNAL_* | **Yes** |
| Fee | any | NETWORK_COST | **Yes** |
| Staking reward | — | PROTOCOL_YIELD | **SOL: yes** via `getInflationReward` (epoch-scoped, *not* in tx history). Not derivable from tx scan. |
| Mining reward | RECEIVE (coinbase) | PROTOCOL_YIELD | **Yes** — coinbase txs are structurally identifiable (`vin` has no `prevout`). **Currently misclassified as a plain receive.** |
| Airdrop | RECEIVE | UNSOLICITED_RECEIPT | **Heuristic.** "I did not sign it and did not expect it." Must be a distinct, un-valued class. |
| Token mint | MULTI_ASSET_CHANGE | SUPPLY_EVENT | Needs decoding |
| Token burn | MULTI_ASSET_CHANGE | SUPPLY_EVENT | Needs decoding |
| Swap | MULTI_ASSET_CHANGE | COMPOSITION_CHANGE | **Shape yes, protocol no.** "N assets out, M in, one signature" is arithmetic. |
| Trade | MULTI_ASSET_CHANGE | COMPOSITION_CHANGE | Same |
| Liquidity deposit/withdrawal | MULTI_ASSET_CHANGE | UNDETERMINED | **Protocol-specific** |
| Bridge | SEND / RECEIVE | UNDETERMINED | **Cross-chain correlation — not derivable from one chain** |
| Wrap/unwrap | MULTI_ASSET_CHANGE | DENOMINATION_CHANGE | **Yes for wSOL** (known mint pair) |
| NFT acquisition/disposal | MULTI_ASSET_CHANGE | COMPOSITION_CHANGE | Needs metadata + decoding |
| Unknown program interaction | MULTI_ASSET_CHANGE | UNDETERMINED | **Yes — this is the honest default** |

## 7.3 The four prohibitions, as invariants

These must be enforced by tests, not comments — the codebase already has the pattern
(`flow-classifier-authority.test.ts` makes the BTC exception executable policy):

1. **An incoming crypto movement is never income by default.** Income requires positive
   evidence (a coinbase/staking attestation), never a sign. The current
   `SIGN_DEFAULT_INFLOW` on all 28 live rows is precisely the defect v2.6-TRUTH-1 removed for
   banks and never removed here.
2. **An outgoing crypto movement is never spending by default.** Sending BTC to an exchange
   is a disposal, not a purchase.
3. **A swap is one event with N movements** and contributes to neither income nor spending.
   Its net fiat effect is a *valuation* change, computed by the historical engine, not two
   opposing cash-flow entries.
4. **A self-transfer changes no quantity and no value.** It must produce zero net movement
   across the wallet aggregate and must never appear in gains/losses. The wallet aggregate is
   the ledger identity that proves it.

# PART 8 — HISTORICAL ENGINE COMPATIBILITY

## 8.1 What the engine does today

`regenerate-history.ts` per day: load crypto accounts (`nativeBalance != null`), load their
`currency="BTC"` POSTED movements, reconcile the ledger, license the constant-quantity carry,
resolve one BTC/USD price for the window, call `valueCryptoDay` with **one price and the literal
symbol `"BTC"`**, and stamp `cryptoValuationStatus`.

`account-series.ts:288–320` reproduces the identical logic for drill-down, from the same four
authorities — good, and it means **both consumers break identically** when a second asset arrives.

## 8.2 Where it breaks on a multi-asset wallet — proven by reading

| Break | Location | Consequence |
|---|---|---|
| One price for all accounts | `valueCryptoDay` `unitPrice: number\|null` | A SOL wallet would be valued at the BTC price. Unreachable today only because no SOL syncer exists. |
| One native quantity per account | `FinancialAccount.nativeBalance` | SOL + 12 SPL mints cannot be expressed. |
| Ledger scoped to `currency = "BTC"` | 4 call sites | A SOL wallet reconciles against zero movements → `NO_MOVEMENTS` → refuse. |
| **All-or-nothing carry licence** | `regenerate-history.ts:338–345` `cryptoAccounts.every(...)` | **One unreconciled wallet refuses the entire Space's crypto history**, including a perfectly reconciled Bitcoin wallet. |
| Epsilon fixed at 1e-8 | `ledger-completeness.core.ts:50` | Wrong unit for lamports; meaningless across token decimals. |
| `probeWalletLedgers` selects `walletChain != null` but reconciles `currency = "BTC"` | `historical-probes.ts:71` | Any future non-BTC wallet reports a permanent false failure. |

**The all-or-nothing licence is live today and already firing.** Verified in this database:

- `Cold Wallet BTC` — 28 movements, Σ = `0.24060252` = `nativeBalance`. **Reconciles exactly.**
- `Jane BTC Wallet` — `nativeBalance` 0.02, **zero** `currency="BTC"` rows → `NO_MOVEMENTS`.
- `John BTC Wallet` — `nativeBalance` 0.038, **zero** `currency="BTC"` rows → `NO_MOVEMENTS`.

Snapshot status distribution across the database: **358 `supported`, 378 `unavailable`,
950 `null` (`legacy-unrecorded`)**. The refusals are the mechanism working as designed — but
the *granularity* is wrong, and Solana will make that acute.

## 8.3 Price floor reality

`Instrument(BTC, CRYPTO)` holds **366 `PriceObservation` rows, 2025-08-03 → 2026-08-03**.
The wallet's history begins **2023-03-18**. So **~2.4 years of licensed quantity has no price**
and is correctly refused. Solana would start from zero price coverage, and every SPL token
outside a small allowlist will *never* have coverage.

This makes the per-asset valuation licence (Part 9) not a nicety but a requirement: a wallet
holding SOL + eleven unpriceable memecoins must still produce a SOL history.

## 8.4 The eight representability proofs

Against the engine **as it stands**:

| Must represent | Today | Why |
|---|---|---|
| Wallet with zero assets before creation | **Yes** | Per-account floor is the earliest real Transaction (`regenerate-history.ts:401`); `holdConstantBeforeEarliest` + ownership licensing keep pre-existence out. (⚠️ memory: `holdConstantBeforeEarliest` back-projects unowned positions — needs re-verification for crypto.) |
| Tokens appearing and disappearing | **No** | One `nativeBalance` scalar. No per-asset dimension. |
| Token accounts closing | **No** | No account-lifecycle concept. |
| Swaps changing composition | **No** | No multi-asset event. |
| SOL fees reducing balance | **Partially** | Fee rows exist for BTC and would work per-asset — but only within the single-asset model. |
| Staking rewards increasing balance | **No** | Rewards are epoch-scoped, outside tx history; nothing models them. |
| Unsupported tokens unvalued not zero | **Conceptually yes, structurally no** | `valueCryptoDay` refuses the whole day (`NO_PRICE`) rather than the asset. The *doctrine* is right; the *granularity* is per-day-per-Space. |
| Historical asset counts changing naturally | **No** | `positionCount` counts *accounts with a material balance*, not assets. |

**Conclusion: the historical engine cannot represent a Solana wallet today.** Not because its
doctrine is wrong — the doctrine (licensed quantity × dated price, refuse otherwise) is exactly
right and should be preserved verbatim — but because its **dimensionality is wrong**. Every
authority is `(account, day)`. It must become `(account, asset, day)`.

That is a mechanical widening of four pure modules and their two bindings, not a redesign.

## 8.5 Solana wallet stress test — NOT PERFORMED, and why

**No Solana wallet address was supplied, and none exists in configuration.** I checked
`.env` / `.env.local`: no `SOL_*`, no wallet address, no RPC endpoint. The database contains
three wallets, all `walletChain = "BTC"`.

I did **not** connect a wallet, invent an address, or mutate anything. The requested estimates
(earliest transaction date, signature count, SOL/SPL movement counts, token count over time,
staking activity, history depth, price coverage, unsupported assets, expected gaps) are
**measurements**, and reporting modelled numbers as findings would be exactly the fabrication
this arc exists to remove.

**To run it, supply a public Solana address.** The read-only protocol — no writes, no
persistence, one throwaway script against a public archival RPC — would be:

1. `getSignaturesForAddress(owner)` paginated by `before` to exhaustion → count, earliest
   `blockTime`, failed-tx ratio.
2. `getTokenAccountsByOwner(owner, {programId: TOKEN_PROGRAM_ID})` and Token-2022 → **current**
   ATAs; scan each the same way.
3. Union the signature sets; count duplicates (multi-account txs) → true distinct event count.
4. `getTransaction(sig, {maxSupportedTransactionVersion: 0})` on a sample → count transactions
   with non-empty `meta.loadedAddresses` → **the ALT exposure estimate**, i.e. how much history
   a signature-scan may be missing.
5. Per-mint first/last `blockTime`, distinct mint count, and mint count over time.
6. `getInflationReward` across the epoch range → staking presence.
7. Cross-check each mint against CoinGecko coverage → the unpriceable set.
8. Compare Σ movements against `getBalance` / current token balances → **whether the wallet
   would reconcile at all**.

Step 8 is the one that matters: if a real wallet cannot reconcile from a signature scan, the
whole Phase A completeness model needs an indexer, not an RPC.

# PART 9 — COMPLETENESS AND RECONCILIATION

## 9.1 The principle, restated for many assets

Bitcoin's identity is `Σ(signed native movements) == observed balance`. It generalises
**per (account, asset)**:

```
for each (custodyAccount, asset):
    Σ movements(account, asset, POSTED, not deleted)  ==  observedBalance(account, asset)
    within epsilon(asset)                              ← from the asset's own decimals
```

Epsilon must be **derived from the asset**, not a constant: 1 satoshi, 1 lamport, or 1 base
unit of a token's `decimals`. Ideally the comparison is exact integer arithmetic and epsilon
disappears — which is another argument for integer base units.

## 9.2 Solana-specific reconciliation questions

- **Does Σ movements reproduce the native balance?** Yes if every signature is seen. Fees,
  rent, and failed-transaction fees must all be movements or the sum will be short. **A failed
  transaction still charges a fee** — omit it and every wallet with failures under-reconciles.
- **Does each mint reconcile independently?** Yes — `pre/postTokenBalances` give exact per-mint
  deltas. This is cleaner than Bitcoin.
- **Fees:** always native SOL, always charged to the fee payer, always a movement.
- **Staking balances:** stake accounts are *separate accounts*. They must be their own custody
  addresses with their own reconciliation, not folded into the wallet's SOL balance. Rewards
  arrive via epoch inflation, not transactions — so a staked wallet **cannot** reconcile from
  transaction history alone. **Phase A must therefore refuse, or exclude, wallets with active
  stake** rather than silently under-reconcile.
- **Rent:** deposits and refunds are real lamport movements and must be captured, or every
  ATA open/close leaves a residual.
- **Failed transactions:** ingest as fee-only.
- **Missing historical signatures:** detected by residual — but the residual cannot say *why*.
- **RPC truncation / retention:** detectable structurally — if the oldest returned signature's
  slot is above the archival floor, or a page returns fewer than `limit` without a terminal
  marker, the scan is bounded, not exhausted. This must be an explicit adapter return value,
  not an inference.
- **ALT gap:** **not detectable by arithmetic alone in general.** A missed ALT transaction shows
  up as a residual only if it changed a balance we observe. This is the strongest argument for
  a per-asset `PARTIAL` state and for eventually depending on an indexer rather than a
  signature scan.

## 9.3 Recommended reconciliation states

Per `(custodyAccount, asset)`, **derived at read time, never stored** (preserving the existing
doctrine at `ledger-completeness.core.ts:33`):

| State | Meaning | History licensed? |
|---|---|---|
| `RECONCILED` | Σ movements == observed balance | **Yes** |
| `TRIVIAL` | No balance, no movements (0 == 0) | Yes (vacuously) |
| `SHORT` | Movements exist, sum ≠ balance | No |
| `NO_MOVEMENTS` | Balance held, no movements recorded | No |
| `NO_OBSERVATION` | No observed balance to check against | No |
| `BOUNDED_SCAN` | The adapter declared its scan incomplete | No |
| `UNRECONCILABLE_BY_DESIGN` | Off-ledger accrual (staking rewards) | No — **and say why** |

Refusal reasons must be stable machine-readable codes, matching the existing style
(`HISTORICAL_CRYPTO_VALUATION_UNAVAILABLE`): `LEDGER_SHORTFALL` · `NO_MOVEMENTS` ·
`NO_OBSERVED_BALANCE` · `SCAN_BOUNDED_BY_RETENTION` · `SCAN_BOUNDED_BY_BUDGET` ·
`ADDRESS_SET_INCOMPLETE` · `OFF_LEDGER_ACCRUAL` · `NO_PRICE_COVERAGE` · `ASSET_NOT_PRICEABLE`.

## 9.4 Can a wallet be COMPLETE for SOL but PARTIAL for one SPL token?

**Yes, and it must be.** Per-mint deltas are independent; a mint whose ATA was closed and whose
history is unreachable does not impugn the SOL ledger.

## 9.5 Can valuation be licensed per asset rather than refusing the whole wallet?

**Yes — and this is the single most important change to the historical engine.**

Two orthogonal licences, per `(account, asset, day)`:

- **Quantity licence** — is the reconstructed/carried quantity trustworthy?
  (`RECONCILED` + no blocking event in the interval)
- **Valuation licence** — did a price reach the day for this asset?

Aggregation rule, which preserves the existing honesty doctrine while fixing granularity:

- Value every asset that holds **both** licences.
- Any held asset missing **either** makes the day's crypto component **`unavailable`** for the
  aggregate — because a partial sum presented as a total is the dishonesty the current
  all-or-nothing rule exists to prevent.
- **But** report the licensed assets' values and the unlicensed assets' *quantities* in the
  drill-down, so the user sees "we hold 1,200 BONK; we cannot value it" rather than nothing.
- Asset counts (`positionCount`) count **held** assets, licensed or not. Holding is observed;
  valuing is licensed. They are different questions.

> *"Do not let one unsupported spam token unnecessarily invalidate a fully reconciled SOL
> history unless the parent aggregate genuinely depends on it."*

The parent aggregate (`SpaceSnapshot.crypto`, and therefore `totalAssets` and `netWorth`)
**does** genuinely depend on it — an unvalued holding makes the total incomplete by definition.
So the aggregate must refuse. But **the SOL asset series, the SOL quantity history, and the
composition view do not depend on it**, and they must not refuse. That distinction is currently
inexpressible because there is only one crypto number.

# PART 10 — SECURITY, PRIVACY, AND ABUSE

## 10.1 Key boundary (currently correct — keep it)

`app/api/accounts/wallet/route.ts` accepts only a public address or an xpub/ypub/zpub
watch-only descriptor. `normalizeExtendedKeyInput` accepts a bare extended key or a Ledger-style
JSON export. `getWalletAddresses` defensively filters extended keys out of the address set
(`btc-sync.ts:430`). **No seed phrase or private key is ever requested or stored, and none
should ever be.** This must become an executable invariant, not a convention.

## 10.2 Findings and required policies

| Risk | Assessment | Policy |
|---|---|---|
| **xpub is a privacy bomb** | An xpub reveals **all past and future addresses** and thus the whole wallet's history. Stored in `Connection.credential`. | Verify it is encrypted at rest with the same guarantee as Plaid access tokens. Never log it; never return it to the client; never include it in exports or AI payloads. |
| Public-address privacy | Addresses are public but **linkage is not**. Storing an address links a real identity to a chain history. | Never expose another user's wallet address across a Space boundary. Redact in AI payloads. |
| RPC provider tracking | Every balance/tx query tells the provider which addresses one party cares about. An xpub scan is especially revealing. | Prefer batched/aggregated queries; document the exposure; make self-hosting a supported deployment. |
| **Token spam** | Solana airdrops arbitrary tokens into any wallet, unsolicited. | Ingest **quantity** faithfully; **never** value or income-classify a non-allowlisted mint. `UNSOLICITED_RECEIPT`. |
| **Fake token symbols** | Anyone can mint `USDC`. | **Identity is the mint address, never the symbol.** `resolveCryptoInstrumentId` currently keys `InstrumentAlias` on **symbol alone** (`crypto-instrument.ts` `externalId: asset.symbol`) — for multi-network this **must** become `(networkId, mintOrContract)`, or a fake mint will collide with the real asset's price series. |
| **Unicode confusables** | `USDС` (Cyrillic С) renders as `USDC`. | Normalize + detect confusables; display a verification badge; never let a symbol drive identity or valuation. |
| **Address poisoning / dust attacks** | Attacker sends dust from a lookalike address so it appears in history and gets copy-pasted. | Never surface a counterparty address as a suggested destination. Flag sub-threshold unsolicited receipts. Fourth Meridian sends nothing, so the payment vector is absent — but the *display* vector is not. |
| **Malicious metadata / phishing links / NFT image URLs** | Token names and NFT URIs are attacker-controlled strings and remote URLs. | Never render remote images from token metadata. Strip/neutralize URLs. Escape all metadata. Treat every string as untrusted user input. |
| Webhook authenticity | Not applicable yet (no crypto webhooks). | If adopted: signature verification + replay protection before any handler runs. |
| Program-data parsing | Decoding arbitrary program data is an attack surface. | Phase A decodes **nothing**. Balance deltas only. |
| **DoS via huge histories** | A whale wallet or a spam-farmed address can have millions of signatures. | Hard bounds per sync with an **explicit `BOUNDED_SCAN` state** — never a silent truncation. Bitcoin's `BTC_TX_PAGE_BUDGET` has the right shape but no explicit exhaustion signal (§3.3). |
| Provider trust | An RPC can lie. | Reconcile every provider claim against arithmetic; a provider's balance is an *observation*, not a fact. |

## 10.3 Display policy summary

Show mint/contract address alongside symbol for any non-allowlisted asset. Never render remote
metadata images. Never present an unsolicited receipt as income. Never format a crypto quantity
through fiat currency formatting (§2.8). Show full precision or explicitly-marked truncation.

# FINAL REPORT

### 1 · Current Bitcoin architecture
A single-chain, single-asset balance sync (`lib/crypto/*`, ~2,000 lines) with **no crypto
tables**, persisting movements as bank `Transaction` rows. Excellent completeness arithmetic;
excellent refusal doctrine; leaked provider DTO; discarded provenance; day-truncated time;
fabricated bank semantics.

### 2 · Bitcoin data gaps versus Plaid
Nearly every v2.6 Financial Truth field is `null` on all 28 live crypto rows. Where Plaid is
richer: counterparty identity, category, lifecycle, authorization date. Where the **chain** is
richer but Fourth Meridian discards it: content-addressed identity, exact fee, finality depth,
input/output structure, raw provenance, second-precision time, mempool state.

### 3 · Bitcoin enrichment proposal
Retain per-input/per-output structure with owned-flags; full-precision block time plus
first-seen; block hash and height for reorg survival; coinbase and RBF identification; fee
linked by relation not string; raw payload retained until reconciled; integer satoshis. Shape
in §3.4.

### 4 · Solana architecture and first supported scope
Adapter over standard RPC (`getSignaturesForAddress`, `getTransaction`,
`getTokenAccountsByOwner`) at `finalized`, pointed at archival. Economics derived from
`pre/postBalances` and `pre/postTokenBalances` — **no program decoding**. Phase A per §4.4;
Phase B (swaps, staking, NFTs, DeFi) explicitly excluded.

### 5 · Provider/indexer comparison
Bitcoin: code to the **Esplora API shape**; keep mempool.space; **demote blockchain.info from
balance authority to discovery accelerator** pending a basis probe; self-hosted Esplora/electrs
(~600 GB + ~1.7 TB) as the end state. Solana: **standard methods on an archival endpoint**;
Helius/Triton/QuickNode as interchangeable URLs; enhanced parsed APIs only as accelerators whose
output is re-derived against balance deltas.

### 6 · Canonical multi-network model
Thirteen concepts, §6.1. Universal: network, custody, address, asset, chain transaction,
observation, event, movement, fee, balance observation, ownership, reconciliation. Chain-specific:
the provenance envelope and the adapter, only.

### 7 · Event/movement taxonomy
Three layers: mechanical (always assertable) → financial meaning (judgment + evidence) →
protocol semantics (optional, versioned, discardable). Four prohibitions in §7.3, to be enforced
by tests.

### 8 · Historical-engine compatibility
Doctrine correct, **dimensionality wrong**. Every authority is `(account, day)` and must become
`(account, asset, day)`. Six specific breaks enumerated in §8.2, including the all-or-nothing
carry licence that is **already firing** on this database (378 `unavailable` snapshots).

### 9 · Solana wallet historical stress-test findings
**Not performed — no address available and none invented.** Read-only protocol in §8.5. The
gating question is step 8: can a real wallet reconcile from a signature scan at all?

### 10 · Completeness/reconciliation design
Per `(account, asset)`, derived never stored, asset-derived epsilon. Seven states, nine refusal
codes (§9.3). Per-asset valuation licensing (§9.5): the SOL series must survive an unpriceable
memecoin; the *aggregate* must still refuse, because an aggregate genuinely depends on
completeness.

### 11 · Security and privacy findings
Key boundary is correct and must become an executable invariant. **Highest-severity finding:
`InstrumentAlias` for crypto is keyed on `symbol` alone** — a fake `USDC` mint would collide with
the real asset's price series. Identity must be `(network, mint/contract)`. Also: the xpub is a
full-history privacy disclosure; token metadata is attacker-controlled; never render remote
metadata images; unsolicited receipts are never income.

### 12 · Parallel-session overlap analysis
The proposed boundary is right in spirit and **understates the entanglement**: the highest-value
Bitcoin fix (the income leak) lives in the most-conflicted files in the repo. Slices A, B (minus
the `flowType` write) and C are fully independent and can start now. Slice 0 and everything
schema-touching must wait.

### 13 · Recommended implementation slices
**0 → A → B → C → D → E → F → G → H.** The brief's A–G order is corrected in two ways: separation
before enrichment, and the canonical model before Bitcoin work.

### 14 · What should happen before L8
- Slice A (pure cores widened to `(account, asset)`) — no schema, no overlap.
- Slice B (adapter extraction, honest bounds, probe fixes) — crypto-only.
- Slice C (Solana read-only audit) — no persistence. **This is the highest-information,

- The design decision in §6.4 (share the abstraction, not the table) should be **ratified before
  L8 designs its own `ProviderObservation`/`EconomicEvent`**, so L8 is designed knowing a second

### 15 · What should happen inside or after L8
- Slice 0 — the income leak — immediately after the transfer/economic-date session lands.
- Slice D — crypto event persistence — after the economic-date migration.
- Slices E, F, G, H — after D.

### 16 · Should Bitcoin and Solana be upgraded together?
**Yes — designed together, shipped in sequence.** Designing Bitcoin's enrichment alone would
re-derive a UTXO-shaped model that Solana then breaks. Designing both together forces the
`(account, asset)` dimension, integer base units, per-asset reconciliation, and the observation/
event split — all of which Bitcoin needs anyway and none of which Bitcoin's own data would have
forced. But **shipping** them together doubles the blast radius: Bitcoin has live production data
and a working reconciliation; Solana has neither. Migrate Bitcoin onto the shared model first
(D), prove reconciliation is preserved, then add Solana (E).

### 17 · How Ethereum, XRP, Cardano and future networks plug in
Each implements the same `ChainAdapter` port and contributes: an asset-identity scheme
(mint/contract/native), a base-unit basis, a finality model, a provenance envelope type, and an
address-discovery strategy. Concretely —
**Ethereum:** account model, `eth_getLogs` + traces for internal transfers, ERC-20 by contract,
18 decimals, probabilistic finality by depth. Hardest part is internal transactions (needs traces).
**XRP Ledger:** account + sequence, `account_tx` gives complete per-account history, **deterministic
finality on ledger validation**, trust lines instead of token accounts. Easiest of the four.
**Cardano:** eUTXO — closest to Bitcoin, plus native multi-assets in outputs and separate stake
addresses. The multi-asset dimension is exactly what Solana forces us to build.
**Anything else:** if a network needs a *new concept* rather than a new envelope type, the
canonical model is wrong — which is why Slice H (Ethereum) exists as a deliberate falsification test.

### 18 · Ideas that must NOT be implemented — they would reduce Financial Truth

1. **Adding a BTC/USD `FxRate` row** to "make crypto totals work." It would inject the full fiat
   value of every crypto receive into the Cash Flow income headline. The empty `FxRate` table is
   currently load-bearing.
2. **Keeping crypto movements in `Transaction`** and adding nullable crypto columns. Two domains
   in one table with a discriminator is the `FinancialState` anti-pattern this codebase already
   ratified against.
3. **Adopting a provider's parsed transaction DTO** (Helius's `getTransfersByAddress`,
   Blockchair's classifications) as the canonical shape. It puts a vendor's interpretation of
   "swap" inside the truth layer.
4. **Classifying incoming crypto as income by sign.** Already happening
   (`SIGN_DEFAULT_INFLOW` on 28 live rows); it is the same defect v2.6-TRUTH-1 removed for banks.
5. **Valuing a token because it has a symbol.** Symbols are attacker-controlled. Identity is the
   mint address; valuation requires an allowlist.
6. **Zeroing an unpriceable holding.** It must be held, counted, and unvalued.
7. **Counting a swap as income + spending.** One event, N movements, zero cash-flow effect.
8. **Treating `blockTime` as authoritative.** Validator-estimated. Fine for ordering and daily
   bucketing; never for a tax lot boundary.
9. **Ingesting at `confirmed` on Solana.** Optimistic confirmation is theoretically reversible.
   Ingest at `finalized`.
10. **Inferring completeness from "the scan finished."** A bounded scan that ran out of budget
    looks identical to an exhaustive one. Completeness is arithmetic plus an explicit adapter
    declaration — never an inference.
11. **Folding staking balances into the wallet's SOL balance.** Rewards accrue off-ledger; the
    wallet would silently under-reconcile forever.
12. **Deriving a counterparty name from an address.** Address poisoning makes this an attack
    surface, and an address is not an identity.
13. **Rendering token metadata images or URLs.** Remote, attacker-controlled.
14. **Storing crypto quantities as `Float`.** Marginal at 8 decimals, disqualifying at 18.
15. **Persisting a completeness flag.** The existing derived-only doctrine is correct and must
    survive the multi-asset widening: a stored flag blesses staleness.
16. **A per-network historical engine.** Two engines will disagree. One engine, `(account, asset,
    day)`, many adapters.
