# v2.6-REVIEW-2 — architectural corrections to REVIEW-1

A re-measurement of `docs/plans/v2.6-REVIEW-1-ARCHITECTURAL-STATE.md`, starting
from the codebase rather than from that document's conclusions. **No product
code was changed. No roadmap document was changed. REVIEW-1 was not edited** —
it stands as written, and this document is the correction record against it.

Two scratch instruments were written to produce the measurements below
(`probe-judgment.ts`, `probe-debt-v2.ts`). They are **not registered audits** and
are not on disk in this repository; §7 recommends which of them should be landed
and enrolled.

⚠️ One measurement in this document was itself wrong on first run and is
corrected in §4.4. It is recorded rather than quietly replaced, for the same
reason this document exists.

## 1. Executive summary

### What REVIEW-1 got right

- **Financial Truth is structurally complete but not fully witnessed.** The
  qualification in §1 — three REQUIRED audits passing on a corpus that cannot
  express their failure mode — is correct, and this document finds it is a
  *larger* problem than stated (§4.5).
- **Grading has largely left React components.** The direction of §2 is right.
  Reading the widened census (§3.3) rather than counting it, there are two
  non-authority financial verdicts left in the UI layer, one of which is
  currently unreachable. That is close to the "effectively zero" claim, though
  reached by a different route.
- **Debt is the remaining duplicate-authority cluster.** §3's identification of
  debt is correct. The specific evidence offered for it is not (§4).
- **`computeAssessment` already inherits Truth.** §4's supporting observation —
  its inputs are the domain assemblers, which already consume the canonical
  authorities — holds, and it is the reason a "rebuild on the authorities" was
  never the real work.

### What it got wrong

| REVIEW-1 claimed | The code shows |
| --- | --- |
| `computeAssessment` "became **the AI's reasoning layer**" | It serves **both** an AI path and a product-UI path. The Daily Brief renders its verdicts as user-facing copy (§2). |
| "Every product surface renders figures; **none renders a graded judgment**" | `app/api/brief/route.ts` branches on `liquidity.classification`, `debt.classification` and `currentStatePriority` to choose the sentence a user reads and the tone it is shown in (§2.3). |
| The open question is "**Are graded verdicts a product surface at all, or an AI input?**" | The question was already answered in code by v2.6-BRIEF-1 (`60a6722`), 19 commits before REVIEW-1 was written. Both. (§2.5) |
| "**VERDICT 1 site**" — grading has left the UI | The instrument cannot see verdicts under 100, named thresholds, string classifications, or judgment arriving via an API payload. The count is a property of the regex, not of the codebase (§3). |
| Weighted APR: "**Two** implementations, and they can disagree" | **Five** implementations (§4.2). On the live corpus they **agree** to rounding (§4.4). |
| "The **display-vs-reporting currency split is the live hazard**" | Not live. Every Space and every account in the corpus is USD. The hazard is real and latent; it is not currently expressible (§4.5). |
| Rank 1 seed convergence, rank 2 debt convergence, as independent items | They are one item. Debt duplication is invisible for exactly the reason the three seed states are, and converging debt first would produce a guard that cannot fail (§5.4). |

### Which roadmap conclusions change

1. **"Assessment migration" is not a roadmap item and never was.** It appears
   once in the repository, as a parenthetical in `docs/architecture/TIME_MODEL.md:232`.
   REVIEW-1 promoted a document aside to a roadmap item and then spent §4 and §6
   re-ranking it. There is nothing to strike from the roadmap because nothing was
   ever on it (§5.2).
2. **The decision REVIEW-1 §6.3 asks for should not be scheduled.** "Decide

3. **Debt convergence is not a new architectural slice.** It is the unfinished
   remainder of roadmap item 1, *Semantic Authority Convergence*, whose exit
   criterion has been unmet since the milestone opened (§5.3).
4. **Seed convergence and debt convergence are one slice, not two.** (§5.4)

## 2. The `computeAssessment` consumer map

### 2.1 Method

REVIEW-1 §4 reported consumers as:

```
computeAssessment consumers:  app/api/ai/chat/route.ts
                              app/api/brief/route.ts
                              (nothing else)
```

That list is accurate for *direct callers* and stops there. It does not follow
either caller to its terminal, which is where the classification is decided. A
route is not a consumer class — it is a hop. This map follows both to the surface
that renders or transmits the result.

### 2.2 The complete map

**Direct callers (non-test): 2.**

| Call site | Terminal | Class |
| --- | --- | --- |
| `app/api/brief/route.ts:767` | → `BriefPayload` → `components/brief/DailyBriefClient.tsx:331` → `app/(brief)/dashboard/brief/page.tsx` | **Product UI** |
| `app/api/ai/chat/route.ts:404` (master), `:454` (per-Space) | → `buildMasterSystemPrompt` / `buildSpaceSystemPrompt` → system prompt string | AI reasoning |

**Indirect consumers of the returned `FinancialAssessment` (non-test): 3.**

| Consumer | What it does with it | Class |

| `lib/ai/context-priority/planner.ts:99` | `planContextSelection` → `AuditLog` row (`AI_CONTEXT_SELECTION_PLANNED`), shadow-only, never consulted when building the prompt | Internal computation |

**Test consumers: 6.**
`lib/ai/intelligence/annotations.ti2.test.ts`,
`lib/ai/intelligence/brief-scope-adequacy.test.ts`,

**API class: none.** No route returns a `FinancialAssessment` or any part of one

returns *prose derived from it*, which is why the distinction matters.

### 2.3 Why the Daily Brief is a real product consumer

Observed, not inferred. `app/api/brief/route.ts` computes the assessment once
(`:767`) and passes it to both section builders. Nine assessment fields across
four sections reach rendered output:

**`buildAttention` — an item, its label, and its severity colour:**

```ts
// app/api/brief/route.ts:367
const liq = assessment.liquidity;
if (liq.classification === "CRITICAL" || liq.classification === "WARNING") {
  items.push({
    id: "low_liquidity", label: "Low cash position",
    value: fmtCurrency(liq.liquidCashTotal),
    detail: `About ${liq.coverageMonths.toFixed(1)} months of expenses covered`,
    tone: liq.classification === "CRITICAL" ? "danger" : "warning",   // :376
  });
}
```

**`buildInsight` — the sentence a user reads, selected by the engine's verdict:**

```ts
// app/api/brief/route.ts:536
const { debt, liquidity, cashFlow, currentStatePriority } = assessment;
switch (currentStatePriority) {                                        // :539
  case "DEBT":
    if (debt.classification === "CRITICAL") { … "high interest rate" }  // :547
  case "LIQUIDITY":
    if (liquidity.classification === "CRITICAL" || "WARNING") { … }     // :555
    if (liquidity.classification === "EXCELLENT") { … }                 // :559
  case "CASH_FLOW":
    if (cashFlow.deficitCause === "POSSIBLE_OVERSPENDING") { … }
}
// :594 — the section's tone is the verdict too
tone: currentStatePriority === "DEBT" || currentStatePriority === "LIQUIDITY"
  ? "warning" : "info",
```

Two further fields gate claims rather than select them:
`assessment.cashFlow.reliability` (`:496`) decides whether the savings-rate
sentence may be stated at all, and `assessment.dataQuality.unidentifiedInflowShare`
(`:505`) decides whether it carries a provisional caveat.

The chain terminates in a rendered page: `DailyBriefClient.tsx:331` fetches
`/api/brief` and renders `payload.sections`; `app/(brief)/dashboard/brief/page.tsx:28`
mounts it. There is no AI in this path. `AiAdvice` is *preferred* when a cached
row exists (`:407`), but the assessment-driven branch is the deterministic
fallback, and on the live corpus it is what a user sees.

### 2.4 The verdict on REVIEW-1 §4

REVIEW-1 wrote:

> `computeAssessment` did not become the canonical product assessment engine. It
> became **the AI's reasoning layer** — a deterministic pre-computation that keeps
> the model from inventing verdicts. **Every product surface renders figures; none
> renders a graded judgment.**

The first sentence is half right — it is not *the canonical* product assessment
engine, because the Debt workspace has its own (§4.6). The second sentence is
wrong. The third sentence is wrong.

⚠️ The mechanism of the error is worth naming, because it is the same one
REVIEW-1 itself warned about in its §2 opening: *a header is a claim, not a
census*. REVIEW-1 replaced header-reading with a component-source census, which
is a real improvement, but a component census cannot see a judgment that was made
on the server and arrived as a finished string. The Brief's verdicts are
invisible to a scan of `components/` because by the time they reach a component
they are prose.

### 2.5 Conclusion: AI-only, UI-only, or both

**Both.** And it was already both when REVIEW-1 was written — v2.6-BRIEF-1
(`60a6722`, "feat(truth): the Brief reads the assessment authority, not its own
ratios", 19 commits earlier) deliberately moved the Brief onto
`computeAssessment` precisely so the Brief and the AI could not state different
conclusions from the same context. The route says so in a comment at `:43`:

> `v2.6-BRIEF-1 — THE deterministic financial assessment. The Brief no longer
> answers "how am I doing?" itself; it reads the same authority the AI reads.`

REVIEW-1 §4 therefore asks a question that the arc had already answered:

> **Are graded financial verdicts a product surface at all, or are they an AI
> input?**

They are both, by a decision already executed and documented. This is not an open
product question and should not be scheduled as one. What follows from that:

- REVIEW-1 §6 item 3 ("Decide whether assessment is user-facing") should be
  struck. It is a measurement, and it has now been taken.
- REVIEW-1 §6 item 4 ("Then, and only then, Assessment migration — or its
  cancellation") is gated on item 3 and falls with it.
- REVIEW-1 §5's row "Surface the assessment | **Feature** | Design question: what
  does a user see?" is wrong about the present tense. The assessment is already
  surfaced, in the Brief. Surfacing it *further* — inside a Space workspace — is a
  genuine feature question and remains correctly classified.

## 3. Review of `audit-surface-independence`

### 3.1 What the instrument does

`scripts/audit-surface-independence.ts` scans `components/` and `app/` for three
line-shaped patterns — AGGREGATION, RATIO, VERDICT — and reports counts plus a
worklist. Its own header is honest about being a candidate-finder, not a defect
detector, and its INFORMATIONAL tier is correctly chosen.

Reproduced unchanged on the current tree:

```
AGGREGATION  29 sites
RATIO        23 sites
VERDICT       1 site    components/platform/widgets/OpsCostWidget.tsx:31
candidate sites : 53 · files involved : 22
```

REVIEW-1 §2 built its central claim on that third number:

> **The VERDICT count is the finding.** One site, and it is
> `OpsCostWidget.tsx:31` — a milliseconds-to-seconds formatter, not a financial
> judgment. **There are effectively zero financial verdicts left in components.**

### 3.2 Why the count is a property of the regex

The VERDICT pattern is:

```ts
// scripts/audit-surface-independence.ts:57
re: new RegExp(String.raw`${MONEY}\s*[<>]=?\s*[\d_]{3,}`, "i"),
```

Four structural blind spots, each of which hides a real judgment shape:

1. **`[\d_]{3,}` requires a literal of three or more digits.** Every threshold
   the financial domain actually uses is invisible: `> 20` (APR), `>= 6`
   (months), `> 0.5` (a ratio), `>= 30` (utilization). The engine's own constants
   — `APR_CRITICAL_THRESHOLD`, `LIQUIDITY_WARNING_MONTHS`, `DEBT_FRACTION_DOMINANT`
   — are all two digits or fewer.
2. **The right-hand side must be a numeric literal.** A comparison against a
   named constant or a config value never matches. `monthsCovered >= targetMonths`
   is a coverage verdict and is not seen.
3. **String classifications are not a comparison shape at all.**
   `classification === "CRITICAL"` is the dominant judgment idiom in this
   codebase and matches none of the three patterns.
4. **`break` after the first match, with VERDICT tested last.** A line that is
   both an aggregation and a threshold is counted as AGGREGATION and never
   reaches the VERDICT test. The VERDICT bucket is structurally the residue of
   the other two.

A fifth limit is scope rather than pattern, and is the one that matters most for
§2: **the scan covers `components/` and `app/` only**, and a judgment that is
computed server-side and delivered as a finished string is invisible everywhere.
REVIEW-1 recorded a version of this in its own "Out of scope" §3, noting `app/`
produced almost no hits because "routes return DTOs" — but `app/api/brief/route.ts`
does not return a DTO. It returns rendered prose containing a verdict.

### 3.3 Corrected measurement

`probe-judgment.ts` widens on the four pattern axes — any-magnitude and decimal
literals, named thresholds, categorical grade literals as the *output* of a
branch — and scans `lib/` as well, so "judgment left the UI" can be checked
against "judgment moved one layer back". Layers are assigned by path, with
`lib/ai/intelligence` and the truth modules classed as authorities.

```
kind                API  AUTH(assess)  AUTH(truth)  COMPONENT  PAGE  SERVER-LENS  lib(other)
GRADED-BRANCH         0            7            0          1     0            1           0
GRADE-FROM-CLASS      7           36            6          6     0            0          21
THRESH-LITERAL        5           17           46         62     1            4          16
THRESH-NAMED          1            6            1          2     0            0           0
TOTAL                13           66           53         71     1            5          37
```

⚠️ This is a wider net, not a better one. 71 component-layer hits is not 71
defects; it is a worklist, and it was read rather than counted — the same
discipline REVIEW-1 applied to its own 29 and 23.

### 3.4 Rendering arithmetic versus financial judgment

The distinction that separates the two, applied to the component hits:

**Not judgment — rendering arithmetic and control flow.** Pagination
(`totalPages > 1`), input validation (`balance < 0`, `apr > 100`), bar and donut
geometry (`value / total`), sign-of-delta tone (`dNet > 0 ? "positive" : "warning"`
in `cash-flow-insights.ts:172` — a direction, not a grade), and simulation bounds
(`months < MAX_MONTHS` in `DebtPayoffSection.tsx:80`). These account for the
overwhelming majority.

**Consuming a verdict, not producing one.** `HoldingsConcentration.tsx:59` and
`InvestmentAllocationPanel.tsx:108` branch on
`concentration.classification`, which is produced by `lib/investments/concentration.ts`
— a single owner with declared bands. This is what correct consumption looks
like and is explicitly not a finding.

**Genuine non-authority financial judgment in the UI layer — two sites:**

| Site | Judgment | Live? |
| --- | --- | --- |
| `components/space/widgets/debt/debt-signals.ts` | utilization grade (`:52`), *"Minimum payments may not cover interest"* (`:72`), APR/minimum completeness verdict (`:94`) | **Yes** — rendered by `DebtWorkspace` |
| `components/space/sections/SectionRegistry.tsx:748` | `monthsCovered >= targetMonths ? "green" : "orange"` — a second liquidity coverage verdict, computed from `cfg.monthlyExpenses` rather than the baseline authority | **No** |

The second is measured as unreachable, not assumed: `emergency_fund_progress` has
**zero rows** in `SpaceDashboardSection` across the corpus, consistent with
v2.6-LEGACY-1 having retired the hero. It is dead code carrying a live-looking
divergence, and it is the successor question that v2.6-LEGACY-1 left open.

### 3.5 What this does to REVIEW-1 §2

REVIEW-1's *conclusion* — grading has largely left React — survives. Its
*evidence* does not. The corrected statement is in §6, item C.

The architecturally meaningful residue is one item, not zero: **`debt-signals.ts`
is a judgment layer inside `components/`**, and it is the UI half of the split
described in §4.6.

## 4. Debt authority review

### 4.1 Starting from questions, not modules

REVIEW-1 §3 started from two code sites that looked alike and inferred a
duplicate authority. That is the right instinct and the wrong entry point: it
finds duplicates that share a shape and misses duplicates that share a question.
Starting from the question instead:

| Financial question | Implementations | Verdict |
| --- | --- | --- |
| What is my weighted average APR? | **5** | duplicate (§4.2) |
| What is my total debt? | **6** | duplicate, populations differ (§4.3) |
| What is my total minimum payment? | **4**, and one *estimates* while another *reports a gap* | duplicate with divergent semantics (§4.3) |
| What is my utilization? | **2** — one uses the `utilizationLevel` authority, one does not | duplicate (§4.3) |
| What is this account's APR? | **1** — `lib/debt/effective-terms.ts`, with a ban-guard | **converged** |
| What does this balance mean? | **1** — `lib/debt/balance-semantics.ts` | **converged** |
| Is my debt healthy? | **2**, and they never meet | duplicate *layer* (§4.6) |
| Which debt should I pay first? | 2, but **different questions** (§4.7) | not a duplicate |
| Am I on track for this goal? | 2, but **different questions** (§4.7) | not a duplicate |

### 4.2 Weighted average APR — five implementations

REVIEW-1 §3 found two and framed the finding on them. There are five.

| # | Site | Population | Currency basis | Rounding | Refusal rule |
| --- | --- | --- | --- | --- | --- |
| A | `components/space/sections/DebtPayoffSection.tsx:194` | `interestRate != null` **including 0** ∧ owes | display | none | none |
| B | `components/space/widgets/debt/debt-kpis.ts:223` (`computePayoffAggregate`) | declared byte-mirror of A (`:196` cites `DebtPayoffSection.tsx:195–219`) | display | none | none |
| C | `lib/perspective-engine/lenses/debt.core.ts:285` (`blendedApr`) | FULL rows, `interestRate != null` **including 0**, **no owes filter** | lens target | none | none |
| D | `lib/ai/intelligence/annotations/metrics.ts:400` (`weightedAvgApr`) | FULL visibility ∧ `apr > 0` ∧ owes | reporting | **2dp** | none |
| E | `lib/ai/intelligence/annotations/engine.ts:273` | back-derived as `interestBurden × 12 / totalDebtWithAPR` | reporting | none | **refuses if ANY debt row has a null APR** ⇒ `INSUFFICIENT_DATA` |

⚠️ **E is inside `computeAssessment` itself.** REVIEW-1 named `metrics.ts:400` as
"the engine" implementation; the engine has two, and they are not the same
function. D is a reported figure; E is the input to the health classification. On
a Space where one debt account lacks an APR, D publishes a number to the AI
prompt (`assessment-serializer.ts:271`) while E refuses to grade at all. That is
the assessment stating a weighted APR and simultaneously declining to stand
behind the population it was computed over.

### 4.3 The rest of the cluster

**Total debt — six sites:** `debt-kpis.ts:107` (`totalDebt`),
`debt.core.ts:253` (lens `totalDebt`), `DebtClient.tsx:465–467`
(`used`/`limit`/`owed`), `debt-adapters.tsx:111` (`totalMinPmt` denominator set),
`debt-perspective-adapters.tsx:153` (`totalMonthly`), and
`engine.ts` (`totalLiabilities`, via the accounts assembler). All are correct in
isolation; each defines its own membership.

**Total minimum payment — a divergence in *semantics*, not arithmetic.**
`lib/data/accounts.ts:251` **estimates** a missing minimum via
`estimateMinimumPayment` when an APR is known and the account owes; it is the
loader behind `/dashboard/credit`. `lib/space/mount-composition.ts:136` resolves
effective terms and **does not estimate**, so the same account arrives at the
Space Debt workspace with a null minimum, is excluded from `debt-kpis.minPayments`,
and is reported by `debt-signals.ts:94` as *"N missing a minimum payment"*.
`DebtClient.tsx:418–423` then estimates a second time on the client.

Two live surfaces, same account, same question: one shows an estimated monthly
minimum, the other says the figure is missing.

**Utilization — two answers.** `debt-kpis.ts:145` calls the
`lib/accounts/credit-utilization.ts` authority. `DebtClient.tsx:472` computes
`limit > 0 ? (owed / limit) * 100 : 0` inline, over a different row set
(`owedCards` for the numerator, `limitedCards` for the denominator) and never
resolves a level.

### 4.4 ⚠️ Why the first divergence probe was wrong

The first run of the divergence probe (`probe-debt-apr.ts`) reported two Spaces
where the client planner and the assessment disagreed materially:

```
Smith-Doe Household   A 4.4275   C 3.8750   D 3.8800    *** DIVERGENT ***
Debt Payoff Tracker   A 13.3662  C 12.1194  D 12.1200   *** DIVERGENT ***
```

**That result was an artifact of the probe, not a property of the codebase.** The
probe modelled derivation A over every debt row the Space contained, including
`BALANCE_ONLY` links. The client never receives those rows in that form:

- `lib/space/mount-composition.ts:179` passes links through
  `normalizeSharedAccounts` (`lib/account-privacy.ts:243`), which **aggregates**
  `BALANCE_ONLY` shares into a synthetic row carrying type, balance, currency and
  `lastUpdated` — and **no `interestRate`, no `creditLimit`, no institution**.
- `lib/data/accounts.ts:181–198` fails closed the same way for
  `/dashboard/credit`, sanitising via `sanitizeForBalanceOnly`.

A withheld account's APR therefore cannot reach any client, and every
implementation is FULL-only in practice. The probe attributed a privacy boundary
to an authority disagreement.

The error is recorded rather than replaced because it is the same class of
mistake as the one this document corrects in REVIEW-1: **a measurement that
models the wrong population produces a confident number about something else.**
REVIEW-1's VERDICT count and this probe's first run are the same failure at
different layers.

### 4.5 Corrected measurement, and why the corpus hides the duplication

`probe-debt-v2.ts`, over 7 Spaces holding debt:

```
Q1  weighted avg APR
      A/B client planner + kpis    4.4403     (n=4)
      C  perspective lens          4.4403     (n=4)
      D  assessment metrics        4.4400     (n=4)
      E  assessment VERDICT        4.4400
      → agree (to rounding)
…
  Spaces with debt         : 7
  weighted-APR divergent   : 0
  minimum-payment divergent: 0
```

**Every implementation agrees on the live corpus.** The only observed difference
is D's 2dp rounding (`4.4403` → `4.44`).

The reason is that the corpus cannot currently express any of the five
divergence mechanisms:

| Mechanism | Requires | Corpus state |
| --- | --- | --- |
| display vs reporting currency (**REVIEW-1's named "live hazard"**) | a Space whose display currency ≠ reporting currency | **every Space and account is USD** |
| `apr === 0` included by A/B/C, excluded by D | a debt account with a 0% APR | **none exists** |
| C's missing owes-filter | a settled or credit-balance account carrying an APR | **none exists** |
| E's `hasNullAPR` refusal diverging from D's figure | one rated and one unrated debt account in the same Space | **none exists** — Chris' Space has two unrated accounts, so both refuse together |
| minimum-payment estimation asymmetry | an indebted account with an APR and **no** minimum payment | **none exists** — the seed supplies a minimum on every rated, indebted row |

⚠️ This is the correction that matters most. REVIEW-1 §3 stated:

> The display-vs-reporting currency split **is the live hazard** — those differ
> whenever the "view as" override is active.

It is not a live hazard. It is a latent one, and the corpus contains no state in
which it can be observed, no test that constructs one, and no audit that would
fail if it appeared. The duplication is **real in code and unwitnessed in
evidence** — which places it in exactly the same category REVIEW-1 identified in
its own §1 for the three seed states, and did not connect to its §3.

### 4.6 The actual remaining duplicate judgment layer

The five APR implementations are an arithmetic duplication. Underneath them is a
structural one that REVIEW-1 did not surface:

```
"Is my debt healthy?"

  computeAssessment  engine.ts:269–291   → debt.classification
                                            CRITICAL / WARNING / IMPROVING /
                                            HEALTHY / INSUFFICIENT_DATA
                     consumed by:  assessment-serializer.ts (AI prompt)
                                   app/api/brief/route.ts:547 (Daily Brief)
                     reaches:      the AI, and the Brief
                     NOT consumed by any Space workspace

  debt-signals.ts    buildDebtSignals()  → DebtSignal[] { tone: "ok" | "warn" }
                     inputs:  utilizationLevel thresholds, simulatePayoff-returns-null,
                              lens promoEnds metric, APR/minimum gap counts
                     reaches: the Debt workspace
                     NOT connected to computeAssessment in any way
```

**Two debt judgment layers, disjoint consumers, zero shared code.** They do not
currently contradict each other on the corpus — on Chris' Space the assessment
returns `INSUFFICIENT_DATA` (both accounts lack an APR) while the workspace says
*"Debt details incomplete — 2 missing an APR"*, which agree in substance. But
nothing makes them agree, they are graded from different inputs against different
thresholds, and only one of them is reachable by the AI.

This — not the weighted-APR arithmetic — is the debt equivalent of what
v2.6-ASSESS-2 resolved for liquidity: one question, two definitions, neither
disclosing which it used.

### 4.7 Genuinely different questions — recorded so they are not "converged"

Three pairs look like duplicates by shape and are not. Recording them is part of
the deliverable, because a convergence slice that collapses them would destroy
information.

- **`lib/goals/goal-trajectory.ts` vs `computeGoalAlignment` (`engines.ts:46`).**
  The first asks *am I on pace to reach the target amount by the target date?*
  and honestly reports that pace projection is unavailable (no contribution
  ledger exists). The second asks *is my behaviour aligned with this goal's
  intent?* — a debt-payoff goal with active payments is `ALIGNED` regardless of
  pace. Same domain, different questions.
- **`metrics.ts` avalanche/snowball targeting vs `DebtPayoffSection.simulatePayoff`.**
  A recommendation (which account first) versus a simulation (how long at this
  payment). Neither answers the other.
- **The perspective-lens `verdict` strings** (`debt.core.ts:360–366`,
  `liquidity.core.ts:354–362`) read like judgments and are not. They are
  deterministic narration templates over amounts and counts, with no threshold
  and no grade. Applying the doctrine in `same-unit-not-same-question`: the unit
  is shared, the question is not.

### 5.2 "Assessment Migration" is not a roadmap item

### 5.3 Semantic Authority Convergence is unfinished, and debt is why

`docs/plans/ROADMAP.md` item 1, the milestone's declared foundation:

> **1. Semantic Authority Convergence** — *foundation; do first*
> Every percentage and derived financial metric has exactly one canonical owner.
> […] a single resolver module plus a source-scan guard that bans inline
> re-derivation repo-wide (`lib/debt/effective-terms.ts` + `effective-terms.test.ts`
> is the reference implementation).
> *Exit:* no displayed percentage or derived metric is computed at more than one
> site; each has a named owner and an enrolment guard.

Weighted average APR is a **displayed percentage** — rendered at
`DebtPayoffSection.tsx:339, 380, 439, 556, 660` and serialized into the AI prompt
at `assessment-serializer.ts:271` — computed at **five sites**, with **no named
owner** and **no enrolment guard**.

The reference implementation's guard covers the APR *value* and stops there:

```ts
// lib/debt/effective-terms.test.ts:86
const BAN = /\.\s*apr\s*\?\?\s*[A-Za-z_$][\w$]*(\??\.)\s*interestRate/;
// :106  "no production file re-derives `apr ?? interestRate` inline"
```

Nothing bans re-deriving the *aggregate*. Item 1's exit criterion has been unmet
since the milestone opened, and debt is the reason. **Debt convergence is not a
new architectural slice competing for a position in the ranking — it is the
remainder of the item the roadmap already put first.** Framing it as new would
conceal that the foundation workstream never closed.

### 5.4 Why seed convergence and debt convergence are coupled

REVIEW-1 ranked them 1 and 2 as separate items with separate justifications. The
measurement in §4.5 makes them one:

- The debt duplication produces **zero** observable divergence on the corpus.
- It produces zero because five specific states are absent: mixed display/reporting
  currency, a 0% APR, a settled account with an APR, one rated + one unrated
  account in the same Space, and an indebted rated account with no minimum
  payment.
- Absent those states, a convergence guard written today **cannot fail**. It joins
  the three REQUIRED audits REVIEW-1 §1 already identified as passing on a corpus
  that cannot express their failure mode.

Converging debt first therefore buys a green check and no confidence. Seeding
first, then converging, produces a guard that would have caught the divergence —
which is the only version of this work that is worth doing. They are one slice,
sequenced seed-then-converge, not two items ranked adjacently.

⚠️ This generalises the lesson REVIEW-1 drew in its own closing note ("Seed
convergence rises to first… it is actually the precondition for trusting every
other item's completion signal") and applies it to the item REVIEW-1 placed
immediately after it, which it did not.

## 7. Recommended next slice — documented, NOT implemented

One slice, three ordered parts. Nothing below has been built.

### 7.1 Extend the seed so debt divergence can exist

Prerequisite, not preamble. Five states, each disarming a different mechanism
(§4.5), each cheap:

1. a Space whose display currency differs from its reporting currency, holding
   debt in both;
2. a debt account with `apr = 0` (a real product state — a promotional balance);
3. a settled or credit-balance debt account that still carries an APR;
4. one rated and one unrated debt account **in the same Space**, so `metrics.ts`
   publishes a figure while `engine.ts` refuses;
5. an indebted, rated account with **no** minimum payment, so
   `lib/data/accounts.ts` estimates while `mount-composition.ts` reports a gap.

⚠️ Per `v2.6-seed1-convergence`: a stale projection cannot live in a seed. States
2–5 must be constructed as legitimate product states, not as broken rows.

### 7.2 Name the owner and converge

Following the roadmap's own reference implementation
(`lib/debt/effective-terms.ts` + guard), one resolver answering the four
duplicated questions of §4.1 — weighted APR, total owed, total minimum, aggregate
utilization — stating its population, its currency basis and its refusal rule,
with the estimation asymmetry of §4.3 resolved as an explicit product decision
(as `resolveExpenseBaseline` did for DECLARED > MEASURED) rather than an accident
of which loader ran.

The five call sites of §4.2, the six of §4.3, and `DebtClient.tsx:472` become
consumers. `engine.ts:273` and `metrics.ts:400` collapse into one.

⚠️ Per `same-unit-not-same-question`: the three pairs in §4.7 must survive
untouched. Converging the unit must not collapse the question.

### 7.3 Land audits that witness the states

- **Enrolment guard**, in the shape of `effective-terms.test.ts:86` — ban inline
  re-derivation of the debt aggregates repo-wide. This is the roadmap item 1 exit
  criterion, stated in code.
- **`probe-debt-v2.ts` → a registered audit.** It becomes REQUIRED only once
  §7.1 lands; before that it passes vacuously and would be a fourth audit
  incapable of failing.
- **`probe-judgment.ts` → INFORMATIONAL, alongside `audit-surface-independence`.**
  Not a replacement: the two answer different questions (arithmetic in a
  rendering surface versus judgment anywhere), and the older instrument's
  narrower net is useful precisely because it is narrow. Registering it also
  keeps the §3 blind spots on the record rather than in this document alone.

### 7.4 What this slice does not do

It does not resolve §4.6 — the two disjoint debt judgment layers. Converging the
arithmetic makes the Brief, the AI and the Debt workspace compute the same
figures; it does not make them state the same verdict, because `debt-signals.ts`
grades from different inputs against different thresholds. That is the debt
analogue of v2.6-ASSESS-2 and is a second slice. It is named here so it is not
mistaken for something this one closes.
