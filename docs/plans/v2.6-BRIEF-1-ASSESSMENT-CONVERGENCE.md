### 1.3 Finding A — a REQUIRED gate was measuring the wrong population 🔴

`scripts/audit-ui-truth-convergence.ts` — a REQUIRED CI gate whose stated job is
"every presentation surface reads its canonical authority" — **imported
`resolveTransferAssessments` and never called it.**

`classifyLiquidity` reads `transferMaturity` (`lib/transactions/liquidity.ts:244`),
and `isDebtPaymentAttested` (v2.6-DEBT-1) admits a row on *either* an owned
liability counterparty *or* a proven liability destination **type**. The
type-level attestation exists only in the maturity, which the live read boundary
attaches in `contextFields`. Without that call every row in the probe carried
`transferMaturity: null`, so the gate fell back to counterparty tier alone.

Measured on the live corpus:

```
probe as written (no resolveTransferAssessments)    94 rows   $195,442.37
the product (live path)                            119 rows   $241,592.37
invisible to the gate                               25 rows    $46,150.00
```

Every check passed anyway, because both sides of each parity comparison were
computed the same wrong way. **Consistency is not correctness**, and this is the
exact hazard the file's own header warns about in another form: a probe that does
not measure the live path is not evidence about the live path.

**Fixed** in this slice — the resolver is called and the maturity threaded. The
gate now measures $241,592.37 / 119 rows, matching the product exactly, and
still passes. No regression was being concealed; the gate was simply blind on 25
rows, and a debt-membership regression touching them could have merged green.

## Part 2 — The slice

### 2.1 The duplicate authority

`computeAssessment` (`lib/ai/intelligence`) is THE deterministic answer to "how
am I doing?" — debt health, liquidity coverage, cash-flow reliability, and which
of them leads. `app/api/brief/route.ts` answered the same questions itself, with
four inline rules that used **different definitions**:

```
totalLiquid / netWorth  < 0.05   →  "Low cash position"
totalDebt / totalAssets > 0.5    →  "Debt makes up more than half your assets"
cash / netWorth         > 0.4    →  "…sitting in cash"
(income − expense) / income      →  a savings rate, stated unconditionally
```

None is the authority's definition. Liquidity is **coverage** — cash measured
against what it must cover — not a balance-sheet share; debt health is **APR and
trend**, not a fraction of assets. So the Brief could open with "Low cash
position" on a Space the AI would tell you has EXCELLENT coverage. Two surfaces,
one corpus, opposite advice, and no way for a user to know which to believe.

### 2.2 The instrument, built first

`scripts/audit-brief-assessment-parity.ts` (INFORMATIONAL) holds everything
constant except `scopeHint`, assembles the real TRANSACTIONS_SUMMARY domain at
both scopes through the real registry, runs the real `computeAssessment` over
each, and diffs. Both arms read the same corpus on the same day, so any
difference is caused by the hint alone.

Its first run made the naive convergence untenable. **`scopeHint: 'brief'` is not
a payload-size knob.** Measured, varying only the hint:

```
incomeTransactionCount     8                     → 0
incomeConfidence           HIGH                  → LOW
cashFlowReliability        RELIABLE              → UNRELIABLE
deficitCause               POSSIBLE_OVERSPENDING → LOW_INCOME_SAMPLE
currentStatePriority       CASH_FLOW             → DATA_QUALITY
incompleteIncomeWarning    false                 → true
estimatedMonthlyExpenses   $5,494.09             → null
```

Had the Brief simply called `computeAssessment`, it would have told a user whose
income data is complete that there wasn't enough of it to read.

Two root causes, both structural:

1. **`byCategory.slice(0, 5)`.** `total` is the KD-17 **debit-only** sum, so an
   inflow category sorts last and is the first thing the slice discards. Income
   is such a category — and the assembler's own comment says its entry exists
   *for its `count`, which the intelligence engine reads for
   `incomeTransactionCount`*. The condensed payload destroyed the one value it
   was keeping that entry for. 11 categories → 5, Income dropped, count 8 → 0.
2. **`accts.accounts ?? []`.** `AccountsSectionData.accounts` is optional and its
   own doc says "omitted when `scopeHint === 'brief'`". The engine collapsed
   WITHHELD and NONE into the same empty set, so a real liability with its
   account list truncated was graded from zero debt accounts: no APR found,
   weighted average 0, verdict **HEALTHY at HIGH confidence**. Reproduced on a
   $20,000 liability in `brief-scope-adequacy.test.ts`.

Both are the arc's signature error in mirror image. v2.6-DEBT-1 established that
*absence of contradiction is not evidence* and refused to admit a debt payment on
silence. The assessment engine was admitting a **finding** on silence.

to a ratio. The ratio rule was a way of appearing to know when the input for
knowing was absent. Losing it is the point.

## Part 3 — v2.6-EVENT-1: the `removed[]` reprojection slice

Finding B (§1.4), fixed as its own narrow slice.

### 3.1 Verified before touching anything

The prior report was re-derived rather than trusted: 480/480 tests,
`audit-ui-truth-convergence` measuring $241,592.37 / 119 rows, `audit-event-identity`
red on exactly the two documented events, and `reprojectEvent` confirmed to have
**zero callers** anywhere outside `event-write.ts`.

### 3.2 Measured first

`scripts/repair-event-projection-drift.ts` — dry-run by default, `--apply`
required, single transaction. Its dry run found exactly:

```
cmsg0offf0djjdxfcfc9418j7   lifecycle PENDING → WITHDRAWN
                            currentTransactionId cmsddr849002tmv1lk2ljc2xj → null
cmsg0offh0djndxfcqu4hd1id   lifecycle PENDING → WITHDRAWN
                            currentTransactionId cmsddr850002vmv1liiofvokv → null
```

Three pre-flight refusals stop the run entirely: a drifting event with zero
observations, any `economicDate` that would move, any `observationCount` that
would change. None triggered.

### 3.3 The fix — write path first

`lib/plaid/syncTransactions.ts`, the `removed[]` branch, now re-projects every
event whose liveness it just changed, through the same `reprojectEvent` the
ingest path already uses. `reprojectEvent` needed no change: it *already* decided
liveness from `deletedAt` and already documented that this is how `WITHDRAWN`
becomes reachable. The authority was correct and simply never called.

Two details carry the correctness:

- **After the tombstone, never before.** The projection reads `deletedAt`;
  running it first would rewrite the same stale state it exists to correct.
- **The affected-event read is deliberately *not* filtered on `deletedAt: null`,**
  unlike the guarded `updateMany`. A run that tombstoned rows and then died left
  a stale event that the guarded count would report as 0 work. Reading the wider
  set makes a replay **self-healing** instead of permanently drifted.

Idempotent by construction: the projection is a pure function of the observations
and current liveness, so re-running writes the same values.

### 3.4 The repair, after the write path

Backup taken first (`backups/fintracker-2026-08-07T13-58-44-412Z.sql`), then
`--apply`:

```
FINANCIAL  fingerprint   b7e7e3df83bb104e → b7e7e3df83bb104e   ✓ held (4405 live rows)
PROJECTION fingerprint   56f3cb194d5ea19f → 4fda79b1bbd244d6   ✓ moved, as intended
residual drift after repair: 0                                  ✓
```

A projection is a lifecycle fact, not a money fact. The FINANCIAL fingerprint
spans every live transaction — not just the repaired rows — so it would catch
collateral damage anywhere, and it did not move. Event count unchanged at 4,381;
observations untouched; the transaction rows remain soft-deleted, not removed.

The repair calls `reprojectEvent` rather than re-deriving. It **cannot** disagree
with the write path, because it *is* the write path.

### 3.5 The guard that CI cannot pass vacuously

This is the part that mattered most. `audit-event-identity` caught the defect on
a long-lived corpus and is **structurally unable** to catch it in CI: a fresh
seed has never had a tombstone, so stored and derived agree vacuously.

`lib/plaid/removed-tombstone-reprojection.test.ts` therefore **manufactures the
state**. It drives the real `syncTransactionsForItem` — real
`recordTransactionObservation`, real `reprojectEvent` — over the in-memory fake
from `cursor-safety.test.ts` extended with the L8 tables. Nothing models the
sync; the sync runs. 25 checks across four scenarios:

1. a pending authorization creates a PENDING event pointing at the live row
2. `removed[]` tombstones it ⇒ **WITHDRAWN**, `currentTransactionId` null, while
   the observation, the event identity, `observationCount` and the economic date
   are all preserved
3. replaying the same `removed[]` is idempotent — and re-projects even when it
   tombstones nothing, which is the self-healing property
4. tombstoning one row does not withdraw a different event

**Verified non-vacuous:** removing the `reprojectEvent` loop makes it fail with 4
failures; restoring it passes. A guard that cannot fail proves nothing.

## Part 4 — v2.6-WINDOW-1: the Brief ↔ Space 90-day mismatch

Reported after Part 2 shipped. The identical-payload diff in §2.6 was true and
proved what it claimed — the four inline *ratio* rules were silent on this corpus
— but it could not have caught this, because the defect was in a **different**
figure that Part 2 never touched: the net-worth trend sentence.

### 4.1 Both figures, traced end to end

| | **Brief** | **Space** |
| --- | --- | --- |
| rendered | "up 14.9% over the last 90 days" | "↑ $9,016 · 47.4% vs May 7, 2026" |
| metric | net-worth % change between two snapshots | the same |
| window | the **90th-most-recent ROW** → newest | `subMonths(asOf, 3)` → asOf |
| dates | 2026-05-10 → 2026-08-07 (**89** days) | 2026-05-07 → 2026-08-07 (**92** days) |
| numerator | `latest.netWorth − oldest.netWorth` | `toValue − fromValue` |
| denominator | `\|oldest.netWorth\|` | `\|fromValue\|` |
| population | `SpaceSnapshot`, `fxMiss` excluded, unassertable-crypto endpoints refused | same rows |
| chronology | snapshot `date` (a balance/**stock** basis) | same |
| pending | n/a — balances, not flows | n/a |
| confidence gate | none | `Completeness: Observed` badge |
| authority | **none** — `SNAPSHOT_HISTORY_LIMIT = 90` row cap | `compareToForPreset` |
| formatting | `toFixed(1)` + `snapshotCount` printed as "days" | `toFixed(1)` + the real date |

Neither figure was arithmetically wrong. The chain, database → surface:

```
SpaceSnapshot rows
  → getRecentSnapshots(days = 90)      ⚠ `days` is used as `take: -days` — ROWS
  → projectSnapshotSection             snapshotCount = usable.length  (a COUNT)
                                       netWorthTrend = newest − oldest (ACCIDENTAL window)
  → SnapshotSectionData
  → app/api/brief/route.ts             `over the last ${snapshotCount} days`
```

`getRecentSnapshots`'s parameter is *named* `days` and *means* rows. Everything
downstream inherited the misnomer.

### 4.2 Why 3 days of boundary produced a 3× difference

```
2026-05-07   netWorth 19,015.30   debt 8,821.91     ← the Space's baseline
2026-05-08   netWorth 24,555.44   debt 3,836.80     ← a $4,985 debt paydown
2026-05-10   netWorth 24,388.03                     ← the Brief's baseline
```

The two baselines straddle a single-day $5,540 net-worth move. The Space measured
from before it; the Brief from after.

### 4.3 Classification

**(1) the same 90-day metric calculated differently — a defect**, and
specifically **(4) an authority bypass**. The Brief never consulted
`lib/perspectives/financial-window.ts` / `compareToForPreset`.

It is the surviving instance of a defect already fixed once. `v2.6-L4F` removed
`trendDeltaPct(trend)` from the Space launcher for the same reason — it "ran over
the last 14 SNAPSHOT ROWS, which is neither a month nor 30 days nor any window
the product defines" and read 25.0% against the inside view's 49.2%. The launcher
was converged onto `compareToForPreset`; the Brief was not, because the authority
was **private and month-only**, so the AI context layer could not reach it.

An unreachable authority does not prevent duplication. It guarantees it.

### 4.4 The fix

| Change | File |
| --- | --- |
| `canonicalWindowChange` extracted to a module with no `server-only` in its graph, generalized past PAST_MONTH, plus `seriesSpanDays`. Re-exported so no consumer moved — the `banking-population.ts` pattern, for the same reason. | `lib/data/snapshot-window.ts` |
| The section now carries `spanDays` (the **measured** calendar distance) and `canonicalChange` (the authority's answer). `netWorthTrend` is retained and documented as an ACCIDENTAL window. | `lib/ai/assemblers/snapshot.ts` |
| `SNAPSHOT_HISTORY_LIMIT`'s comment no longer claims "→ ~90 days"; it is a row cap and says so. | same |
| The insight and the "Net worth" item both read `canonicalChange` and name the window by its date. | `app/api/brief/route.ts` |
| Signal titles read `spanDays`. `snapshotCount` is kept for the density gate — a different question — and the distinction is written down. | `lib/ai/signals/detectors/snapshot.ts` |
| `dataQuality.snapshotSpanDays` is the real span; the model was being told a row count was a duration. | `lib/ai/intelligence/annotations/engine.ts` |

The Brief now shows a **calendar month**, matching the launcher and the
inside-Space default, rather than an unreachable quarter. No surface says
"90 days" any more.

## Part 5 — v2.6-WINDOW-2: finishing the window authority

Part 4 fixed the one place a row count reached a user. This audits the other six
call sites and closes the API that made the confusion possible.

### 5.1 The measurement that decided everything

`SpaceSnapshot` carries **`@@unique([spaceId, date])`** — at most one row per
Space per day, enforced by the schema. Therefore **N rows always span at least
N−1 calendar days**: a row cap is a *conservative over-cover* of the same number
of days and can never silently truncate a window.

Measured across the corpus:

```
Jane's Space          366 rows   366 distinct days   1.00 rows/day   371d span (5 gaps)
John's Space          365 rows   365 distinct days   1.00 rows/day   365d span
Smith-Doe Household   120 rows   120 distinct days   1.00 rows/day   120d span
Debt Payoff Tracker    90 rows    90 distinct days   1.00 rows/day    90d span
Chris' Space          748 rows   748 distinct days   1.00 rows/day   748d span
```

Every Space runs at exactly 1.00 rows/day, and gaps only *widen* the span. So no
caller was computing a wrong number. **The defect class was labelling, not
arithmetic** — which is why it survived review for so long: the behaviour was
right everywhere, and only the names lied.

### 5.3 The API change

`getRecentSnapshots(days = 30)` → `getRecentSnapshots({ rows: N })`.

A positional number cannot say which unit it is. An object can, and
`getRecentSnapshots(365)` now **fails to compile** — so the ambiguity is closed
by the type rather than by everyone remembering. The `SnapshotReadBound` doc
carries the `@@unique` argument for why a row bound is *correct* here and not
merely tolerated.

**No date-bounded reader was added.** The measurement says no consumer needs one:
every caller is a generous cap with client-side clipping, and the one surface
that makes a *claim* about a window resolves it through `canonicalWindowChange`.
Shipping a window reader with no consumer is the failure this codebase already
learned once — TX-3, "never ship an authority without a consumer".

### 5.4 Guards

`lib/data/snapshot-read-bound.test.ts`, each **verified to fail when violated**:

1. every call states `{ rows: N }` — *fails* on a positional call (and `tsc`
   independently rejects it: `Argument of type 'number' is not assignable`);
2. no duration-named constant feeds the bound — *fails* when
   `HERO_HISTORY_ROWS` is renamed `HERO_HISTORY_DAYS`;
3. `@@unique([spaceId, date])` still exists — *fails* when removed. This is the
   load-bearing one: it pins the schema fact the whole safety argument rests on,
   so if that constraint is ever dropped, every `{ rows: N }` caller becomes
   capable of under-covering and this test says so.

## Out of scope — recorded (Part 5)

1. **`lib/export/assemble.ts` was not browser-verified.** It is a download path,
   covered by typecheck and the suite; the change there is a one-line signature
   update with an already-correctly-named constant.
2. **The canonical "Last 90 days" preset is still `subMonths(asOf, 3)` = 92 days.**
   Unchanged from Part 4 — correct as a calendar quarter, but the label states a
   day count. Changing it moves every surface that renders a preset name.
3. **`getRecentSnapshots` keeps its name.** Only the parameter lied; the function
   does return recent snapshots. Renaming it would touch four source-scan guards
   that pin it as the canonical read boundary for no gain in clarity.
