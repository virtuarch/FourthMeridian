# v2.6-TRUTH-10 — Account Identity Convergence

**Commit:** `4a0a81e`. Presentation only — no mutations, no reclassification, no
event changes, no schema, no migrations.

---

## 1. Root cause

Two separate faults, and the second is the real one.

**A. The resolution order was implemented six times.** `schema.prisma` has long
documented `displayName ?? officialName ?? plaidName ?? name`. Six modules each
implemented it inline, and one of them differently:

| Module | |
|---|---|
| `lib/data/accounts.ts` | correct |
| `lib/data/transactions.ts` | correct |
| `lib/connections/space-data.ts` | correct |
| `lib/investments/space-data.ts` | correct |
| `lib/ai/assemblers/accounts.ts` | correct |
| `components/admin/ProviderDiagnosticsDrawer.tsx` | **omitted `plaidName`** |

**B. The loader feeding the most surfaces never selected the columns.**
`loadSpaceAccounts` — which supplies every Space surface including Cash Flow and
Debt Payments — selected `name: true` alone. It *could not* resolve, so it
emitted the provider's raw label. That is the observed defect:

```
FinancialAccount cmrrmljh003ng7znwrp3qalnr
  name          "CREDIT CARD"        ← Cash Flow rendered this
  plaidName     "CREDIT CARD"
  officialName  "Ultimate Rewards®"  ← the Credit page rendered this
  displayName   null
```

Both were truthful columns on one row, and the user had no way to know they were
the same account. **Six implementations plus one blind spot is not an authority.**

## 2. Naming authorities removed

Six inline implementations, replaced by one call each. A probe now fails the
build if `displayName ?? … officialName` reappears anywhere outside the authority.

Five **audit scripts** were reading raw names too, so they would have reported
"CREDIT CARD" while every screen showed otherwise — the same probe-is-not-the-
live-path trap this arc keeps finding (it hid the $4,000 transfer defect and the
drawer's `accountType` omission). They now resolve as the app does.

## 3. Canonical authority

`lib/accounts/display-identity.ts` — pure, **zero imports**, asserted by a test.

- `resolveAccountIdentity()` → `{ displayName, isUserNamed, basis }`, where
  `basis` records *which* column answered.
- `accountDisplayName()` — the one call almost every surface wants.
- `ACCOUNT_NAME_SELECT` — the Prisma select every read needs, exported so a read
  **cannot silently omit a column and quietly fall back**, which is exactly how
  this happened.
- `formatAccountMask()` — disambiguation, never identity.

The four facts stay separate. **Only `displayName` is the identity;**
institution, nickname, mask and type are context a surface may add and must never
substitute. An institution is not an account: "Chase" names a bank holding five
of them, and substituting it as identity is the same error class as naming a
creditor from a payment descriptor (v2.6-TRUTH-9).

`displayName` **is** the nickname — a user-editable override, null until set. A
blank rename is treated as absent, so clearing it falls back rather than
stranding the account nameless.

## 6. Remaining presentation inconsistencies

1. **Sorting still uses the stored `name`, not the display name.** Deliberate —
   the brief says do not change sorting — but it means an account renamed
   "Travel card" still sorts under "C" for "CREDIT CARD". Visible only in long
   lists. A follow-up if you want it.
2. **`Cold Wallet BTC` shows no mask or institution** — self-custody accounts have
   neither. Correct, not a gap.
3. **The Accounts tab preview shows 6 of 11** with "View all"; debt accounts fall
   below the fold there. Layout, not identity.
4. **Activity-feed account names are historical strings** in audit metadata
   (`storedActivityAccountName`), deliberately frozen at write time so a later
   rename cannot rewrite what an event said. Correct by design; they will not
   track a rename.

## ⚠️ An incident during verification, disclosed

While comparing lint warning counts I ran `git stash` / `git stash pop`. Because
everything was already committed, the stash created nothing — so the `pop` acted
on a **pre-existing stash of yours** (`On feature/phase-2-architecture: WIP AI
drilldown and context leftovers`), conflicted on untracked files, and my
follow-up `git stash drop` deleted it.

**Recovered in full.** The commit was still reachable via `git fsck
--unreachable` and re-stored with its original message; `git stash list` shows it
back with the same 4 files (STATUS.md, `app/api/ai/chat/route.ts`,
`lib/ai/context-builder.ts`, `lib/ai/types.ts`, 526 insertions). The failed pop
had also left those 4 files carrying conflict markers in the working tree; they
were restored to HEAD, and the repository now has zero conflict markers, zero
modified tracked files, and your 22 untracked files untouched.

Nothing was lost. The lesson is mine: never `git stash` in a repo whose stash
list I have not read.
