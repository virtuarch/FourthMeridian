# v2.6-REVIEW-1 — architectural state, measured

A review of where v2.6 actually is, starting from the codebase rather than the
roadmap. **No product code was changed.** One instrument was added
(`scripts/audit-surface-independence.ts`) and registered, because leaving an
unclassified audit on disk breaks the gate.

---

## 1. Is Financial Truth structurally complete?

**Yes, structurally. With one qualification that matters more than the answer.**

34 audits registered, 18 REQUIRED, all green on the live corpus. The truth layer
has a named authority for every question that caused a defect in this arc:

| Question | Authority | Enforced by |
| --- | --- | --- |
| which rows are banking? | `lib/data/banking-population.ts` | `audit-banking-population` |
| who classified this row? | `flowAuthority` + `lib/transactions/flow-authority.ts` | `audit-flow-desync` |
| when did this happen? | `economic-date.ts`, `event-identity.ts` | `audit-chronology-basis`/`-cutover` |
| is this one event or two? | `event-projection.ts`, `event-write.ts` | `audit-event-identity` |
| where did this money go? | `transfer-resolution.ts`, `transfer-maturation.ts` | `audit-transfer-authority` |
| is this a debt payment? | `debt-payment-attestation.ts` | `audit-debt-payment-attestation` |
| what is this account called? | `accounts/display-identity.ts` | source-scan guard |
| what does this balance mean? | `debt/balance-semantics.ts` | 11 surface consumers |
| what window is this? | `perspectives/financial-window.ts`, `data/snapshot-window.ts` | `audit-snapshot-window-claims` |
| is crypto banking? | `CRYPTO_LEDGER` + `NOT_CRYPTO_OWNED` | `audit-crypto-banking-leak` |

**The qualification: completeness of the layer is not the same as coverage of the
gate.** Three REQUIRED audits still pass on a corpus that cannot express their
failure mode (`estimated snapshots`, `2+ observation events`, `resolved
counterparty` are all absent from the seed), and `audit-event-identity`
structurally cannot catch the `removed[]` defect in CI at all — that needed a
fixture. Chronology was in the same state until two days ago.

So Financial Truth is **built**; it is not yet **fully witnessed**.

## 2. Has judgment actually left the product surfaces?

This is the claim the arc rests on, and it had never been measured — reading
module headers does not work, because 100+ modules under `lib/` describe
themselves as "THE" answer to something. A header is a claim, not a census.

`audit-surface-independence.ts` measures the opposite direction: where a
**rendering** surface does the arithmetic itself.

```
AGGREGATION  29 sites   a total that exists only in this component
RATIO        23 sites   one money quantity divided by another
VERDICT       1 site    a threshold comparison in a component
```

**The VERDICT count is the finding.** One site, and it is
`OpsCostWidget.tsx:31` — a milliseconds-to-seconds formatter, not a financial
judgment. **There are effectively zero financial verdicts left in components.**
That is a real structural result: grading has left the UI.

Reading the other two categories rather than counting them:

- **23 RATIO sites are almost entirely composition geometry** — `value / total`
  for a bar width or a "% of tier" label. Presentation, not judgment. The one
  financial ratio that *was* a judgment, `cashNow / expenseBaseline.amount`, now
  divides by an authority-supplied figure (v2.6-ASSESS-3).
- **29 AGGREGATION sites split cleanly in two.** Most are the denominator for
  those share bars — a local total feeding a local percentage, harmless. The rest
  are real financial figures summed in React, and they cluster in **one place**.

## 3. The remaining duplication is DEBT, not Assessment

`components/space/sections/DebtPayoffSection.tsx:194`

```ts
const weightedApr = withRate.reduce((s, r) => s + (r.a.interestRate! * r.bal.amount), 0)
                  / withRate.reduce((s, r) => s + r.bal.amount, 0);
```

`lib/ai/intelligence/annotations/metrics.ts:400`

```ts
const weightedAvgApr = totalForWeighting > 0
  ? Math.round((totalWeighted / totalForWeighting) * 100) / 100 : null;
```

Two weighted-average-APR implementations, and **they can disagree**:

| | component | engine |
| --- | --- | --- |
| population | accounts with `interestRate` that owe | FULL-visibility debt accounts with APR |
| weight | `amountOwed` in **display** currency | `amountOwed` in **reporting** currency |
| rounding | none | 2dp |
| taint | its own | `estimatedInputs` on the strategy |

This is the same shape as the expense-baseline divergence (v2.6-ASSESS-2): one
judgment, two definitions, neither disclosing which it used. The display-vs-
reporting currency split is the live hazard — those differ whenever the "view as"
override is active.

The same cluster also sums `used / limit / owed` (`DebtClient.tsx:465`), total
minimum payment (`debt-adapters.tsx:111`) and total monthly (`debt-perspective-
adapters.tsx:153`) locally.

**Debt is where liquidity was before this arc touched it.**

## 4. Re-evaluating Assessment's role

Measured, not assumed:

```
computeAssessment consumers:  app/api/ai/chat/route.ts
                              app/api/brief/route.ts
                              (nothing else)
weightedAvgApr consumers in app/ or components/:  NONE
```

**The architecture has evolved differently from the roadmap's assumption.**
`computeAssessment` did not become the canonical product assessment engine. It
became **the AI's reasoning layer** — a deterministic pre-computation that keeps
the model from inventing verdicts. Every product surface renders figures; none
renders a graded judgment.

That is not obviously wrong. It may be the right architecture. But it makes
"Assessment migration — rebuild Assessment on the new Financial Truth
authorities" the wrong next question. The real question is prior to it:

> **Are graded financial verdicts a product surface at all, or are they an AI
> input?**

If they are an AI input, `computeAssessment` is already correctly placed and
needs no migration — only the debt duplication above resolved so the AI and the
UI cannot disagree. If they are a product surface, the work is a *feature* —
designing what a user sees — and rebuilding the engine first would be building
the wrong thing well.

Two supporting observations:

- The engine already inherits Truth: its inputs are the domain assemblers, which
  consume `bankingTransactionWhere`, `display-identity`, the canonical windows
  and the flow authorities. A "rebuild on the authorities" would find much of it
  already done.
- Its verdicts have been wrong twice this arc in ways no user could have
  reported, precisely because no user sees them (`Infinity → EXCELLENT`,
  `READY_TO_INVEST` from absent evidence). An unobserved judgment layer is a
  judgment layer without a feedback loop.

## 6. Re-ranked, by dependency and leverage

**1. Close the three seed states.** *(architecture, unblocked, highest leverage)*
Everything else's safety rests on the gate meaning what it appears to mean. Three
REQUIRED audits currently cannot fail. This is the cheapest work with the largest
effect on confidence, and the instrument and pattern already exist.

**2. Converge the debt judgment.** *(architecture, unblocked)*
The last real duplicate-authority cluster in the product. Same shape the arc has
resolved four times; the display-vs-reporting currency split makes it a live
hazard rather than a theoretical one.

**3. Decide whether assessment is user-facing.** *(decision, not work)*
Blocks any sensible "Assessment migration". Cheap to answer, expensive to get
wrong by defaulting.

**4. Then, and only then, Assessment migration — or its cancellation.**
If the answer to 3 is "AI input", this item should be struck from the roadmap
rather than done.

**5. Retired-category deletion** — after `monthly_expenses` lands.

**6. Context Frame → Attention → Decision Engine** — genuinely closer than the
roadmap implies, provided 1 lands first.

### What changed versus the historical plan

- **"Assessment migration" drops from near-top to conditional**, and may not be
  work at all. The architecture evolved away from the premise the item was
  written under.
- **"One judgment layer" is done for liquidity and not started for debt.** The
  roadmap treated it as a single item; the measurement shows it was two, and the
  second was never visible because nobody had counted where components do maths.
- **Seed convergence rises to first.** It was written as plumbing. It is actually
  the precondition for trusting every other item's completion signal.

## Out of scope — recorded

1. **"Authority" has become the default framing.** 100+ modules under `lib/`
   claim to be "THE" answer to something. Some are genuine; many are ordinary
   modules wearing the vocabulary. The word is losing its signal, which makes the
   real authorities harder to find — the reason this review had to measure
   consumers rather than read headers.
2. **The census cannot tell composition from judgment.** It flags
   `value / total` identically whether that is a bar width or a verdict. Reading
   was required, and a future run will need the same reading.
3. **`app/` produced almost no hits**, which is expected — routes return DTOs.
   The census therefore says little about server-side duplication, where
   `debt-space-data.ts` / `liquidity/space-data.ts` and the assemblers all
   compute overlapping figures.
4. **28 pre-existing lint warnings**, all unused-variable, untouched.
