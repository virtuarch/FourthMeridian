# v2.6 — Pending Transactions, Balance Freshness & Current-State Accounting

**Investigation only.** No code, no schema, no migration, no write, no regeneration, no commit.
Branch `v2.6`, HEAD `bf1e665`. Live local corpus: 4,394 active transactions, 35 accounts, 5 Spaces.
Every figure below is a raw query result, recorded inline.

The historical engine answered *"what did I own and what was it worth?"* It could assume the past
had stopped moving. This engine cannot. It answers:

> **What is happening right now, and how do we say it truthfully while providers are still catching up?**

---

## 0. The finding that reframes everything

We already capture almost all the evidence this engine needs. We discard it at the seam.

| evidence | captured? | used? |
|---|---|---|
| `Transaction.authorizedAt` (Plaid `authorized_date`) | **3,996 / 4,394 rows** | **never** — not by any reader |
| `Transaction.pendingTransactionRef` (Plaid `pending_transaction_id`) | **60 rows** | **never** — no reconciler queries it |
| `Transaction.settlementState` | **4,042 rows** | **never** — `pending` boolean is read instead |
| `FinancialAccount.availableBalance` | **every Plaid account** | **never** — zero readers outside the write path |
| `FinancialAccount.balanceLastUpdatedAt` | **0 / 35 rows** (Plaid never sent it) | AI assembler only |
| `Transaction.counterpartyAccountId` | **0 / 669 transfer-ish rows** | read-time resolver only, never persisted |

So this is not mainly a *capture* problem. It is an **authority** problem: nothing owns the
question "what is the state of this economic event right now," so each surface answers it from
whatever column is nearest.

## 1. Transaction lifecycle — when did the economic event happen?

### 1a. What each provider exposes

| provider | authorization | pending id | posted date | settlement | reconciliation id |
|---|---|---|---|---|---|
| **Plaid** (Chase, Amex, Schwab, Robinhood) | `authorized_date` (+ `authorized_datetime`) | `pending_transaction_id` on the *posted* row | `date` — **redefined on posting** | `pending` boolean | `transaction_id`, **new on posting** |
| **Plaid Investments** | — | — | `date` | none exposed | `investment_transaction_id` |
| **BTC / on-chain** | broadcast (mempool) | none | first-confirmation block time | confirmation depth | `txid` (**stable across the whole lifecycle**) |
| **CSV / manual import** | none | none | user-supplied | none | `externalTransactionId` |

On-chain is the only provider whose identifier survives the lifecycle. Everywhere else, **posting
mints a new identity.**

### 1b. The date moves. Measured.

`Transaction.date` is written at `lib/plaid/syncTransactions.ts:387` as `new Date(txn.date)` —
Plaid's `date`, which for a pending row is the authorization date and for a posted row is the
**posted** date. `authorized_date` is captured to `authorizedAt` and never consulted.

Distribution of `date − authorizedAt` over the 3,996 rows that carry both:

| lag (days) | rows |
|---|---|
| 0 | 1,183 |
| 1 | 1,809 |
| 2 | 772 |
| 3 | 191 |
| 4–8 | 39 |
| 38 | 2 |

**2,813 of 3,996 rows (70.4%) sit on a date later than the day the economic event occurred.**

The user's coffee example, live from the corpus:

```
Tap Talabat Food   −$12.50   authorized 2026-07-29   →   date 2026-08-02   (moved 4 days)
Amazon             −$39.19   authorized 2026-07-23   →   date 2026-07-26   (moved 3 days)
Shake Shack        −$14.92   authorized 2026-07-16   →   date 2026-07-19   (moved 3 days)
```

Four of those cross a month boundary in the general case; two in this corpus cross a week boundary.
**A closed period is not closed** — a July purchase can still land in August's totals.

### 1c. Two records, not one — and sometimes neither

Plaid's pending→posted transition arrives as `removed:[pending_id]` + `added:[new posted row]`.
`syncTransactions.ts` tombstones the removed row (`deletedAt`, line ~690) and creates a new one.
The fingerprint fallback includes `txn.pending`, so a pending row can never match its own posted
successor.

Of the 60 posted rows carrying a `pendingTransactionRef`:

- **37** point at a tombstoned pending row — the intended path.
- **23** point at **nothing at all** — the posted row arrived before we ever saw its pending row.
- **0** point at a still-live row.

44 tombstoned rows exist, *all* `pending = true`. There is **no live double-count today** — I
checked this directly and the inner join is empty. But the identity of an economic event is
destroyed and re-minted on every posting, which is why nothing downstream can hold a stable
reference to "that coffee."

### 1d. The canonical date

> **The canonical date of an economic event is the earliest date at which the provider attests the
> event occurred, and it is immutable once observed.**

Resolution order, evidence-first:

1. `authorized_date` — the provider's own attestation of when it happened.
2. the `date` first observed while the row was **pending** — pending dates are authorization-shaped.
3. `date` — posted-only rows with no earlier evidence.
4. user-supplied date (imports).

Posting **never** rewrites it. Posting is a *lifecycle transition*, recorded as such.

⚠️ Rule 1 has a known trap: the two rows at lag 38 are almost certainly a provider re-issue, not a
38-day authorization. The rule needs a bound (reject `authorizedAt` more than ~N days before
`date`) and an explicit `CONTRADICTORY` state — the same shape the historical engine already uses.

## 2. Pending as first-class evidence

### 2a. One logical transaction, not two — recommended

The lifecycle is a property *of* an economic event, not a different event. The model should be:

```
EconomicEvent
  economicDate      immutable, from §1d
  lifecycleState    PENDING | POSTED | SETTLED | CANCELLED | EXPIRED | REVERSED
  observations[]    one per provider delivery: (providerId, state, amount, date, observedAt)
```

The provider row ids become *observations*, not identity. Identity is the event.

Why one record rather than two:

- Amounts change between pending and posted (tips, currency, partial captures). Two rows means two
  amounts and no statement of which is true.
- A closed period must stay closed. Two rows with two dates cannot guarantee that.
- The pending→posted link already exists in 37 of 60 cases; making it identity rather than a
  pointer removes the 23-case gap entirely — an event with no pending observation is simply an
  event whose first observation was POSTED.

### 2b. State transitions per provider

| transition | Plaid | on-chain | import |
|---|---|---|---|
| → PENDING | row with `pending=true` | mempool (**we do not ingest**) | n/a |
| PENDING → POSTED | `removed` + `added` with `pending_transaction_id` | first confirmation | n/a |
| POSTED → SETTLED | **not exposed** | N confirmations | n/a |
| → CANCELLED / EXPIRED | `removed` with **no** replacement | dropped from mempool | n/a |
| → REVERSED | a *new* offsetting row | a *new* offsetting tx | n/a |

Two honesty constraints fall straight out:

- **SETTLED is not observable for Plaid.** Do not model a state no provider attests. Either the
  enum stops at POSTED for card/bank rails, or SETTLED is explicitly `UNOBSERVABLE` there. Fabricating
  it would repeat the mistake the historical engine spent four slices removing.
- **CANCELLED and EXPIRED are indistinguishable from each other** on `removed`-with-no-replacement.
  Collapse them to one honest state (`WITHDRAWN`) rather than guessing which.

`removed` handling is currently a *blanket* tombstone — it cannot tell "this pending became that
posted row" from "this pending was cancelled." Those are opposite economic facts and today they
produce byte-identical database states.

### 2c. `pending` and `settlementState` already disagree

| `settlementState` | `pending` | rows |
|---|---|---|
| POSTED | false | 4,036 |
| **null** | false | **348** |
| PENDING | true | 6 |
| **null** | **true** | **4** |

352 rows carry a lifecycle claim in one column and nothing in the other. Two representations of one
fact, not co-maintained. The engine must retire one.

## 3. Balance authority — balances are observations

Today `FinancialAccount.balance` is a scalar with no provenance, read as truth by every current-state
surface.

Proposed authority — four distinct quantities, never interchangeable:

| quantity | definition | source | may be null? |
|---|---|---|---|
| **observed** | what the provider last said the balance was | `balance` | no |
| **available** | what the provider says is reachable now | `availableBalance` | yes — and its **meaning is account-type-dependent** (see §3b) |
| **predicted** | observed + provider-observed pending (§4) | derived | yes — null when unexplained |
| **freshness** | when the provider fetched it, and how old that is | `balanceLastUpdatedAt` ?? `lastUpdated` | — |

### 3a. Freshness is currently unmeasurable, and the UI claims otherwise

`balanceLastUpdatedAt` is **null on all 35 accounts** — Plaid marks
`last_updated_datetime` optional and these institutions do not send it. So we know when *we wrote*
the balance, never when the *institution* computed it. Those are different facts and only the
second answers "is this stale."

Worse, the surface that exists is optimistic:

```ts
// components/dashboard/SpaceDashboard.tsx:353
// "Surfaced in the header subtitle so no balance is read without knowing how old it is."
const newestAccountUpdate = accounts.reduce((best, a) => a.lastUpdated > best ? a.lastUpdated : best, …)
```

It takes the **MAX**. Live numbers:

| | |
|---|---|
| newest account update (what the header shows) | 2026-08-04 00:09 |
| oldest account update (reality) | 2026-06-09 10:00 |
| **spread** | **56 days** |
| accounts staler than 7 days | **24 of 35** |
| **value sitting behind a stale balance** | **$939,564 of $974,231 — 96.4%** |

The header says *"Updated 16 hr ago."* 96% of the money it describes has not been observed in eight
weeks. The comment states the correct intent; the reducer inverts it. A `MIN` would be honest; a
`MAX` is the most optimistic claim the data permits.

### 3b. `availableBalance` is polymorphic and unread

Zero readers outside the Plaid write path. And its meaning changes by account type — from the live
corpus:

| account | type | observed | available | gap | what "available" means |
|---|---|---|---|---|---|
| CHASE COLLEGE | checking | 5,106.77 | 1,106.77 | **4,000.00** | reachable cash |
| Amex HYSA | savings | 6,315.04 | 2,315.04 | **4,000.00** | reachable cash |
| Schwab Individual | investment | 901.66 | 0.00 | 901.66 | *settled* cash |
| **Chase CREDIT CARD** | debt | 562.37 | **33,022.48** | **−32,460.11** | **available credit** |

One column, three semantics. Any consumer that treats it uniformly is wrong for two of the three.

## 4. Balance reconciliation — can we predict without fabricating?

**Yes, and the corpus proves it to the cent.**

The proposed identity, using only provider-observed pending rows:

```
predicted = observed + Σ(provider-observed pending amounts)
```

Tested against an *independent* provider observation (`availableBalance`) — the prediction is never
fitted to it, so agreement is a genuine check:

| account | observed | Σ pending | predicted | provider available | verdict |
|---|---|---|---|---|---|
| **CHASE COLLEGE** | 5,106.77 | **−4,000.00** | **1,106.77** | **1,106.77** | **EXACT** ✓ |
| Chase CREDIT CARD | 562.37 | −77.60 | 484.77 | 33,022.48 | n/a — available *credit* |
| **Amex HYSA** | 6,315.04 | **0.00** | 6,315.04 | 2,315.04 | **UNEXPLAINED $4,000** |
| Schwab Individual | 901.66 | 0.00 | 901.66 | 0.00 | UNEXPLAINED (settlement) |
| Robinhood individual | 484.25 | 0.00 | 484.25 | 471.21 | UNEXPLAINED $13.04 |

Two conclusions, both load-bearing:

1. **The prediction works** where the transaction feed has caught up. Chase reconciles exactly.
2. **The gap is itself evidence.** The Amex HYSA has a $4,000 hold that *no pending transaction
   explains* — the balance feed knows about money the transaction feed has not delivered.

So the invariant is not "predicted must equal available." It is:

> **`observed − available − Σ(pending) = unexplained`. When `unexplained ≠ 0`, say so. Never smooth it.**

An unexplained hold is a *first-class output*, in exactly the vocabulary the historical engine already
uses: EXACT / PARTIALLY_ATTRIBUTED / UNAVAILABLE / CONTRADICTORY.

**Never** infer from recurring history or user behaviour — a prediction whose inputs the provider did
not attest is a forecast wearing an accounting costume.

## 5. Provider freshness — the feeds advance independently

Measured as `max(balance write date) − max(transaction date)` per institution:

| institution | accounts | balance written | newest tx | drift |
|---|---|---|---|---|
| Self-custodied (BTC) | 3 | 2026-08-04 | 2026-07-04 | **+31 d** (balance ahead) |
| American Express | 3 | 2026-08-03 | 2026-08-01 | +2 d |
| **Chase** | 3 | 2026-08-03 | **2026-08-03** | **0 d** |
| Robinhood | 2 | 2026-08-03 | *none* | **no tx feed at all** |
| Charles Schwab | 2 | 2026-08-03 | *none* | **no tx feed at all** |
| Alpha / Sample / Beacon / Demo / Example / Summit (seed) | 18 | 2026-06-09 | 2026-07-11 … 07-18 | **−32 to −39 d** (tx ahead) |

Three distinct regimes, all present simultaneously:

- **Balance ahead of transactions** (BTC): the balance is a live on-chain read; the transaction
  ledger is a paged import that stops early. Compounded by a known truncation — the BTC ledger holds
  25 of 28 on-chain transactions and there is no Σ-equals-balance invariant.
- **Transactions ahead of balance** (all seed institutions): 39-day drift, balances frozen at import.
- **Balance only, no transaction feed** (Schwab, Robinhood): 8 investment accounts hold just 40
  transaction rows between them; 6 crypto accounts hold 47.

**The feeds are independent and neither dominates.** Any model with a single "last updated" per
account is structurally unable to express this — which is precisely why the header can claim 16
hours while carrying 8-week-old balances.

The user's *"Amex updates before Chase"* is confirmed but is the milder version of the problem. The
sharper one is that a *single account's* balance and transactions have different ages.

## 6. Transfer maturation — classification is happening far too early

### The live example, complete

Both legs of one $4,000 transfer are in the database right now:

| leg | account | type | date | state | amount | descriptor | **classified** |
|---|---|---|---|---|---|---|---|
| source | Chase CHASE COLLEGE | checking | **2026-08-03** | **PENDING** | −4,000.00 | `ORIG CO NAME:AMERICANEXPRESS CO ENTRY DESCR:TRANSFER SEC:WEB` | **`DEBT_PAYMENT`** ✗ |
| destination | Amex High Yield Savings | **savings** | **2026-07-31** | POSTED | +4,000.00 | `Internet transfer from JPMORGAN CHASE BANK, NA DDA account XXXXX2058` | `TRANSFER` |

The destination is a **savings account**. This is a savings transfer, filed as a debt payment,
because the descriptor contains "AMERICANEXPRESS" and Amex also issues cards. `classificationReason`
is `PLAID_PFC_PRIMARY` — Plaid's own category, taken at face value, **while the row was still
pending and its counterparty unknown**.

### Three compounding failures

1. **Classified at first sight.** The decision was made from the source descriptor alone, at PENDING,
   with no destination evidence — and it is durable.
2. **The misclassification excludes it from its own repair.** `transfer-resolution.ts:114` targets
   `r.flowType === "TRANSFER"`. A row mislabelled `DEBT_PAYMENT` is never a candidate. **The only
   mechanism that could correct it is gated on it already being correct.**
3. **The window is too narrow anyway.** `TRANSFER_WINDOW_DAYS = 2`; these legs are **3 days apart**
   — and the destination posted *before* the source. Any matcher assuming source-precedes-destination
   fails here.

`counterpartyAccountId` is resolved on **0 of 669** TRANSFER / DEBT_PAYMENT / UNKNOWN rows. The
destination-aware seam exists in the schema and has never held a value.

### The maturation model

Classification must be a **function of evidence available**, re-evaluated as evidence arrives, with
specificity that only increases:

```
pending outflow, descriptor only        →  TRANSFER (direction known, destination unknown)
+ owned-account leg matched              →  INTERNAL TRANSFER
+ destination account type = savings     →  SAVINGS TRANSFER
+ destination account type = liability   →  DEBT PAYMENT
```

Today the pipeline jumps from step 1 to the *wrong* leaf and stops. The right default at step 1 is
the **least specific honest answer** — "a transfer out, destination unknown" — which is exactly the
`UNKNOWN` the historical engine treats as a legitimate terminal state rather than a failure.

And note **where the matching evidence lives**: at the moment the Chase leg was classified, the Amex
leg was visible only as an `availableBalance` gap. Transfer maturation therefore needs the *balance*
authority, not just the transaction feed. That coupling is the strongest argument for building these
as separate authorities that compose, rather than one transaction-centric engine.

## 7. The defects — one architecture, three faults

The six reported symptoms are **not** six bugs, and not one. They are **three faults**, each with a
single cause:

### FAULT A — no lifecycle authority (symptoms 1, 6-partial)

*Pending purchases move to the posted date.*

`date` is overwritten with the posting date; `authorizedAt` is captured and unread; identity is
re-minted on posting; `pending` and `settlementState` disagree on 352 rows. **70% of rows are dated
later than the event.** One cause: nothing owns the lifecycle.

### FAULT B — no balance authority (symptoms 2, 3, 6)

*Stale Chase balances · Amex updating before Chase · checking overstated because balances lag.*

Balance is a provenance-free scalar; `balanceLastUpdatedAt` is null everywhere; `availableBalance` is
written and never read; freshness is reported as a **MAX** across accounts. **96.4% of value sits
behind a balance older than 7 days, under a header claiming 16 hours.** One cause: balances are
modelled as truth rather than observation.

Note the corrected diagnosis of symptom 6: checking is *not* overstated because balances lag
transactions. Chase's drift is **0 days**. It is overstated because `balance` (5,106.77) is shown
where `available` (1,106.77) is the reachable figure — a **$4,000 overstatement on one account**,
caused by reading the wrong quantity, not a stale one.

### FAULT C — premature classification (symptoms 4, 5)

*HYSA transfer classified as debt payment · unresolved transfers stay unresolved.*

Classification is a one-shot write at ingest; the repair path is gated on the classification being
right; the match window (2 d) is shorter than observed provider skew (3 d); counterparty is resolved
on 0 of 669 rows. One cause: classification is treated as a fact rather than a current best estimate.

**A, B and C are independent** — each can be fixed without the others, and none fixes another. But C
*depends on* B for its evidence (the destination leg was balance-only when the source was classified),
which fixes the implementation order.

## 9. Recommended architecture — five authorities

Do not build one "current state engine." Build five, composing in one direction. This mirrors what
worked historically: `loadHoldingOwnership` → `buildHistoricalHoldings` → `valuePortfolioAsOf`, each
independently assertable.

```
  1. LIFECYCLE          economic identity, immutable economicDate, observations[]
         │                 "when did this happen, and what state is it in?"
         ▼
  2. BALANCE            observed · available · freshness · confidence
         │                 "what did the provider say, and when?"
         ▼
  3. RECONCILIATION     predicted = observed + Σpending; unexplained is an OUTPUT
         │                 "what is reachable, and what can't we account for?"
         ▼
  4. TRANSFER           maturation over evidence from (1) AND (3)
         │                 "where did it go, given what we now know?"
         ▼
  5. CURRENT-STATE      the read authority every surface consumes
                          "what do we tell the user, and how sure are we?"
```

Authority 4 reads 3, not just 1 — the HYSA case proves the destination evidence can be
balance-only. That dependency is the reason B must ship before C.

### Invariants

1. **`economicDate` is immutable once observed.** A lifecycle transition never moves it.
2. **A closed period stays closed.** No posting may change a total for a period already reported.
3. **Identity survives the lifecycle.** Provider row ids are observations, not identity.
4. **`observed − available − Σpending = unexplained`**, and `unexplained ≠ 0` is *reported*, never absorbed.
5. **No predicted balance without provider-observed pending.** Never recurrence, never behaviour.
6. **Freshness is per-account and per-feed.** Never a single scalar, never a MAX.
7. **Classification specificity only increases.** A later evidence arrival may refine, never contradict-and-hide.
8. **Never model a state no provider attests** (SETTLED on card rails; CANCELLED vs EXPIRED).
9. **`available` is read through an account-type-aware accessor**, never as a bare column.
10. **Every current-state claim carries its basis** — observed / predicted / stale — or it does not ship.

## 10. Proposed slices

Small, independent, each verifiable alone. Ordered so every slice has a consumer.

| # | slice | fault | depends on | ships |
|---|---|---|---|---|
| **L1** | Freshness truth: per-account age, `MAX`→honest distribution in the header, per-account staleness on every `p.accounts` surface | B | — | **read-only, no schema** — highest value/effort ratio in the list |
| **L2** | `availableBalance` accessor: one type-aware authority (cash / settled cash / credit), plus probes that it is never read raw | B | — | no schema |
| **L3** | Balance observation authority: observed / available / freshness / confidence as one read model; `balanceLastUpdatedAt` capture hardened + honest null | B | L1, L2 | no schema |
| **L4** | Reconciliation: `predicted` + `unexplained`, in the EXACT / PARTIAL / UNAVAILABLE / CONTRADICTORY vocabulary | B | L3 | no schema |
| **L5** | Liquidity surfaces consume predicted; Debt stays observed; both labelled | B | L4 | no schema |
| **L6** | Lifecycle read model: `settlementState` becomes the single lifecycle column, `pending` retired behind it; the 352 disagreeing rows reconciled | A | — | **repair, no schema** |
| **L7** | `economicDate` as a derived read authority (`authorizedAt` bounded → first-pending date → `date`), with the CONTRADICTORY guard for the lag-38 shape | A | L6 | **derive first, persist later** |
| **L8** | Event identity: pending↔posted as one logical event; `removed` distinguishes withdrawal from transition | A | L7 | **schema — the only one** |
| **L9** | Classification becomes re-evaluable: `DEBT_PAYMENT` rows enter the transfer resolver; window widened past observed provider skew; default is the least-specific honest answer | C | L4 | no schema |
| **L10** | Transfer maturation: counterparty resolved from transactions **and** balance-gap evidence; specificity monotonic | C | L9 | persists `counterpartyAccountId` |
| **L11** | Standing probes + observability (below) | all | — | — |

**Recommended order: L1 → L2 → L6 → L3 → L4 → L5 → L7 → L9 → L10 → L8.**

L1 first because it is read-only, ships in one slice, and converts the single most misleading number
on the dashboard. L8 last because it is the only schema change and every other slice reduces its
risk. **L6 and L7 before L8**: derive `economicDate` and prove it against the corpus *before*
persisting anything — the same discipline that made the historical engine safe.

### Standing integrity probes

1. `economicDate` never decreases for a given event across syncs — the closed-period guarantee.
2. A period total, once reported, never changes because of a posting.
3. `observed − available − Σpending = unexplained`, and unexplained is surfaced wherever non-zero.
4. No predicted balance exists without a provider-observed pending row behind it.
5. No surface reads `availableBalance` raw (static, comments stripped).
6. Freshness is never a `MAX` across accounts (static — this one would have caught the header).
7. Every `TRANSFER`/`DEBT_PAYMENT`/`UNKNOWN` row is *eligible* for the resolver.
8. Classification specificity is monotonic across re-evaluations.
9. `pending` and `settlementState` never disagree (until `pending` is retired).
10. Σ(on-chain ledger) equals the wallet balance — **does not exist today**, and the BTC ledger is
    truncated at 25 of 28.

### Observability

Per-institution, per-feed: newest observation age, drift between balance and transaction feeds,
pending population and its age distribution, unexplained-hold total, unresolved-transfer count and
age. All derivable read-only today except the last two.

### Production, migration, compatibility

- **L1–L7, L9 are read-model changes** — deployment-only, no data change, instantly revertable.
- **L6 is a repair**: 352 rows with disagreeing lifecycle columns. Apply the historical arc's proven
  shape — read-only audit, apply only what it reports, prove a zero-write second pass.
- **L8 is the only migration.** Additive columns first, dual-write, backfill `economicDate` from
  evidence, verify against the corpus, then cut readers over. **Never** rewrite `Transaction.date` in
  place: it is the historical engine's input and its immutability is load-bearing.
- **Backwards compatibility:** `date` remains as the *posting* date — it is a real fact and the
  posted-basis reconstruction depends on it. `economicDate` is added alongside. They answer different
  questions and both should exist.
- **Standing rule, unchanged:** local repair does not imply production is repaired. 96.4% of value is
  behind a stale balance *locally*; production must be measured, not assumed.

## 11. What I could not determine

- **True provider latency** (Chase vs Amex clock-time lag) is not measurable from this corpus: only
  the newest `lastUpdated` per account is retained, so there is no refresh history. Measuring it
  needs L1's observation log, which is itself a reason to build it early.
- **Whether Plaid ever sends `last_updated_datetime`** for these institutions — 0 of 35 here, but the
  seed accounts never went through Plaid at all. Needs a production sample.
- **The 2 rows at lag 38** — provider re-issue or genuine long authorization. Two rows; worth reading
  directly before L7 encodes a bound.
- Whether `SETTLED` is exposed by any provider we intend to support beyond Plaid and on-chain.

## 12. Database safety

Read-only throughout. Every query was a `SELECT`. No schema change, no migration, no write, no
regeneration, no price acquisition, no event ingestion, no commit. Counts recorded before and after
and unchanged: transactions 4,438 (4,394 active + 44 tombstoned), price observations 9,036,
investment events 51, snapshots 1,686.
