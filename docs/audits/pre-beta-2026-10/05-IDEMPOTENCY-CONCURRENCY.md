# 05 — Idempotency and Concurrency

Pre-beta audit of Fourth Meridian · `v2.6` · HEAD `cde8fa0e25d2c744933109b41611d1dd65a1f9a8` · 2026-10-21 · read-only. Finding IDs `IDEMP-nnn`. Installed DB constraints are evidenced from `prisma/schema.prisma` and `prisma/migrations` (local Postgres was down); Vercel cron overlap/retry semantics and whether Vercel drains `void` promises after a response are UNVERIFIED.

## 1. Verdict

Concurrency posture is uneven. It is strong where it was designed deliberately: the AI allowance reservation (per-user advisory lock, in-flight counter, fail-closed, `finally` release, real-Postgres CI suite), the Daily Brief claim (unique lease, token-fenced completion), the Plaid per-Item compare-and-set lease, notification dedupe, insert-only price/FX archives, position-observation and investment-event uniques. It is weak where it was assumed: CSV import has no idempotency key and duplicates rows on concurrent submission (IDEMP-001); the account purge is non-transactional, re-checks "due" only once, and can run twice via the fallback route (IDEMP-002, destructive); job dispatch is check-then-insert with a six-minute soft window and no row-level claim; the scheduled crypto sweep takes no wallet lock; the Plaid lock release is unfenced and the cursor write is not compare-and-set; webhooks are not deduplicated beyond the five-minute `iat` window. No P0: no double-charging path, no unbounded spend, no wrong-customer path. Weighted score: **6.2 / 10**.
